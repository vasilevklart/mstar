A model declares what each node keeps between steps in `declare_state()` and reaches it through handles. `mstar.engine.state` is the engine surface a ported package imports: `test/modular/test_state_lint.py` refuses any other engine import outside its listed exceptions ([Lint rules](/adding_models#lint-rules)). Its `__all__` only grows. [Step 2a](/adding_models#step-2a-declare-your-state), [Step 4a](/adding_models#step-4a-declare-the-step) and [Reaching your state](/adding_models#reaching-your-state) explain each name in context.

## Example {#example}

One autoregressive node with a paged KV array and a sampler. Each piece is from a file in the tree, shortened.

Declare the state on the model (`mstar/model/orpheus/orpheus_model.py`; its `Rope` also carries the Llama 3.1 factors):

```python
from mstar.engine.state import Array, Attend, Causal, KVEntry, Positions, Read, Rope, Sampler

KV_CACHE, SAMPLER, ATTN = "kv_cache", "sampler", "attn"   # the names mstar/model/orpheus/config.py defines

def declare_state(self) -> list[Array | Sampler]:
    c = self.config
    return [
        Array(
            KV_CACHE, nodes={"LLM"}, layers=frozenset(range(c.num_hidden_layers)),
            entry=KVEntry(heads=c.num_key_value_heads, head_dim=c.head_dim),
            max_len=c.max_position_embeddings,
            positions=Positions(rope=Rope(theta=c.rope_theta)),
            reads={ATTN: Read(mask=Causal(), op=Attend(q_heads=c.num_attention_heads))},
        ),
        Sampler(SAMPLER, nodes={"LLM"}, vocab_size=c.vocab_size, penalty=True),
    ]
```

Bind the handles. The node takes both (`DeclaredTokenDecoder.bind_state` in `mstar/model/components/sampled_token_decoder.py`), and each attention layer takes the array's (`ParallelAttention.bind_state` in `mstar/model/components/distributed/attention.py`):

```python
# the node
def bind_state(self, handles):
    self.kv = handles[self.KV_CACHE]
    self.sampler = handles[self.SAMPLER]

# each attention layer, built with its layer id
def bind_state(self, handles):
    self.state = handles.get(self._kv_key)
```

Call them in the forward. The layer rotates and attends; the node picks each row's last token and draws:

```python
q, k = rope(self.state, q, k)                          # rotate at this step's positions
out = add_read(self.state, self.layer, q, k=k, v=v)    # add this step's k and v, then attend

hidden = at_last_token(self.kv, hidden)                # each row's last token in this step
tokens = sample(self.sampler, logits)                  # one draw per row
```

Declare the step. `SampledTokenDecoder.declare_step` builds one `Segment(request_id, "main", span)` per row, padding rows included, and `DeclaredTokenDecoder.node_step` says what the step does to each declaration:

```python
def node_step(self, segments, prefill_tokens, advance):
    return SubmoduleStep(
        segments=segments,
        state={self.KV_CACHE: ArrayStep(advance=advance), self.SAMPLER: SampleStep(prompt_tokens=prefill_tokens)},
    )
```

Tune it in the deployment, under the declared names (`configs/orpheus.yaml` with a `resources:` block added; the values are examples):

```yaml
model: "orpheus"
max_seq_len: 131072
resources:
  kv_cache:            # the Array: a paged KV pool
    max_num_pages: 1024
    cpu_offload_pages: 128
  attn:                # its read: an attention over the pool
    flashinfer_backend: fa2
  sampler:             # the Sampler
    enable_logprobs: true
node_groups:
  - node_names: [LLM]
    ranks: [0]
    graph_walks: [prefill, decode]
  - node_names: [snac_decoder]
    ranks: [1]
    graph_walks: [snac_chunk]
```

Test it on CPU, with the Rust extension built (`maturin develop --release -m rust/Cargo.toml`, [Testing](/adding_models#testing)):

```bash
CUDA_VISIBLE_DEVICES="" HF_HUB_OFFLINE=1 python -m pytest -q \
    test/modular/test_state_lint.py test/modular/test_model_contracts.py test/modular/test_orpheus_model.py
```

## Names {#names}

Everything in `mstar.engine.state.__all__` (`mstar/engine/state/__init__.py`), by kind.

| Kind | Name | What it is |
|----|----|----|
| Declaration | `Array(name, *, nodes, layers, entry, max_len, reads=, updates=, rewritable=, labels=, positions=)` | Per request, label and layer, entries at log positions `0` to `n - 1`. `max_len=0` keeps nothing between steps; `None` has no bound. |
| Declaration | `Value(name, *, nodes, layers, entry, updates=)` | A rewritable array of one entry: a recurrent state, a carried tensor, host fields. |
| Declaration | `Entry(tensors, *, host=)` | What one entry holds: named `TensorType` fields, and host fields. |
| Declaration | `TensorType(shape, *, dtype, shard=None)` | A field's global shape, its dtype (`None` is the compute dtype) and the axis split across TP ranks. |
| Declaration | `KVEntry(*, heads, head_dim)` | An `Entry` of `k` and `v`, sharded on their heads. |
| Declaration | `Positions(rope=None)` | A position counter per request and label on an append-only array. |
| Declaration | `Rope(theta=, rotary_dim=, interleave=, scale=, low_freq_factor=, high_freq_factor=, old_context_len=, dtype=, table_dtype=, longrope=)` | The rotation the positions apply. |
| Declaration | `LongRoPE` | A short and a long factor set, picked per request by prompt length; `LongRoPE.from_hf(config)`. |
| Declaration | `Sampler(name, *, nodes, vocab_size, penalty=True, min_p=False, eos_ids=(), draws=1)` | A sampler and the kernel variants its captures record. |
| Declaration | `SeqShard(name, *, nodes, labels=, walks=None, exchange="auto")` | The node's steps may split over its SP ranks. |
| Read | `Read(mask, op=None, layers=None, walks=None, queries=None, packed=True, segmented=False)` | How a layer reads an array, per layer and walk. |
| Mask | `Causal()`, `Window(size)`, `Block()`, `Bidirectional()` | Which entries each query sees: up to its own, the last `size`, its own segment (`max_len=0`), every entry of its row. |
| Op | `Attend(q_heads)` | Attention with the model's query heads, a multiple of the entry's heads. |
| Op | `CausalConv(activation="silu")`, `GatedDeltaNet(qk_l2norm=True, scale=None)`, `Mamba2(time_step_limit=)` | Kernels that read and write a `Value`'s `conv`, `state` or `ssm` field in place. |
| Read result | `Reached` | What a read with no op returns: `fields` and `row_offsets`, tensors the caller owns. |
| Request | `SampleSettings` | One request's settings for one sampler, from `get_request_resource_configs`. |
| Request | `Layout(spans=, growth=, scratch=, max_growth=)` | What a request writes to one label, from `process_prompt`'s `state_layout`. |
| Request | `Span` | One write in a layout: `kind` (`ids`, `digest`, `rows`), `walk`, `length`, `advance`, `source`, `scratch`, `opens_step`. |
| Step | `Segment(request_id, label, span)` | One request's contribution to one label in a step. |
| Step | `ArrayStep(segments=, keep=, forks=, placeholders=, eager_add=, fixed_layout=, advance=, position_ids=, host=)` | What one step does to one array. |
| Step | `SampleStep(apply_penalty=, apply_filters=, prompt_tokens=, kept_rows=)` | What one step does with one sampler. |
| Step | `Fork(src, dst, at, rows=None)` | Fork one label from another, at `"start"` or `"end"` of the step. |
| Step | `SlotLease` | The graph slot a step replays on, passed to `declare_step` as `slot_lease`. |
| Call | `add_read(h, layer, q, *, keep=None, **fields)` | A layer's add, then its read, behind one graph break. |
| Call | `rope(h, q, k)` | `q` and `k` rotated at this step's positions with the declared `Rope`. |
| Call | `position(h, rid_handle, label)`, `positions(h)` | A request's next position on the host; this step's position ids on the device. |
| Call | `at_last_token(h, x, *, label=None)` | `x` at each (row, label)'s last token in this step. |
| Call | `sample(s, logits)`, `last_sampled(s)` | One fresh draw per row; each row's last sampled token, for a `DeviceLoopback`. |
| Call | `causal_conv(h, ...)`, `gated_delta_net(h, ...)`, `mamba2(h, ...)` | Run a `Value`'s update kernel for one layer. |
| Call | `host(h, request, label, layer)` | One entry's host fields, as the last committed step left them. |
| Call | `scatter(shard, *xs, dim=None)`, `gather(shard, *xs, dim=None)`, `split_range(shard)` | This rank's share where the step splits; every rank's share back; this rank's range. |
| State op | `state_op(*, adds=, writes=, reads=, mutates=, formats, reference)` | Make a kernel that writes state in one launch a state op, with a reference over the calls above. |
| State op | `PagedNHD(dtypes=, devices=)`, `PagedNHDTarget` | A storage format a state op can address, and where it writes this step's entries on one layer. |

A handle also has methods: `add(layer, *, keep=None, **fields)`, `read(layer, q=None)`, and on a `Value` `write(layer, **fields)` and `set_start(fields)`. A shard handle has `ranks`.

These import from `mstar.engine.state` but stay out of `__all__`, so they can change: `SubmoduleStep` (the engine's own dataclass), `kernel_setting` (temporary, with `kernel_settings()`), `MAX_POSITION_KWARG` (the prompt length a `LongRoPE` request picks its table by), and the fused draw (`fused_draw_args`, `drew`, `FusedDrawArgs`, `draw_row`, `draw_row_layout`), which one model uses.

## What the engine builds {#resources}

The engine builds one resource per declaration, read and update, under the declared name, and a deployment tunes it under `resources:` by that name. The same name is what `kernel_settings()` keys its defaults by. An unknown key raises at load, so a misspelled setting is never ignored.

| Declaration | Resource | Key | `resources:` keys |
|----|----|----|----|
| `Array` with `max_len` above 0 | `KVSpec` with a `PagedKVConfig`: a paged KV pool | the array's name | `max_num_pages`, `page_size`, `max_seq_len`, `cpu_offload_pages`, `prefix_cache`, `prefix_cache_salt`, `prefix_cache_tp`, `context_parallel` |
| its `Attend` read (`Causal`, `Window` or `Bidirectional`) | `AttentionSpec` over the pool | the read's key | `backend` (`auto`, `flashinfer`, `dense`, `xpu_paged`), `flashinfer_backend` (`auto`, `fa2`, `fa3`), `decode_tensor_cores`, `decode_fmha` |
| its `Attend` read with `queries=` | `CrossAttentionSpec` over the pool | the read's key | `backend` (`auto`, `flashinfer`), `flashinfer_backend`, `decode_tensor_cores` |
| its `Positions` | `PositionSpec` | `rope`, or `<x>_pos` for an array named `<x>_kv` | none |
| `Array` with `max_len=0` and a `Block` read | `RaggedAttentionSpec`, or `RaggedCrossAttentionSpec` with `queries=`; reads of one kind, nodes and config share the first one's | the read's key | `backend` (`auto`, `flashinfer`, `dense`, `cudnn`, or `sdpa`, which builds no resource), `flashinfer_backend`, `max_segments_per_request`, `max_segments_per_step`, `max_tokens_per_request` |
| `Array` with `max_len=None` and one `Window` read | `BoundedKVSpec`: one slot per request | the array's name | `max_slots` |
| `Value` with tensor fields | `RecurrentStateSpec`: one slot per request and label | the Value's name | `max_slots`, `state_dtype` (with a `GatedDeltaNet`), `prefix_slots` |
| its `GatedDeltaNet` or `Mamba2` update | `LinearAttnSpec` over the Value's pool | the update's key | `backend` (`flashinfer`, the default and the only backend GDN and Mamba-2 run) |
| its `CausalConv` update | runs inside the Value's linear attention | the linear attention's | none |
| `Value` with host fields only | nothing on the device | none | none |
| `Sampler` | `SamplerSpec` | the sampler's name | `enable_logprobs`, `enable_processed_logprobs`, `greedy_capture` |
| `SeqShard` | `SeqShardSpec` | the shard's name | `min_tokens`, `exchange` (`auto`, `none`, `ulysses`, `all_gather`, `ring`) |
| `lora_roots()` | `LoraSpec`, only with a `resources: lora:` block | `lora`; each node's pool is `lora@<node>` | `max_slots`, `max_rank`, `cpu_capacity`, `adapters`, `targets`, `runtime_updates`, `runtime_update_timeout_s` |

`kernel_settings()` reaches a few fields the engine does not pick yet: `splits`, `decode_fmha` and `decode_tensor_cores` on a paged read, `splits` on a `GatedDeltaNet`, `max_segments_per_request`, `max_segments_per_step`, `compile_op` and `workspace_mb` on a `Block` read, and the pool size under the array's name (`max_num_pages`, or `max_slots`).

## Resource notes {#resource-notes}

### Paged KV {#paged-kv}

`PagedKVConfig` carries the model geometry and `max_seq_len`; the keys a deployment tunes are in the table above. `max_num_pages` defaults to 2048, and `cpu_offload_pages` is the number of pinned host pages used for offload (0, the default, disables it). A pool keeps only a window of the layers a windowed attention over it runs ([sliding windows](#attention)); its `page_size`, `max_num_pages` and `cpu_offload_pages` then work as described there. A pool whose nodes can run on several workers, as BAGEL's LLM nodes do under CFG parallel, has a leader node whose pool admits each request. A declared array on several nodes takes as leader the node that runs every walk any of its nodes runs, `LLM` for BAGEL under CFG parallel, and none where no node or several do; left without one, each worker's pool admits requests on its own.

Two lockstep-parallel nodes on one worker (TP, SP or CFG nodes placed on the same ranks) must not share a resource whose state rank 0 decides for the other ranks outside the step that uses it: a resource implementing `supports_eviction`, `lease_cached_prefix` or `page_trail`, which the paged KV cache does with or without host offload. The other ranks replay each decision with the next step of the node it was recorded under, so two nodes on one such resource could admit out of step. The conductor refuses that placement (`Resource.journals_resident_moves` says which resources it covers); give each node an array of its own, or place the nodes on different workers.

### Attention over a paged array {#attention}

`backend` selects `auto` (the default, which lets the engine pick the platform's paged backend, FlashInfer for now), `flashinfer` or `dense`, or `xpu_paged` on Intel XPU. Leave it at `auto` unless the model needs a specific kernel. `dense` runs one varlen pass over each stream's frozen prefix (gathered from the pages once) and the step's fresh K/V, eager only: FA3 (AITER on ROCm), or FlashInfer's ragged prefill where FA3 has no kernel for the GPU, the same choice the ragged resources make (`dense_or_flashinfer`), with `flashinfer_backend` picking its kernel. The engine plans and runs a tiny layout on that kernel when it builds the resource, so a backend the GPU or FlashInfer build cannot run stops the server with a `ValueError` naming it. Its wrappers share one workspace, taken at build. `flashinfer_backend` selects a kernel generation: `"auto"`, `"fa2"` or `"fa3"` when the FlashInfer backend is selected.

`decode_tensor_cores` (default `True`) runs one-token decode rows on FlashInfer's tensor-core kernel; `False` picks the CUDA-core decode kernel, which can be faster for MHA and narrow GQA (few query heads per KV head). Measure before changing it: Whisper, Qwen3-ASR and Qwen3-TTS set `False` in `kernel_settings`. `decode_fmha` (default `False`) runs captured one-token decode rows on FlashInfer's trtllm-gen fmha kernel on Blackwell, with no FlashInfer plan per step; a geometry trtllm-gen has no kernel for keeps the paged kernel, with a warning. Eager steps and prompt rows stay on the paged kernels. Qwen3.5 declares `True`.

A `Window(N)` read is a sliding window: each query attends to the last `N` positions, its own included, and the cache keeps only about the last `N` tokens of this attention's layers per request, returning the rest to the pool, so long requests take far fewer pages. It needs the FlashInfer backend, causal attention, a paged NHD cache and the read's layers, which the engine maps to the pool's layer indices. The cache's other layers keep every token, and the reads over it that declare no window run them (Command A+); each attention refuses a layer it doesn't run. The cache works this out from its attentions before anything is built (`derive_kv_groups`); a window at least the cache's `max_seq_len` keeps every token, so it costs nothing. Startup refuses a window over another kind of cache, a layer declared twice, two different windows over one cache (one per cache for now), a window over every layer of a cache, other layers that no attention without a window reads, cross attention over such a cache, and a backend other than FlashInfer; its kernel must be `auto` or `fa2`, or `fa3` on SM90, and from SM100 `auto` runs `fa2`. The window's pages hold `page_size × full layers / sliding layers` tokens, which must be whole. Left unset, the page (`tokens_per_page`) is the smallest whole one whose pages of either group hold at least 64 tokens (192 for 13 full and 39 sliding layers, 184 for 16 and 46); a `page_size` in the YAML must be a multiple of `sliding layers / gcd(full, sliding)`. A window is kept in whole pages of its layers plus up to one more, so with few sliding layers among many full ones (1984-token sliding pages at 31 full and 1 sliding) a short window saves little. `max_num_pages` and `cpu_offload_pages` count pages of every layer at the declared `page_size`, or at 128 tokens when it is unset, so the pool's bytes don't move with the derived page. Such a cache doesn't prefix cache yet, so its `prefix_cache` goes off (logged at info), and a serving config's `prefix_cache: true` is refused. With `context_parallel` the window's layers stay whole on every partner ([Context parallelism](#context-parallelism)). It doesn't fork, serve a node on another instance (replicas included) or hand out `write_slots` yet either; each of these is refused.

A read with `queries=` is cross-attention over a paged context that is written once and never extended ([Cross-attention](/adding_models#cross-attention-encoder-decoder-models)). Only FlashInfer is implemented. A step whose rows each query one token runs FlashInfer's decode kernel, and `decode_tensor_cores` picks its variant as above.

### Attention within a step {#ragged-attention}

An array with `max_len=0` builds cacheless (ragged) varlen attention over the segments packed into one forward. Nothing is paged, and nothing carries to the next step. Its config holds the read's heads and head dim (pre-sharding), an `sm_scale` that defaults to `head_dim ** -0.5`, `backend`, `flashinfer_backend`, the two graph ceilings `max_segments_per_request` (`max_segments_per_step` for a `one_row_per_step` region) and `max_tokens_per_request`, `compile_op` and `workspace_mb`. The ceilings size capture buckets, which is a memory-against-coverage trade the deployment makes, not the model. A resource sized per step refuses `max_segments_per_request`, which it would ignore. The heads are split across the node's TP ranks (TP × SP over a label the node's shard lists, on a node whose shard splits). `workspace_mb` is the floor of each label's FlashInfer workspace per slot (default `MSTAR_WORKSPACE_BUFFER_MB`, 512, which doesn't apply once it is declared): a plan that asks for more at startup grows it. A node with many labels can declare less, since a ragged prefill only uses it for split-KV partials. Where the node's sequence shard lists a label the resource plans, the resource attends it by Ulysses, splitting the heads over TP × SP on a node whose shard splits ([Sequence and context parallelism](#sequence-parallelism)). `compile_op` and `workspace_mb` are the model's declaration; the serving config's `resources:` overrides take only the backends and the ceilings.

`auto` (and an explicit `flashinfer`) plan through FlashInfer's ragged prefill wrapper. For a self-attention whose config names neither a backend nor a `flashinfer_backend` (`None`, the default; an explicit `auto` is FlashInfer's own choice), `auto` first reads the `ragged_attention` kernel table (`mstar/kernels/tables/ragged_attention/`, see [Tuned kernel configs](/adding_models#tuned-kernel-configs)) for the rank's head geometry on the GPU. An eager plan runs the row its layout's longest query segment falls in, so one slot can run a different kernel from one layout to the next; a captured bucket runs the row of the layout that first plans it. On `sm_103` the table names torch's cuDNN SDPA (`cudnn`) for klein 4B / 9B and Z-Image's geometries (24, 32 and 30 heads of 128; Wan2.2-TI2V-5B's 24 heads read klein 4B's entry, LTX-2.5's 32-head video self-attention klein 9B's), because under a CUDA graph FlashInfer's `auto` stays on FA2 there (its cutlass plan can't be replanned in graph mode, and its cuDNN path needs cuDNN 9.24). An entry whose larger sizes no served model has run bounds them with a numeric last row and a `"*"` row naming `flashinfer`, the resource's own default. A GPU of the architecture reads the file whichever model it is, and the build-time log names the GPU the row was swept on. Where no table has the geometry, `auto` is FlashInfer with its own `auto` choice.

The cuDNN wrapper runs a layout of equal-length segments, a DiT batch's, as one dense `[segments, S, H, D]` call. A captured one replays only the layout it was planned with, so a captured bucket takes it only when the step that plans it declares `ArrayStep(fixed_layout=True)`, and stays on FlashInfer otherwise. The DiT scaffold's denoise step declares it on each of its arrays: every row of a denoise bucket, padding rows included, spans the bucket's tokens. An eager layout of unequal segments runs FlashInfer. It is self-attention only. A config that names `backend: cudnn` fails at build where cuDNN can't run it: on a cross-attention, under GQA, in a dtype other than bf16 / fp16, or at a head dim FlashInfer pads. `dense` plans the same layouts into static `cu_seqlens` buffers and runs FA3 `flash_attn_varlen` (AITER on ROCm) instead, with no page scatter, or FA3's fixed-length kernel for an eager plan of one non-causal segment on Hopper (and, at head dim 128, once per segment for a plan whose segments are all at least 1536 rows). If that kernel is not importable, the factory logs a warning and builds FlashInfer. The fallback does not cover a GPU or dtype the kernel lacks: `fa3-fwd` 0.0.3 is built for Hopper (`sm_90a`) and runs bf16 but not fp16. `backend: sdpa` runs SDPA outside the resources and builds none; it is refused over keys the node's shard splits.

A `Block` read with `queries=` is cross-attention between spans (a DiT's video queries over text keys): each pair is planned as its own layout, pairing each request's query span with that request's key span, and it is never causal. One resource has one head geometry. A label exchanged over SP ranks on its step can't return a log-sum-exp; where keys split, the resource merges the partials itself (LTX-2.5's audio queries over each rank's share of the video tokens, merged by `gather_merge`).

### Bounded KV {#bounded-kv}

An array with `max_len=None` and one `Window(size)` read keeps, per request, its newest `size` entries in a fixed slot. A request takes a slot when it first runs and keeps it; the window is a ring overwritten in place, so a step reserves and releases nothing. A step's layout is computed on the host from the position the step declares, which is also what lets rows at different positions share a batch and a captured graph. Each query attends the keys at distances `0..size - 1` from it, so a step of several frames is causal within itself (a conformer's `att_context_size=[left, 0]`). The read takes `distance_bias`, `(rows, q_heads, T, size)`, passed unscaled. The streaming FastConformer (Nemotron VoiceChat's `ENCODER_KV`) is the example.

### Positions {#positions}

Position tracking and RoPE, under `rope` (or `<x>_pos` for an array `<x>_kv`). The declared `Rope` sets the rotation: `theta`, `scale`, the Llama 3.1 factors `low_freq_factor`, `high_freq_factor` and `old_context_len`, `interleave` for GPT-J pairing, `rotary_dim` for a partial rotation, and `table_dtype` for a cos/sin table built once (GLM-5.2 uses float32); the position resource's `cos_sin_table` hands that table to a kernel that rotates inside a larger fusion, and `interleave` says which pairs that kernel must turn. A model with learned position embeddings also declares `Positions()`, because it needs the counter, and never applies RoPE. A cos/sin table on CUDA needs a `rotary_dim` that is a multiple of 32 with NeoX pairing, of 16 with GPT-J pairing.

`Rope(longrope=LongRoPE.from_hf(config))` (Phi-3, Phi-4-mini, Phi-4-multimodal) builds a short and a long table, each with its per-dimension factors and attention scale. A request whose `MAX_POSITION_KWARG` (set by `process_prompt`; the data worker drops a client's value) passes `original_max_position_embeddings` rotates with the long one for its whole life, others with the short one. Set it to the length the model's reference picks its table by: the prompt's for Phi-3 and Phi-4, not prompt plus `max_tokens`. The resource builds the request's config from that kwarg and names the long table in its prefix keys, so the two cannot disagree. Explicit position ids are refused under it. On resident tables a row keeps its table id's offset beside its position's, both fixed between host steps.

### Sampler {#sampler}

A sampler with its own per-request parameter buffers, philox stream, and optional seen-token mask. `penalty` and `min_p` declare capabilities, not intentions: each selects which kernel variant is recorded into the captured graph. Whether the penalty runs on a given step is decided from the `repetition_penalty` values of the resident requests. See `SampleSettings` under [Per-request settings](/adding_models#per-request-settings) for `enable_logprobs`, `enable_processed_logprobs` and `greedy_capture`.

### Recurrent state {#recurrent-state}

A `Value` with tensor fields is fixed-size per-request state that carries between steps (a conv tail, a gated-DeltaNet or Mamba layer's state, a streaming encoder's caches): one slot per request and label, `labels` naming every label a request's steps address or fork into, so that admission reserves a slot for each, and one copy per declared layer. `max_slots` counts the sink unless the pool disables it; a value that leaves no slot for a request is refused at startup. Slot 0 is the sink that padding rows address.

A `GatedDeltaNet` or `Mamba2` update builds a linear attention planned against the Value's pool: gated DeltaNet or Mamba-2. A layer calls gated DeltaNet through `causal_conv` and `gated_delta_net`, and Mamba-2 through `causal_conv` and `mamba2`, so the layer never names a block of the pool. The shared layer is `ParallelGatedDeltaNet` (`mstar/model/components/distributed/`). Gated DeltaNet stores `state` K-last, in fp32 unless the decode kernel takes the declared dtype.

### Sequence shard {#sequence-shard}

Whether a step's tokens split over the node's sequence-parallel ranks, and each listed label's per-rank ranges. Its step is the node's segments, so the model declares no step for it, and the model brackets its layer stack with `scatter` and `gather` on the shard's handle. See [Sequence and context parallelism](#sequence-parallelism).

### LoRA pool {#lora-pool}

Per-request LoRA adapters on the node's LoRA-capable linears: a pool of device slots, a pinned host tier, and the per-step addressing a LoRA kernel reads. It is opt-in: built from the model's `lora_roots()`, and only when the serving YAML has a `resources: lora:` block. One spec spans every node adapters reach, with a pool per node. [Per-request LoRA adapters](/adding_models#per-request-lora-adapters) covers what a model declares; `declared_lora_spec` builds an ordinary `LoraSpec` from it, whose parts follow.

- **Targets.** `LoraTarget` gives the unsharded linear's shape and how the base layer is split under tensor parallelism. For a column-parallel linear, A is replicated and B is split by output rows, per slice (a slice with fewer heads than ranks is replicated, as `QKVParallelLinear` does with K/V). For a row-parallel linear, A is split along the input and B is replicated; the delta is a partial sum, added to the partial base output *before* the all-reduce. LoRA adds no collective to the forward. `layers` restricts a target to some layers of a hybrid stack. A checkpoint tensor that packs several of the target's slices, each split across ranks on its own, is named in `slice_packs` (Qwen3.5's delta-net `in_proj_qkv`: one A for the three, B cut by their widths), and a base linear that pads a slice per rank for alignment says so in `slice_align`. `parallel="none"` is a target whole on every rank, its delta added to an output that is already whole. `experts=E` is one stacked parameter of an MoE layer's routed experts: each (token, top-k) row runs its token's slot's A and B for the expert the router picked, addressed by one combined id `(slot - 1) * E + expert` (the zero adapter's are not stored), on the fused-MoE grouped GEMM (`LoraBackend.apply_experts_`; one align per layer over the combined ids, then a shrink and an accumulating expand per slice). Experts targets are opt-in, since every slot holds a copy of each expert's factors: `module_lora_spec` declares them in `LoraSpec.dropped_targets`, and the YAML's `targets:` serves them by naming them. The align op groups fewer than 1024 ids once padded to its warp of 32, so a spec serves at most `992 // E` slots (7 at 128 experts) and refuses more where the YAML sizes it. Experts split by expert parallelism are refused at deployment validation and at bind (`expert_split`); serve them under TP.
- **Target kinds and rows.** `kind="embedding"` is a token embedding: `in_features` is the vocabulary, the layer passes token ids as `x`, and the shrink is a gather of A's column per token (`mstar::lora_gather_shrink`), PEFT's `lora_embedding_A` / `_B`; an id outside the vocabulary (an image position's `-1`) adds nothing. `per_segment` is one row per segment and `token_fold=k` one row per `k` consecutive tokens of a segment. The pool plans an addressing per grouping its targets use; the call checks the rows it gets.
- **Checkpoint layouts.** Adapters are validated from the same read that pins their digest: modules map to targets, shapes fit them (an adapter for another model size is a 400, not an admit failure), and a conv adapter whose kernel is its stride flattens to the linear over the patch. DoRA (PEFT's `lora_magnitude_vector`, Kohya's `dora_scale`), `modules_to_save`, trainable tokens and bias LoRA are refused by name. A YAML `targets: [...]` keeps a subset of the model's targets (dropping vocabulary-sized ones saves their slots); an adapter touching a dropped target is refused, and its modules stay unbound. Without the list, a deployment with `runtime_updates` off keeps the targets its configured adapters touch (a node left with none gets no pool): the API server reads them once at startup (`resolve_lora_adapters`) and the conductor, handed that config, spawns every worker with the list, so every process builds the same pools; an adapter it cannot read fails the deployment.
- **Requests.** Nothing per model. `LoraSpec.request_config` opens a request that names an adapter in the `lora_adapter` kwarg, which the OpenAI `model` field maps onto (or which the model's `process_prompt` sets; see [Cross-request prefix reuse](/adding_models#cross-request-prefix-reuse)), with a `LoraReqConfig`, which each node's pool takes; a base-model request carries none. The API server refuses, with a 400, an adapter it does not serve (`ServedModels`), and the conductor, with a 409, one a runtime load or unload is in flight for; an adapter is checked when it is registered (rank within `max_rank`, only declared targets, shapes that fit), not per request. A request on an adapter is prefix-cached in its adapter's own namespace ([Prefix cache](#prefix-cache)).
- **Capture and compile.** Nothing per model: a node serving adapters captures the same buckets and compiles the same as one that does not. A capture plans every row on the zero adapter; a replay's plan writes each row's slot into the buffers that capture recorded, so a captured graph serves any mix of adapters without recapture. The kernels are the custom ops `mstar::lora_shrink` and `mstar::lora_expand_` (the latter declares the `y` it writes), and an experts target's grouped GEMMs are one more, `mstar::lora_experts_apply_`, so `torch.compile` takes them as single nodes without a graph break. Under Triton the launch grid depends on the token count and the slot count alone. The pool is a lean resource ([Lean captures](#lean-captures)), so the engine captures every bucket whose step drives it a second time with no LoRA kernel in it: a step none of whose rows names an adapter replays that twin (or runs its deltas as `y` untouched, eagerly), and the LoRA capture when the twin was not captured. The choice reads only which adapter each request named, the same on every rank, and the pool checks it again at plan; `cg_key_info` and `declare_step` still state only the node's own key.
- **dtype.** The slot weights take the nodes' compute dtype (the serving config's `autocast_dtype`, e.g. `float16`). A node that runs outside autocast sets `LoraSpec.dtype` to its weights' dtype.

A request takes its adapter's slot on its first admit and holds it until it is removed. Slot 0 is a zero adapter (rank 0) that base-model rows and capture padding rows address, and the kernels skip it. A miss loads the adapter from the host tier into a free slot, or into the unheld slot released longest ago. A request whose adapter cannot get a slot (every slot held by running requests, or reserved for requests admitted ahead of it) waits at the runner's admission (`LoraAdapterPool.ask` / `reserve`), in arrival order with every other resource that asks, so it holds no KV pages meanwhile and the rows already running keep stepping; the admit's `AllocationFailed` stays only as a backstop. Only the first waiting request is admitted, so a cold adapter is not starved by steady traffic on resident ones: requests behind it wait too, and the held slots drain. On one GPU, where KV admits every request as well, that holds back base-model requests too: a request waiting for a slot, or for its adapter's host copy, stops every newer admission on its node until a slot drains or the read lands. Under tensor parallelism KV does not ask, so base requests go on past it. The slot wait does not arise while the adapters in rotation fit in `max_slots`, and the copy wait is at most one read, which starts at the request's ingest. A slot is reserved for a request only once its adapter's host copy is in (even for an adapter resident in a slot, which a miss admitted ahead may evict), so its admit does not wait on a read there; a request whose adapter failed to read, and is in no slot, is let through at once, and its admit fails it before handing out any slot, so it takes none that a counted request needs. A reservation counts slots and pins none: which slot an admit takes follows from the slot table alone. An adapter with nothing for a pool's targets (a text-only adapter on a vision tower's pool) takes no slot there and runs no delta (its steps can replay the lean capture): the pool knows it from the file's header at startup, or from a runtime load's read, and its rows address the zero adapter. Only the rank that chooses batches admits: on a lockstep instance the leader, whose choice the followers run as sent, so its reservations need no agreement across ranks. The plan writes each step's addressing (for each row grouping its targets read, per token, per segment or per fold, the rows grouped by slot: the only thing the kernels read) into one fixed buffer per capture slot, sized to its bucket, so a captured replay reads stable addresses; a replay's padding rows address the zero adapter and its tail tokens no slot. The pool admits and plans on the GPU thread only (no pre-plan), in step order, and every write it makes to the device (an adapter load, the addressing) goes on the stream the forwards run on, so a load into a slot lands after every step queued before it. `backend` picks the kernels a pool registers behind the custom ops, which every device runs: `"triton"` (slot-grouped shrink and expand, the default on CUDA) or `"torch"`, which registers none and leaves the reference (no data-dependent shapes, the default elsewhere). Registration is process-wide: once anything in the process has registered the Triton kernels, every pool on CUDA runs them.

Under tensor parallelism each rank of the node's lockstep instance keeps its own pool and makes its own slot decisions, with nothing journalled from rank 0, and they come out the same on every rank: admits run in the order rank 0 broadcasts, and the worker lands each teardown between the same two admits on every rank (the `after_tp_seq` stamp on a forwarded remove, honoured on rank 0 by waiting for the admit of the step it is stamped behind). That is why the LRU clock counts admits rather than commits, which may land on either side of a teardown. Which adapters are resident, which slot a miss takes and whether an admit refuses then follow from the same state on every rank. Reading an adapter from disk is the one step that can fail on one rank only, so the ranks agree where each one's copy stands (in, still being read, or failed) before any waits for one, and every rank installs it or refuses the request: one gloo all-reduce per admit with an adapter to install (all of its misses at once), a second when a rank was still reading, none in steady state. Files are read on the pool's own reader thread: every rank starts reading an adapter into the host tier when it ingests a request that names it, the leader reserves a slot for the request only once its copy is in, and an admit never reads a file itself. A follower whose read is still in flight waits for it, unless another rank's read has failed. That wait is short when the follower's read started at the same ingest as the leader's, the usual case, but it can be a whole read: a tier keeps what the ingests and removes on its rank leave it, a follower takes removes from rank 0 and ingests from the conductor, and a remove that races an ingest can leave a follower without a copy rank 0 kept. Neither the wait nor the agreement holds the pool's lock, so the main thread's ingests and removes go on meanwhile.

Adapters loaded and unloaded at runtime (`/v1/load_lora_adapter`) reach each worker as a control message from the conductor, which each rank applies whenever it arrives rather than at a step the instance agrees on. `LoraAdapterPool.load_adapter_async` only reads the adapter into the host tier, on the reader thread (the worker acknowledges the load from its main loop once every pool has it), and `unload_adapter` only stops new requests from naming it; once no live request names it (immediately, or at the last one's teardown) the pool forgets its host copy and its name's slot entry, and leaves the slot's weights and LRU standing as they were. Neither touches what an admit decides from, and the next request that names the adapter is ingested after a reload, which reaches every rank after the unload did. Nothing per model is needed for either.

### Prefix cache {#prefix-cache}

A model opts in through `PrefixKeys` and `checkpoint_path` ([Cross-request prefix reuse](/adding_models#cross-request-prefix-reuse)). The rest is the resources'.

On a node with a recurrent state pool, a hit is cut to the longest snapshot of that state the pool holds under it, since a recurrent layer can't skip tokens. The engine links the pool to the node's paged array, and the deployment gives it `prefix_slots` under the pool's `resources:` key. Each snapshot slot costs as much as a request slot.

- A prefill keeps the state at its last page boundary before its end, since a resend's KV hit always leaves the last page to recompute, and at its KV hit's last page boundary when that is past what it restored. A shared prefix is then served from the third request that shares it. A step longer than the largest captured bucket checkpoints less often, so that its checkpoints fit the captured steps' buffer, and keeps its boundaries on that interval.
- A prompt the step budget cuts into chunks keeps each chunk's last boundary (a chunk with more of its prompt to come keeps its own end), so a resend restores past its first chunk, and a later chunk's snapshot makes the earlier one the first to evict, as a reply's is. Checkpoints fall a page apart from where a chunk starts, so the pool declares a page as its `chunk_alignment` and the scheduler cuts its chunks whole pages long.
- A decode step that ends a page keeps the state there, so a later turn that re-sends the reply restores it. It replaces the request's previous decode snapshot once the KV chain keys its page; a step whose token never reaches the chain, such as the one speculated past the reply's end, leaves the previous one in place.
- A snapshot is keyed by the KV chain's key at its page. A full set of slots evicts the least recently used snapshot that no request holds, a decode snapshot before a prompt's, so the slots hold about one prompt each. A decode snapshot that a later prompt restores is kept like a prompt's from then on.

Snapshots stay off without `prefix_slots`, and also above one rank, without a linked KV cache, when that cache isn't on every node of the pool, or when its `prefix_cache` is off or can't open at the pool's world size; in those cases the pool allocates no snapshot slots. Neither does a pool whose cache the engine keeps shut for another reason, such as a model that names no checkpoint and sets no salt. Every cache on the node of a pool without snapshots stays shut, and the engine logs which pool kept it shut. `opening_prefix_caches` in `mstar/engine/resources/kv/config.py` is that rule over the specs. The engine evaluates it once, before it builds any resource, and opens exactly the caches it returns of those it holds; the conductor's routing and the API server's prompt hashing take, for each rank, the caches the rank holds and its engine opens (`prefix_caches_by_rank`). Each spec answers for itself: `NodeResourceSpec.keeps_prefix_cache` says whether the resource keeps a prefix cache of its own, and `restores_prefix` marks one whose state a hit must restore (the pool, and the resource over it), so another resource takes part through its spec alone.

A request on a LoRA adapter fills different KV for the same tokens, so its keys chain from a root that names the adapter's weights: a SHA-256 over every module's A, B (with dtype and shape) and alpha, read once when the adapter is registered (`adapter_prefix_root` in `mstar/engine/resources/lora/identity.py`). The API server takes the root when it selects a request's adapter (`ServedModels.select`) and the preprocess worker keys the prompt from it. The root travels with the request as `KVReqConfig.prefix_root` so that a page generation fills is keyed under it too. The same tokens under two adapters, or under an adapter and the base model, never share pages; two names for identical weights do; and a name registered again with other weights misses everything the old weights filled; a request selected under the old weights carries their digest (`LoraReqConfig.digest`), and a pool serving the new ones refuses it at ingest. A base-model request chains from the empty root. Only a registered adapter can be selected, so every request on one has its root; one that arrives without is not cached. Nothing on the model side is needed for this.

A resource whose KV differs per request for the same tokens (a LongRoPE table picked by prompt length) says so in `NodeResourceSpec.prefix_variant(model_kwargs)`: opaque bytes, from the same kwargs its `request_config` reads, or None. The data worker folds every declared spec's variant into the root after any adapter's, in declaration order and under the spec's key (`variant_root` in `mstar/engine/resources/kv/keys.py`), keys the prompt and sends that root on, so generated pages are keyed under it too. Requests share pages only under the same variants, and a request whose resources name none keys under the root it had.

### Admission hooks {#admission-hooks}

A resource whose capacity can run out before a request starts, and that the request then holds until it is removed (KV pages, recurrent-state slots, sampler rows), answers for that capacity through the admission hooks on `Resource`. The runner's `Admission` decides who gets it and when: one arrival order across resources, and a request takes everything it asks for or nothing. Capacity a single step takes and gives back goes through `admit` and `rollback_admit` instead.

- `ask(rid, node_name, graph_walk)` returns `ASKS` while the request needs this resource's capacity to start on the node, None when it needs none, or a failing outcome when it can never fit.
- `reserve(rid, node_name, graph_walk, published)` takes what the request asked for and returns None, or returns a mark of what it didn't fit against.
- `unreserve(rid)` gives back what `reserve` took, when another resource the request asks didn't fit.
- `grew_since(mark)` says whether a request that didn't fit against `mark` may fit now. The runner tries a blocked queue again only once it is True, so a pass that changed nothing costs one call.

A request is admitted once it is first in every queue it waits in. A resource may also let a later request pass a first request that can't start, by overriding `reserve_past(rid, node_name, graph_walk, published)`. It takes the passer's capacity while leaving the first request what it needs, so passing can't starve that request, or returns a mark, and the runner tries a passing request again only once `grew_since` that mark. The runner calls it only while the first request can't start: a resource that lets requests pass refused it and hasn't grown since, or the oldest request holds back that resource's queue while it waits to return, and the passing request passes, or takes nothing, at that resource too. A resource that doesn't override it keeps strict order, and a request waiting in its queue can't pass anywhere. A resource that overrides it asks nothing more of a waiting request whose capacity it set aside on its own, as the KV cache does when it moves other requests for it, and the request may then start wherever it stands in that resource's queue.

### Routing across data-parallel replicas {#routing}

When a node group has several replicas, the conductor sends each new request to the replica where it is cheapest ([Serving](/serving)). A resource whose state makes a request cheaper on one replica than another takes part through its spec, so models declare nothing for it.

`NodeResourceSpec.routing_mirror(ctx)` returns a `RoutingMirror` or `None`, the default. The router asks once per set of node groups with replicas that holds one of the spec's nodes, and `ctx` (a `RoutingContext`) gives the replica count, the walks of the worker graphs there that hold the spec's nodes, the resource's keyed labels with the walks that key each (empty for a resource that is not a KV cache), and whether every replica's engine opens its prefix cache, which the router derives with `prefix_caches_by_rank`. A mirror is conductor-side bookkeeping that follows the resource's own rules as far as the conductor's inputs allow. The module that defines one must stay free of kernels, since the conductor builds it. Each of its methods is given the request's `ResourceReqConfig` for the resource, which the conductor builds and validates before the pick:

- `facts(config)` reports the request's `RoutingFacts` on each replica: named counts, such as `work` (prompt positions) and `kv_hit` (of those, the ones predicted cached). The router adds every mirror's row on a replica field by field, then prices the sum once with `routing_cost` in `mstar/conductor/routing.py`, one term per `routing_weights` key, each 0 when its facts are absent.
- `add_request(config, replica)` records the placement once the request is dispatched, and returns a handle.
- `remove_request(handle, ran)` releases it when the request leaves. `ran` says whether a pass came back for one of the request's partitions with a walk on the resource's node groups.

A new resource adds its fields to `RoutingFacts`, its mirror, and its term to `routing_cost` and `RoutingWeights`. `ReplicaRouter` changes only if its fields are not counts that add, or if its mirror reads a model declaration other than the KV ones, which then becomes a `RoutingContext` field that `ReplicaRouter` fills. `KVSpec` with a `PagedKVConfig` is the one implementation. Its mirror runs the worker's own `PrefixIndex` and `PageArena` per replica, with no storage, takes each request's lease, pages and index entries at dispatch, an item's end inside a page among them, and exists only where a walk keying the cache runs and `opening_prefix_caches` says the workers open it.

### Lean captures {#lean-captures}

A resource whose kernels can be left out of a step whose rows all allow it sets `Resource.lean_capture`, answers `lean_for(request_ids)` from state every rank of a lockstep instance sets alike (its ingests), and says which kinds of capture get its twin (`lean_captures`). Beside each bucket whose step drives such resources, the engine captures a twin for each set of them, keyed by that set (`BucketKey.lean`). A step replays the twin of every resource its rows let run lean, else one with fewer of them (largest set first, ties in declaration order), else the plain bucket; the engine names the set in `StepContext.lean`, eager steps included, and each resource checks its rows again at plan. A resource whose callers read its plan inside the forward also overrides `Resource.outside_step`, which the engine enters around compile warm-ups outside any step (the LoRA pool's runs them lean). Twins are sized, planned and captured after every plain bucket, and a twin left out (under the capture budget, say) is logged at INFO and is not a dropped bucket: its steps replay the plain bucket. Lean resources: the LoRA pool, for steps none of whose rows names an adapter, in every kind of capture; and a sampler (see `SamplingReqConfig`), for steps whose rows all sample greedily, in batched captures. A model declares nothing for these.

## Sequence and context parallelism {#sequence-parallelism}

A node's `sp_size` ranks share each of its steps, along two axes:

1.  **Per step, the tokens are split or copied.** A sequence shard on the node decides, every step: split, each rank runs the token-local layers (norms, MLPs, projections) on its share of each listed label (contiguous, or on a ring node striped by KV position); or copied, every rank runs them all. Without one, every step is copied.
2.  **Per paged KV pool, stored K/V is split by head or by position.** By head (the default) over the node's `tp * sp` ranks; by position with `context_parallel: true` (below), heads over TP.

Each attention resource derives what it does from the two and the shard's `exchange` (below); the model writes no exchange (a ragged attention's Ulysses follows from the labels it plans):

| Tokens / storage | By head | By position (`context_parallel`) | Cacheless (ragged) |
|----|----|----|----|
| Copied | head slice: this rank's heads of q, k and v, write and attend, gather the heads | each rank attends its slots, partials merged (below) | heads over TP; over a label the shard lists on a splitting node, a head slice |
| Split | Ulysses: one all-to-all from split tokens to split heads, write and attend, one back | by the shard's `exchange` (below): `all_gather`, one gather of every rank's q, k and v, attend as a copied step, keep this rank's rows; or `ring`. With `auto`, the node's steps run copied | Ulysses over a label the resource plans; any other split label refused at its first split step |
| Cross, split queries | n/a | n/a | each rank's queries over every key |
| Cross, split keys | n/a | n/a | each rank's partial over its keys, merged by log-sum-exp (`gather_merge`) |
| Cross, both split | n/a | n/a | refused at load |

Splitting is declared in four places:

- `SeqShard(name, nodes=, labels=, walks=)` names the labels whose tokens split, on its reads' axis: axis 0 cuts packed tokens or a segmented row into contiguous ranges, and axis 1 cuts each row of a `[B, S, ...]` layout alike (reads with `packed=False`, every row of the label one length). `walks` limits splitting to those walks; the others plan copied. A step splits only when it isn't one token a row, its listed tokens reach `max(sp_size, min_tokens)`, and every listed label has at least `sp_size` tokens (a row, on axis 1). `min_tokens` (default 0) is a `resources:` override, a deployment's trade between the exchanges' cost and the split layers' saving, as is `exchange` (below), how a split step reaches the node's paged attentions. A captured step decides from its bucket's size, not its prompt's, so capture and replay split alike; where a resource's split steps run eagerly only (`NodeResourceSpec.splits_eagerly`), the shard sets its own floor at load, one past each walk's largest captured bucket, so a captured bucket runs copied and only a bigger, eager step splits (`min_tokens` only raises it). The shard covers every node of the attention resources that depend on it: a resource spanning nodes the shard doesn't cover is refused, as is a KV pool whose attentions depend on two shards. MiniMax-H3's video decoder writes a shard by hand with `exchanges=False`, which declares that no op on the node mixes the label's units, so nothing exchanges them: the node needs no attention, and a rank may get none of them (fewer units than ranks still splits). It reads `shard.split_range(label)` for its range and gathers the decoded clips with `shard.gather` (`mstar/model/minimax_h3/submodules.py`); such a shard is refused beside an attention that takes split steps.
- The model declares **no step** for the shard: its step is the node's segments and combined labels (as `Resource.steps_from_segments` says), added at any SP size (at one rank its plan is a constant), so a combined plan label gets a range too. A step that declares no segments has no shard plan, and the attention resources refuse it, so it fails on one GPU. The diffusion scaffold's step holds each label's segments once, however many arrays attend them (LTX-2.5's video tokens are the keys of two).
- The forward **brackets** its layer stack with `scatter(shard, *xs)` and `gather(shard, x)` on the shard's handle: `scatter` before it (this rank's share of each tensor, `dim` the shard's axis by default; `None` passes through), `gather` after it. `split_range(shard)` is this rank's range of the label (`start`, `count`, every rank's `counts`) where the step splits it, else `None`, for what must follow the cut (Wan2.2's timestep runs, MiniMax-H3's rope rows). Both are the identity on a copied step, at one SP rank, and outside a step (a warmup compile); at one rank they trace straight through a compiled frame, and on SP ranks each breaks the graph once. Everything between them runs on this rank's tokens. LTX-2.5 brackets the DiT in its denoise step (`mstar/model/ltx2_5/submodules.py`), Wan2.2 and MiniMax-H3 inside their DiT's forward; Cosmos3 brackets the generation layer stack after its whole-sequence prologue (`mstar/model/cosmos3/components/transformer.py`); Qwen3.5 brackets its LLM's stack, gated delta rule layers included (`Qwen3_5ForCausalLM.forward`).
- The attention is reached through the array's handle. A state op that fuses the K/V write into its norm/RoPE kernel (Qwen3-Omni's `qk_norm_rope_table_attend`) runs its reference, through `add` and the exchange, wherever the step's read exchanges (`AttentionManager.step_exchanges(label)`): a label the step splits, and every step over KV stored by head, copied steps too (each rank's head slice). A cacheless self-attention over a label the shard lists runs Ulysses, and the array declares nothing for it. Both are no-ops on a node with no shard, or one whose shard never splits (`SeqShardSpec.splits`), so one declaration serves every deployment shape. A read bound to SDPA (`backend: sdpa`) runs outside the resources and is refused over keys the shard splits.

**Recurrent and sliding-window layers.** They take split steps through their own resources too, and the model writes nothing more than the bracket. Each resource's state is stored one of three ways over the SP ranks (`NodeResourceSpec.storage`): by head, by position (`context_parallel`), or copied (heads over TP alone, every SP rank holding all of it). A copied resource takes its own exchange wherever the node's shard splits, whatever the shard's `exchange`:

- A **recurrent pool** (GDN, Mamba-2) is copied, so decode reads it with no collective, and a split step leaves the same bytes in every replica. On a split step the conv runs on each rank's tokens from the earlier ranks' last inputs (`conv_halo`, one all-gather a layer), and every row's final window is written on every rank. A combined walk's leading decode rows run copied. The prompt rows take the exchange the linear resource picks from the model's head counts: `ulysses` where each TP rank's heads split `sp_size` ways (one all-to-all to a block of heads, the chunked kernel over that block of the state, the block's final states gathered, one all-to-all back), `state_passing` where they don't (each rank runs its pieces, hands its state on in one fixed-size gather, and runs a row continuing into it from the state it gets). Mamba-2's scan is a loop over tokens, so `ulysses` saves memory there, not time. `state_passing` and Mamba-2's split are tested on CPU only and no in-tree model adopts them yet. Both exchanges run eagerly, so a node with a recurrent layer never splits a captured step: the shard's floor sits above its largest captured bucket, so a bigger step runs eagerly and splits, and every other step keeps its graph. Prefix snapshots stay off above one rank.
- A **sliding-window** attention over a pool stored by position keeps its window layers whole on every SP rank (`PagedKVConfig.placed_groups`) while the full layers' slots stripe: its copied steps (decode included) attend as on one rank, with no collective, and its split steps gather the step's keys (`kv_gather`), eagerly. Its pages hold `1/sp_size` the tokens they would unplaced, so each window page must split `sp_size` ways. Its split, copied and decode steps are tested on CPU only, over FlashInfer's reference.

Every resource of a splitting node must support split steps (`Resource.supports_split_steps`: the KV pool, paged FlashInfer and dense attention, ragged self and cross attention, positions, the sampler, the recurrent pool and its GDN and Mamba-2 resources); MLA, DSA, KDA, flex and XPU attention don't, so a splitting node can't own them. The conductor refuses, before a worker starts (and the engine again at load): a node on SP ranks that neither splits its steps (a shard whose `exchange` isn't `none`, with a resource that takes split steps or `exchanges=False`) nor places its pools by position; a shard on axis 1 over a pool stored by position; a head-stored pool whose query and KV heads per TP rank don't divide by `sp_size`; a ragged Ulysses attention whose heads don't divide by `tp * sp`, or beside a ring; an SDPA read over keys the shard splits; a ragged cross-attention under a shard on axis 0 or with `exchanges=False` (either can leave a rank none of a row); a linear layer (not Mamba-2) whose heads per TP rank don't divide by `sp_size` (so it takes `state_passing`) and whose key and value head dims differ, at `sp_size` 3 or more; a linear layer under a shard on axis 1 or a ring's; a `kv_gather` attention under a ring's (it plans contiguous pieces); a window page that doesn't split `sp_size` ways; and expert parallelism. The engine alone refuses a resource without `supports_split_steps` at load, and, at warmup (after the weights load and the compiles), piecewise captures, a capture replayed under listed and unlisted walks, and a packed capture of a listed walk unless the shard lists one label on axis 0 (its padding joins that label). Each attention resource of a splitting node logs at load how it takes split steps.

### Choosing the exchange {#choosing-the-exchange}

`exchange` in the shard's `resources:` block picks how its split steps' tokens reach its paged attentions, from where their KV is stored. `auto` (the default) runs Ulysses over KV stored by head, and over KV stored by position runs the node's steps copied, so a node whose pools store KV by position splits its steps only where the deployment opts in with `all_gather` or `ring`. A value the node's storage can't take fails at load, at any SP size. It only picks the split exchange: copied steps keep the storage's own path. A ragged attention runs Ulysses over a label it plans that the shard lists (above), and a copied resource takes its own exchange (the list above), on a shard that splits. Each row assumes the node declares a shard and runs on `sp_size` above 1:

| `exchange` | KV stored | Split steps | Copied steps | Pick it when |
|----|----|----|----|----|
| `auto` / `ulysses` | by head | Ulysses all-to-all | head slice | q and KV heads per TP rank divide by `sp_size` (Cosmos3; LTX-2.5, Wan2.2 and MiniMax-H3's DiT, which have no paged pool, by their ragged attentions over the labels their shards list) |
| `auto` / `none` | by position (`context_parallel`) | never: the node runs copied, as one without a shard | partials merged | KV capacity alone (DCP), no token split |
| `all_gather` | by position | gather q, k and v, attend as copied, keep own rows | partials merged | long prompts where one KV head per TP rank can't split by head (Qwen3-Omni's Thinker on TP4 x SP2) |
| `ring` | by position | striped pass-Q ring, eager only | partials merged | attention is the step's peak memory (below); not beside a recurrent layer or a `kv_gather` attention |
| `none` | by head | refused at load: the SP ranks would only share heads | n/a | never; use TP |

And for the copied resources, under any `exchange` that splits:

| Resource | Split steps | Copied steps | Pick it when |
|----|----|----|----|
| sliding-window attention over KV stored by position | `kv_gather`, eager only (CPU-tested only) | as on one rank, no collective | always; its window pages must split `sp_size` ways |
| recurrent layer, `ulysses` | conv halo; all-to-all to heads; eager only | as on one rank | chosen where the heads (and Mamba-2's B/C groups) per TP rank divide by `sp_size` (Qwen3.5) |
| recurrent layer, `state_passing` | conv halo; one state hand-off; eager only | as on one rank | chosen where the heads per TP rank don't divide; a hand-off's bytes don't grow with the prompt (at `P = 2` it waits on the previous rank, so it isn't faster). CPU-tested only |

`ulysses` over KV stored by position, and `all_gather` or `ring` over KV stored by head, are refused. A shard that never splits (`none`, or `auto` over KV stored by position) makes the node plan every step copied, from the config alone, so it takes what a node without a shard takes (expert parallelism, say).

### Ring {#ring}

`exchange: ring` stripes each split step's tokens over the SP ranks by KV position: a row whose pool already stores `c` tokens gives rank `r` its tokens at positions `x` with `x % P == r`, exactly the ones whose K/V it stores, so it writes its own K/V and nothing moves. Each layer then runs `P` rounds: rank `r` sends its queries to rank `r + i`, attends rank `r - i`'s over its own slots (stored context and the step's tokens together, one call, causal or not as the step declares), sends the partial back, and merges what it gets in fp32. Its hops are synchronous, and only the `flashinfer` backend plans it. Another is refused when the engine builds the attention, at any SP size like the storage checks, but after the validation that runs before a worker starts. Ring is eager only, so a ring node doesn't capture the buckets a step could split in: those steps split eagerly, and the rest keep their graphs. A step that combines listed labels into one plan (Cosmos3's batched CFG) is refused when it plans on a ring node, not at load: the stripe reads each listed label's rows from the pool's plan, which holds the combined label's instead.

A step's peak memory is its resident tensors plus the larger of its attention and its MLP (or MoE) phase. All-gather's attention phase holds the whole step's q, k and v and `P` partials per query; ring's holds this rank's tokens alone, and two fp32 copies of their result while a round merges. So ring lowers the peak only once attention outgrows the MLP phase. An estimate from allocation sites, not a measurement, puts that at about `P = 4` for the Qwen3-Omni Thinker's geometry (at `P = 2` its MoE phase is larger), and sooner for dense models, whose MLP phase lacks the top-k expansion. Ring merges `P` bf16 partials per query, so its greedy output can differ from the copied path's; all-gather attends as a copied step does. Chunked prefill stays off on SP ranks either way, so a long prompt prefills in one step.

### Context parallelism {#context-parallelism}

`context_parallel: true` on a paged KV pool stripes each page's slots over the ranks that would otherwise store the same KV heads: slot `s` lives on partner `s % P`, page ids stay the same on every rank, and each rank holds `page_size / P` slots a page. Attention runs on each rank's slots and merges the partials across the partners exactly (`mstar/engine/resources/context_parallel.py`). The model declares nothing.

- **TP mode (no SP ranks).** The partners are the TP ranks sharing a KV head, `P = tp / num_kv_heads`, so TP must be a larger multiple of the KV heads. They are the contiguous blocks `kv_head_replicas` (`mstar/distributed/utils.py`) gives, as `QKVParallelLinear` loads them; a model that shards K and V itself must match. Each placed layer exchanges queries and partials over the TP group, except for a plan label of an eager step that isn't one token a row and has no stored context on any row, which attends its own tokens alone.
- **SP mode.** The partners are the node's SP ranks, `P = sp_size`. Heads shard over TP alone. Without a shard every layer but attention runs copied across SP; prefer TP mode where it applies. With one whose `exchange` is `all_gather` or `ring`, long steps split their tokens too (above). Every paged pool of the node must set the key. Each placed layer all-gathers the partials of a step copied or split by `all_gather`. Under the same exception such a step attends no slots and gathers its own tokens' shares alone; a ring step never does. Chunked prefill stays off on SP ranks (`_unchunkable_nodes`), so SP mode prefills a prompt in one step. TP mode chunks prompts as without placement.

A page's tokens (`page_size`, 128 when it is unset) must be divisible by `P`; the conductor checks these rules against `node_groups` before it starts a worker. `max_num_pages` counts logical pages, so raise it by `P` to use the memory placement frees (the pool logs its bytes per rank). Every resource over the pool must support it, or loading fails naming the one that doesn't. FlashInfer attention (`flashinfer`) with `flashinfer_backend` `auto`, `fa2` or `fa3`, RoPE positions and the recurrent state pool (the same state on every SP partner) do; dense, flex, XPU, block-causal and MLA attention, cross-attention and DSA don't, and a ring or bounded KV pool can't set the key. `auto` runs as `fa2` from SM100. An SP-placed pool that prefills on `fa2` warns at startup: an explicit `fa2` on any architecture, and `auto` where FlashInfer has no `fa3` (below SM90 and from SM100); `auto` on SM90 prefills on `fa3`. A sliding window kept in its own group of layers stays whole on every partner, in pages of `1/P` its unplaced tokens (which must be whole), while the full layers stripe; a window at least `max_seq_len` reads the placed layers and is refused there. The `fa2` warning holds for the window's attention too. A decode/prefill `splits` and `decode_fmha` are ignored over a placed pool, and a node over one plans on the host rather than resident (`resident_planning`). A node that captures a step combining labels into one plan (as classifier-free guidance does) at a batch size above 1 is refused at load: a replay's padding rows would sit between its real ones.

A step of one token a row attends the pages after its KV write (in TP mode on tensor cores whatever `decode_tensor_cores` says). Any other step attends its stored context on the pages and its own tokens from the `k` and `v` the layer adds. A fused K/V write that leaves `k` unrotated rotates it when the step attends it; a state op's fused kernel doesn't run on such a step, so its reference's `add` hands the handle `k` and `v`. In SP mode, rank `r` attends only the step's own tokens in *zigzag* chunks `r` and `2P - 1 - r` of each row's `2P` (`zigzag_rows`), which shares the causal work about evenly on rows of `2P` tokens or more; it merges them into its context partial before the gather.
