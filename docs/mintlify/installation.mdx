## Requirements {#requirements}

- Linux with an NVIDIA GPU. A CUDA 13 build of torch needs an r580 or newer driver. BAGEL also runs on Intel GPUs from the [XPU image](#docker). [Supported hardware](/hardware) lists what is tested.
- Python 3.12 or newer, and [uv](https://docs.astral.sh/uv/).
- For the Rust build, [rustup](https://rustup.rs) and a C/C++ compiler ([Rust](#rust) has the install command).
- At run time, `nvcc` from a CUDA toolkit: FlashInfer and the MoE align kernel compile kernels on first use. The builds that go through `torch.utils.cpp_extension` (the MoE align kernel, flash-attn from source) also need its major version to match torch's CUDA ([Match the CUDA toolkit](#cuda-toolkit)).
- PyTorch `>=2.10,<2.13`, which the install pulls in. CI and the CUDA Docker image use 2.10.0.
- The GPUs the model's default config uses; [Supported models](/models#matrix) gives the count per key.

## Install from source {#install-from-source}

```bash
git clone https://github.com/mstar-project/mstar.git
cd mstar
uv venv --python 3.12 --seed
source .venv/bin/activate
uv pip install --torch-backend=auto -e ".[bagel]"

# Rust graph runtime and HTTP frontend (needs rustup)
uv pip install maturin
maturin develop --release -m rust/Cargo.toml
cargo build --release --manifest-path rust/server/Cargo.toml

mstar serve bagel
```

- `--torch-backend=auto` makes uv read the NVIDIA driver's CUDA version, not the toolkit's, and install the torch built for it. Pass it on every install, or `export UV_TORCH_BACKEND=auto`. If your uv rejects the flag, update uv. If the driver is newer than your `nvcc`, see [Match the CUDA toolkit](#cuda-toolkit).
- `".[bagel]"` installs the core runtime, the `mstar` and `mstar-serve` commands and BAGEL's dependencies. For another model, use its extra from the Extra column of [Supported models](/models#matrix).
- `maturin develop` builds the `mstar_rust` extension (graph runtime, control mesh, SHM tensor arena) into the virtualenv. `cargo build` builds the `mstar-server` HTTP frontend into `rust/server/target/release/`. The server needs both.
- `mstar serve bagel` downloads about 30 GB of weights into `$HF_HOME` (default `~/.cache/huggingface`), then compiles the model before it listens. Measured on 1x H200, 2026-11-27, with the weights downloaded and in the page cache: the first start took 8.6 minutes, nearly all of it compilation and FlashInfer kernel builds, and a restart took about 70 to 80 seconds. Read cold from a network filesystem, the weights took about 142 seconds to load and the first start 11.1 minutes (664 s). [Cold start](/cold-start) explains the wait and how to keep the caches.

## Rust extension and mstar-server {#rust}

Without Rust, install rustup and load it into the current shell:

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y
. "$HOME/.cargo/env"
```

The first `maturin` or `cargo` call in the checkout also downloads the compiler pinned in `rust-toolchain.toml`. On a 192-core H200 host (2026-11-27), `maturin develop` took 33 seconds and `cargo build` 71 seconds; a smaller machine takes longer.

Rebuild both whenever `rust/` changes. In a checkout, the conductor and each worker compare `mstar_rust.BUILD_SOURCE_HASH` with a hash of the files in `rust/` and refuse an extension built from other sources. The errors print these rebuild commands, with absolute paths:

```bash
touch rust/build.rs && maturin develop --release -m rust/Cargo.toml
touch rust/build.rs rust/server/build.rs && cargo build --release --manifest-path rust/server/Cargo.toml
```

`mstar serve` looks for `mstar-server` in this order: `--rust-frontend-bin`, `MSTAR_SERVER_BIN`, the environment's scripts directory, `$PATH`, `rust/server/target/release/mstar-server`. In a checkout it skips a binary built from other `rust/` or `rust/server/` sources and, if none is left, stops at startup with the second command above. A stale binary named by the flag or the variable runs with a warning. `mstar-server --source-hash` prints the source hashes a binary was built from. An installed package has no `rust/` beside it, so neither check runs there.

With `CARGO_TARGET_DIR` set, `cargo build` puts the binary in `$CARGO_TARGET_DIR/release/`, which `mstar serve` does not search. [Verify](#verify) and `mstar serve` then find no binary, or skip an older one in `rust/server/target/release/`, and the rebuild command they print builds into `$CARGO_TARGET_DIR` again. Point the variable at the new binary:

```bash
export MSTAR_SERVER_BIN="$CARGO_TARGET_DIR/release/mstar-server"
```

## Install from PyPI {#install-from-pypi}

```bash
uv venv --python 3.12 --seed
source .venv/bin/activate
uv pip install --torch-backend=auto "mstar-ai[bagel]"
```

The distribution is `mstar-ai`; the import package is `mstar`. PyPI has 0.2.1, whose wheels have neither `mstar_rust` nor `mstar-server`, and its `mstar serve` knows 14 of the 61 model keys. Install from source until a newer release is out. The alias names `mstar-project` and `mstar-serve` forward only some extras, so install `mstar-ai`.

An installed package ships the default configs in `mstar/default_configs/`.

## Extras {#extras}

The Extra column of [Supported models](/models#matrix) names the extra each model key needs. Combine extras with commas: `-e ".[bagel,audio]"`, or `"mstar-ai[qwen3_omni,audio]"`. Extras that are not tied to a model:

| Extra | For |
|---|---|
| `audio` | Non-WAV audio output (mp3, flac) from the SDK and the OpenAI routes. WAV and PCM work without it. |
| `metrics` | `--enable-metrics` and `GET /metrics` ([Metrics](/metrics)). |
| `vad` | `server_vad` and `semantic_vad` turn detection on `/v1/realtime`. |
| `audioseal` | The opt-in AudioSeal watermark on generated speech. |
| `eval` | `python -m benchmark.eval`, which runs from a checkout. |
| `dynamo` | `python -m mstar.integrations.dynamo`. |
| `dev` | Linting and the test suite. |
| `all` | Most model extras in one environment. |

`all` includes `audio`, `vad`, `audioseal`, `ruff` and `pytest`, and requires `transformers>=5.18`. It leaves out `metrics`, `eval`, `dynamo`, `bagel_xpu`, the torch pins of `asr`, and packages only Chatterbox and Chatterbox Multilingual use; add the model's own extra for those, for example `-e ".[all,chatterbox]"`. Command A+ also needs `huggingface-hub>=1.5` from `command_a_plus`.

The `asr` extra pins torch 2.10, torchaudio 2.10 and torchcodec 0.10, so it moves the environment's torch to 2.10.

## Manual installs {#manual-installs}

No extra installs these: PyPI refuses git and URL dependencies in package metadata, flash-attn has no PyPI wheels, and `qwen-tts` pins versions other models conflict with.

| Package | Needed by | Command | Details |
|---|---|---|---|
| `omnivoice` | `omnivoice` | `uv pip install "git+https://github.com/k2-fsa/OmniVoice.git"` | [OmniVoice](/models/omnivoice#serve) |
| `qwen-tts` | `qwen3_tts`, `qwen3_tts_1p7b`, `qwen3_tts_voicedesign`, `qwen3_tts_base` | `uv pip install --no-deps "qwen-tts==0.1.1"` | [Qwen3-TTS](/models/qwen3-tts#serve) |
| `flash-attn` | `lingbot_world_1_3b` with `reference_numerics: true`. Optional for BAGEL, whose ViT otherwise falls back to SDPA. | Below | [World models](/models/world-models#serve) |
| `flash-attn-4` | `waypoint`'s default `FLASH` attention backend, with torch 2.11 or newer; without it the server falls back to `TRITON`. Install it after `flash-attn`. | From the flash-attention repo at a pinned commit | [World models](/models/world-models#serve) |
| `taehv` | `waypoint` | `uv pip install --no-deps "taehv @ https://github.com/madebyollin/taehv/archive/7dc60ec6601af2e668e31bc70acc4cb3665e4c22.zip"` (uv 0.4.0 or newer) | [World models](/models/world-models#serve) |

A flash-attn wheel must match your torch. The prebuilt wheels stop at torch 2.10, and for 2.10 only CUDA 13 builds exist; the URL below is the Python 3.12 one. For any other torch, build from source with `FLASH_ATTN_CUDA_ARCHS` set to your GPU's compute capability (`90` for H100, `80` for A100); the default list includes Blackwell targets that fail under nvcc 13.

```bash
python -c "import torch; print(torch.__version__, torch.version.cuda)"

# torch 2.10 with CUDA 13
uv pip install "https://github.com/Dao-AILab/flash-attention/releases/download/v2.8.3/flash_attn-2.8.3+cu13torch2.10cxx11abiTRUE-cp312-cp312-linux_x86_64.whl"

# any other torch
uv pip install psutil
FLASH_ATTN_CUDA_ARCHS="90" uv pip install flash-attn==2.8.3.post1 --no-build-isolation
```

## Match the CUDA toolkit {#cuda-toolkit}

Code that compiles on your machine (flash-attn from source, FlashInfer's JIT kernels, the MoE align kernel) uses the system CUDA toolkit. Set `CUDA_HOME` to that toolkit if it is not the default. Its major version should match torch's CUDA. Compare the two:

```bash
python -c "import torch; print(torch.version.cuda)"
nvcc --version
```

A CUDA 13 driver with a CUDA 12 toolkit is common on cloud and NGC images. There `--torch-backend=auto` installs a CUDA 13 torch: on 1x H200 (2026-11-27, driver CUDA 13.0, nvcc 12.9) it picked `cu132`. BAGEL served with it, and FlashInfer's JIT built with nvcc 12.9. Builds that go through `torch.utils.cpp_extension` (the MoE align kernel of the MoE models, flash-attn from source) check that the two major versions match and stop. In a new venv, install the torch for your toolkit instead (`cu129` for nvcc 12.9, `cu128` for 12.8; the configs in [Verified on H200](/models#verified-on-h200) ran on torch 2.12.1+cu129):

```bash
uv pip install --torch-backend=cu129 -e ".[bagel]"
```

Without `--torch-backend`, install torch from the PyTorch index for your CUDA version first (`cu128`, or `cu130` for CUDA 13), then M\*:

```bash
uv pip install torch==2.10.0 torchvision==0.25.0 torchaudio==2.10.0 \
    --index-url https://download.pytorch.org/whl/cu128
uv pip install -e ".[bagel]" "torchcodec==0.10.*"
```

torchcodec does not declare its torch version, so pin the release built for your torch (0.10 for 2.10).

## Docker {#docker}

Build both images from the root of a checkout.

The CUDA image is the `serve` stage of `mstar/integrations/dynamo/docker/Dockerfile`: torch 2.10.0 for CUDA 13, `.[all]`, `qwen-tts`, flash-attn, the `mstar_rust` extension and Mooncake's CUDA 13 build. Its header lists the build arguments for a CUDA 12 host. The image does not build `mstar-server`, so serve from it with `--python-frontend`, the deprecated FastAPI frontend:

```bash
docker build -f mstar/integrations/dynamo/docker/Dockerfile --target serve -t mstar-serve .
docker run --rm -it --gpus all --ipc=host -p 8000:8000 \
  -v "$HOME/.cache/huggingface:/root/.cache/huggingface" \
  -v mstar-cache:/root/.cache/mstar \
  mstar-serve mstar serve bagel --python-frontend
```

The named `mstar-cache` volume keeps compiled kernels across containers without leaving root-owned files in `$HOME/.cache/mstar`.

The Intel XPU image, `docker/Dockerfile.xpu`, clones M\* from GitHub (`main` unless you pass `--build-arg MSTAR_REF=<branch or tag>`), installs the `bagel_xpu` extra and builds both Rust pieces. It starts a shell. The host needs an Intel GPU driver and `/dev/dri`:

```bash
docker build -t mstar:xpu - < docker/Dockerfile.xpu
docker run --rm -it --device=/dev/dri --ipc=host \
  -v /dev/dri/by-path:/dev/dri/by-path:ro \
  -p 8000:8000 \
  -v "$HOME/.cache/huggingface:/root/.cache/huggingface" \
  -v mstar-cache:/root/.cache/mstar \
  mstar:xpu
```

Inside the container, serve BAGEL on three Intel GPUs (encoders and decoder on one, the LLM at TP2 on two):

```bash
cd /mstar-workspace/mstar
mstar serve bagel --config configs/bagel_xpu_tp2.yaml
```

## Verify {#verify}

```bash
python -c "import mstar_rust; print('mstar_rust OK')"
python -c "from mstar.api_server.rust_frontend import find_server_binary; print(find_server_binary())"
python -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.device_count())"
```

The first fails on a PyPI 0.2.1 install, so it tells that install from a checkout, which reports the same version number. The second prints the `mstar-server` that `mstar serve` will run, or the error it would stop with. The third should show a CUDA build of torch and enough GPUs for your config (on XPU, use `torch.xpu.device_count()`). Then serve a model and check [`/health`](/quickstart#check-health).

## Troubleshooting {#troubleshooting}

Errors that stop `mstar serve` at startup are in [Cold start](/cold-start#startup-errors).

### `CUDNN_STATUS_SUBLIBRARY_VERSION_MISMATCH` {#cudnn-status-sublibrary-version-mismatch}

```text
RuntimeError: ... cudnn_status: CUDNN_STATUS_SUBLIBRARY_VERSION_MISMATCH
```

A CUDA 12 torch pins `nvidia-cudnn-cu12==9.20.0.48`, which lacks the `libcudnn_engines_tensor_ir` engine, so on a host with a system cuDNN 9.21 or newer (in `/usr/lib64`, say) cuDNN loads that engine from the system copy. Complete the environment's own cuDNN:

```bash
uv pip install --no-deps -U "nvidia-cudnn-cu12>=9.21"
```

pip may warn that torch pins `9.20.0.48`; cuDNN is ABI-compatible within v9.

### `libcudart.so.12: cannot open shared object file` {#mooncake-cuda13}

With `--tensor-comm-protocol TCP` or `RDMA`, startup fails with:

```text
RuntimeError: Mooncake TransferEngine is required for RDMA/TCP protocol. Failed to load
mooncake: ImportError: libcudart.so.12: cannot open shared object file: ...
```

The extras install Mooncake's CUDA 12 wheel, which cannot load next to a CUDA 13 torch. `SHM`, the `mstar serve` default, is not affected. Swap in the CUDA 13 build:

```bash
uv pip uninstall mooncake-transfer-engine
uv pip install --reinstall --no-deps mooncake-transfer-engine-cuda13
```

Installing an extra again puts the CUDA 12 build back, so repeat the swap after it.
