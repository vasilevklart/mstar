---
title: "Compile-cache bundles"
description: "Carry a warmed-up server's compile caches to a new host or container, so its first start is warm."
---

A first start compiles every captured forward with Inductor (tuning it at `-O1` and `-O2`), Triton builds the kernels, and on ROCm MIOpen searches its convolution solvers. All three cache what they produce ([Restarts and the compile cache](/serving#restarts-and-the-compile-cache)), so a start on the same host skips that work. A *bundle* carries those caches to another host or container with the same software stack, so its first start is warm too.

```bash
# on a host that has served the configs you want to ship warm
mstar cache pack /shared/mstar-bundles --note "qwen3_5_9b, whisper_large"

# on the new host, before serving
mstar cache unpack /shared/mstar-bundles
# or in one step
mstar serve qwen3_5_9b --compile-bundle /shared/mstar-bundles
```

## The stack key {#the-stack-key}

A bundle is only useful on the stack that compiled it, so bundles are kept per key:

```text
<product>/torch-<torch version>-<hip|cuda>-<version>-triton-<triton version>
mi325x-vf/torch-2.12.1+rocm7.2-hip-7.2.53211-triton-3.7.1
```

`mstar cache key` prints this host's. The product is the GPU's name, lower-cased with `AMD Instinct` dropped. The manifest also records the GPU arch (`gfx942`, `sm_90`).

- The arch, torch, HIP or CUDA, and Triton versions must match, and on CUDA the product too. Inductor and Triton key their own entries on them (on CUDA, Inductor's graph key holds the GPU's name, so an H100's graphs miss on an H200), so a bundle from another stack would unpack without error and its compiled graphs would never be read. `mstar cache unpack` refuses it (`--force` unpacks it anyway).
- On ROCm the product doesn't have to match, since Inductor keys graphs on the gfx arch there. Autotuning picks are timings taken on the product that compiled them: an MI300X bundle loads on an MI325X (both gfx942) and starts warm, but its kernels were tuned on the MI300X. The startup line says so. A root is searched only under this host's product, so pass such a bundle's own directory.
- Inductor's graph key also holds the device index, so tensor-parallel ranks share no entries: a bundle serves the GPU layout it was warmed on, the same TP size and the same mapping of graph nodes to GPUs.
- Nothing in the key covers the driver, `ptxas` or the M\* version. A newer M\* that changes a captured forward's graph compiles that graph again on first start and keeps the rest.

## Layout {#layout}

A bundle root holds one directory per key; each is a bundle:

```text
<root>/<product>/<torch-...-triton-...>/
    manifest.json        the key, member count and size per tar, and one history entry per pack
    inductor.tar         TORCHINDUCTOR_CACHE_DIR, less a Triton dir inside it
    triton.tar           TRITON_CACHE_DIR
    miopen.tar           MIOPEN_USER_DB_PATH (ROCm)
    miopen-kernels.tar   MIOPEN_CUSTOM_CACHE_DIR, only when it is a different directory
    .append.lock         taken by every pack
```

Each tar is uncompressed and holds its directory's files as `./<path>`, so it can be read and merged with plain `tar`. `unpack` and `pack` find these directories the way a server started from the same environment does: an exported variable, else M\*'s default for Inductor and Triton (`~/.cache/mstar/torchinductor` and its `triton` subdirectory, see [Compilation](/environment_variables#compilation)), else the library's own (MIOpen's `~/.config/miopen` and `~/.cache/miopen`). `mstar cache dirs` prints them.

Not in a bundle: FlashInfer's JIT builds (`FLASHINFER_WORKSPACE_BASE`), AITER's and FlyDSL's on ROCm (`AITER_JIT_DIR`, `FLYDSL_RUNTIME_CACHE_DIR`), which are keyed by their own package versions rather than by this key, and the weights.

On NVIDIA, FlashInfer decides whether a start from a bundle is warm. Its JIT builds took 126-259 s of each cold start on an H200, and a copied build directory rebuilds at a new path, since its ninja files name outputs by absolute path: Qwen3.5-0.8B with every cache directory copied to a new path still took 306 s to start. Install FlashInfer's prebuilt kernels wherever a bundle is unpacked, with `flashinfer install-jit-cache-wheel --mode minimal` (this machine's GPUs) or `flashinfer download-kernels` (every architecture), which pick the wheels for the installed `flashinfer-python`. With them, Qwen3.5-0.8B started from a bundle in 112 s, against 284 s with empty Inductor and Triton caches, the same as a warm restart.

## Trust {#trust}

A bundle is code. Inductor's entries are pickled graphs and Triton's are compiled kernels (`.so`, `.cubin`, `.hsaco`), and a server loads and runs them. Unpack only bundles you built or got from a source you trust, as you would a container image, and keep a shared bundle root writable only by those who pack into it. `unpack` refuses a member whose path or link leaves its cache directory; that keeps a damaged tar from writing elsewhere, and says nothing about what the files in it do.

## Building a bundle {#building-a-bundle}

1. Point the caches at empty directories (or start from a bundle for the same key), for example `export XDG_CACHE_HOME=$(mktemp -d)`.
2. Start each config you want warm and send it a request of every shape that compiles on first use, such as each image size a diffusion model will serve. Most of the work happens before `/health` answers: every capture bucket is compiled at startup.
3. Stop the servers, then `mstar cache pack ROOT`. Packing must not run while a server is writing to the caches.

`pack` adds to the bundle for this host's key under `ROOT`, creating it if needed. It appends the Inductor and Triton files the bundle doesn't have and those whose size or modification time differ from its last copy; their entries never change once written. MIOpen keeps each database in one file (the find and perf databases as `key=value` text, compiled kernels in SQLite), so a changed one is merged with the bundle's copy, this host's record winning where both have one: caches warmed separately, each from empty, add up rather than replace each other. Each tar is copied, appended to and renamed into place, so a concurrent `unpack` never reads a partial tar, and the lock serializes packs, so several hosts with the same key can add to one bundle in turn. `pack` runs the system `tar` (GNU or BSD); `unpack` needs only Python.

## Unpacking {#unpacking}

`mstar cache unpack SRC` takes a bundle or a root of bundles, picks the one for this host's key, and extracts the last copy of each file in each tar into its cache directory:

- A file the directory already has is kept, since Inductor and Triton entries never change once written.
- A MIOpen database the directory already has is merged with the bundle's copy, the bundle's record winning where both have one, so the records only this host has stay.
- Each file is written beside its name and renamed into place, and each directory is locked while it is written (`.mstar-unpack.lock` in it, which `pack` leaves out), so servers starting together on one host can unpack into the same caches.

It exits with status 3 when `SRC` has no bundle for this stack, and `mstar serve --compile-bundle` then starts cold with a warning. A damaged bundle (a manifest or tar it can't read, or a tar holding fewer files than the manifest records) exits with status 1 and a `damaged bundle:` line, and `serve` stops. Nothing checks the files' contents, so a damaged byte inside one goes unnoticed. `unpack` leaves `mstar-bundle.json` in the Inductor directory, naming the bundle and its key.

At startup each worker logs its stack key and what it found:

```text
Worker audio_encoder: compile cache: stack mi325x-vf/torch-...-triton-3.7.1; bundle /shared/mstar-bundles/mi325x-vf/torch-... unpacked 2026-10-29T21:04:11+00:00 matches
Worker decoder: compile cache: stack mi325x-vf/...; no bundle unpacked into /root/.cache/mstar/torchinductor
```

A bundle built for another arch, torch, HIP, CUDA or Triton, or on CUDA for another GPU model, logs a warning instead, since its entries won't be used.

`mstar cache show ROOT` lists the bundles under a root with their sizes and last packs.
