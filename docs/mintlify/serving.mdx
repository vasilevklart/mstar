M\* has two server commands:

- `mstar serve <model>` takes a key from [Supported models](/models) and serves that key's default config. It sets a per-user upload directory and the SHM tensor transport, then calls `mstar-serve`.
- `mstar-serve --config <yaml>` starts whatever a config file describes. It defaults to the RDMA tensor transport and an upload directory shared by every user on the host.

Every flag of both commands is in the [CLI reference](/reference/cli), and every config key is in the [Config reference](/reference/config).

## Frontends {#frontends}

HTTP and WebSocket traffic is served by `mstar-server`, a Rust binary that the Python launcher starts once the model has loaded. The launcher looks for the binary before it loads anything, in this order:

1. `--rust-frontend-bin <path>`
2. the `MSTAR_SERVER_BIN` environment variable
3. the Python environment's scripts directory, where a Linux wheel installs it
4. `$PATH`
5. `rust/server/target/release/mstar-server` in the source checkout

In a source checkout, a binary built from other sources than the checkout's `rust/` directory is stale. The lookup skips a stale binary, or uses it with a warning when you named it with the flag or the variable. The check also needs a `mstar_rust` extension built from the same checkout (`maturin develop --release -m rust/Cargo.toml`). If no binary is found, or every one found is stale, the command exits before the model loads and prints the build command. From the checkout root:

```bash
cargo build --release --manifest-path rust/server/Cargo.toml
```

[Installation](/installation#rust) covers the Rust toolchain.

The launcher passes `--host` to `mstar-server` as `MSTAR_SERVER_HOST`. If that variable is already exported, it wins over `--host`. If `mstar-server` exits with an error, for example because another process took the port while the model loaded, the deployment stops and the command exits with status 3.

`--python-frontend` serves the same routes from the deprecated uvicorn/FastAPI frontend instead, and does not take `--rust-frontend-bin`. The config key `ws_per_message_deflate` applies only to that frontend: `mstar-server` never offers per-message deflate. The routes are listed in the [HTTP API reference](/reference/http-api#routes).

## mstar serve {#mstar-serve}

```bash
mstar serve <model> [options]
```

Common flags:

| Flag | Default | Effect |
|---|---|---|
| `--gpus` | unchanged | Sets `CUDA_VISIBLE_DEVICES`, for example `0,1`. |
| `--port` | `8000` | HTTP port. |
| `--host` | `0.0.0.0` | Bind address. |
| `--api-key` | `MSTAR_API_KEY`, else none | Require a bearer key on every route but `/health` and `/metrics` ([API key](/serving#api-key)). |
| `--config` | the model's default | Serve your own YAML ([Custom configs](/serving#custom-configs)). |
| `-O`, `--compile-level` | `MSTAR_COMPILE_LEVEL`, else `1` | Compile tuning at startup: `0` starts fastest, `2` tunes most ([Compile levels](/cold-start#compile-levels)). |
| `--cache-dir` | Hugging Face default | Where weights are downloaded. |
| `--log-stats` | off | Print a profile of each request ([Request profiling](/serving#request-profiling)). |
| `--enable-metrics` | off | Serve Prometheus metrics at `/metrics` ([Metrics](/metrics)). Needs `mstar-ai[metrics]`. |

```bash
# Qwen3-Omni's default config places its nodes on two GPUs
mstar serve qwen3_omni --gpus 0,1

# A second server on the same machine: another GPU and another port
mstar serve kokoro --gpus 2 --port 8001

# Local clients only, the fastest start, weights on a large disk
mstar serve qwen3_5_9b --host 127.0.0.1 -O0 --cache-dir /data/hf
```

The command prints example calls for the model as soon as it starts, before the weights load and the graphs compile. The server accepts connections only once it is ready, so poll `curl http://localhost:8000/health` until it answers. [Cold start](/cold-start#startup-sequence) explains the wait, and [the compile cache](/cold-start#compile-cache) how to keep compiled kernels across restarts and containers.

## Custom configs {#custom-configs}

`--config` serves your own YAML. Start from a shipped config:

```bash
cp configs/qwen3_5_9b.yaml my_qwen.yaml
# edit my_qwen.yaml
mstar serve qwen3_5_9b --config my_qwen.yaml
```

The model name is still required. The config's `model:` key decides what is served; the name on the command line only picks the example calls printed at startup.

The shipped configs are in `configs/` in a source checkout. A wheel ships the same files in the `mstar.default_configs` package, and this prints where they are:

```bash
python -c "import mstar.default_configs as d, os; print(os.path.dirname(d.__file__))"
```

Each key's default config is in the Default config column of [Supported models](/models#matrix). It is not always `<model>.yaml`: `bagel` uses `bagel_single_gpu.yaml`.

To run a config without `mstar serve`, call `mstar-serve`. It defaults to RDMA tensor transport, which needs Mooncake and an RDMA network, so on one machine pass SHM:

```bash
mstar-serve --config my_qwen.yaml --tensor-comm-protocol SHM
```

`mstar-serve` has no `--gpus` or `-O`; set `CUDA_VISIBLE_DEVICES` and `MSTAR_COMPILE_LEVEL` instead. Its `--upload-dir` defaults to `/tmp/mstar_uploads`, one directory for every user on the host.

## Config files {#config-files}

A deployment config is a YAML mapping. This is `configs/bagel_single_gpu.yaml` in flow style, with comments added:

```yaml
model: "bagel"            # registry key
max_seq_len: 32768
node_groups:              # which nodes run on which ranks
  - {node_names: [vit_encoder], ranks: [0]}
  - {node_names: [vae_encoder, vae_decoder], ranks: [0]}
  - {node_names: [LLM], ranks: [0]}
```

`model`, `max_seq_len` and `node_groups` are required. Startup checks only that the top-level `max_seq_len` is present; a KV cache's length limit is its own `max_seq_len` under `resources`. The optional keys, by what they control:

| Area | Keys |
|---|---|
| Devices | `rank_devices`, `gpu_memory_fraction`, `mps` |
| Model setup | `model_kwargs`, `autocast_dtype`, `resources`, `knobs` |
| Admission | `max_concurrent_requests`, `unpausable_outputs`, `rebuild_host_mb`, `routing_weights` |
| Steps and scheduling | `max_batch_tokens`, `min_chunk_tokens`, `batch_builder`, `can_override_mixed_max_tokens`, `speculate_mid_prefill`, `speculation_mixes_walks`, `scheduling` |
| Startup | `warmup_requests`, `prefill_token_buckets` |
| Parallel groups | `tp_allreduce`, `tp_allreduce_max_kb`, `tp_async_sched`, `sharding_config`, `dist_timeout_s` |
| API server | `preprocess_workers`, `preprocess_torch_threads`, `max_call_input_mb`, `client_streams`, `ws_max_message_mb`, `ws_per_message_deflate`, `openpi` |

Each key has a one-line entry in the [Config reference](/reference/config).

### Resource overrides {#resources}

A model declares its KV caches, attention backends, positions and samplers, each under a name. A `resources:` block tunes them by that name. The names differ per model: BAGEL's KV cache is `kv`, Qwen3-Omni's Thinker cache is `thinker_kv`. The shape of a block, with example names:

```yaml
resources:
  kv_cache:
    max_num_pages: 1024      # also: page_size, max_seq_len, cpu_offload_pages,
                             # prefix_cache, prefix_cache_salt, prefix_cache_tp,
                             # context_parallel
  talker_attn:
    flashinfer_backend: fa2  # also: backend, decode_tensor_cores, decode_fmha
  vit_attn:                  # a cacheless (ragged) attention resource
    max_segments_per_request: 2  # also: max_segments_per_step, max_tokens_per_request,
                                 # flashinfer_backend
  seq_shard:                 # a node's sequence shard (SP ranks)
    min_tokens: 2048         # also: exchange
  linear_attn:               # a recurrent layer's resource (GDN, Mamba-2)
    backend: flashinfer
  sampler:
    greedy_capture: false    # also: enable_logprobs, enable_processed_logprobs
```

A block that names a resource the model does not declare, or a key the resource does not take, fails at startup. The [state contract](/contributing/state-contract) lists what each declaration builds and the keys it takes.

`prefix_cache: false` turns off cross-request prefix reuse for one cache. `prefix_cache_salt` goes into every cached page's key; a model that names no checkpoint needs one, or its prefix cache stays off. A single request opts out by sending `prefix_cache=False` in its `model_kwargs`. Above one rank the prefix cache stays off unless `prefix_cache_tp: true` is set; that cannot be combined with `cpu_offload_pages` or with replicas.

### KV admission and preemption {#kv-admission}

A request waits in its KV pool's queue until its reservation fits beside the ones already admitted. When a running request runs out of pages, newer requests give theirs up: each moves to host memory if the host pool can hold it, and otherwise, if it can be rebuilt, is dropped and later recomputes its KV from its token ids. The keys that control this:

| Key | Effect |
|---|---|
| `max_concurrent_requests` | Caps running requests; the rest wait in the conductor's queue. The pool's pages divided by one request's pages, prompt and output together, is a safe value. |
| `resources: <kv>: max_num_pages` | Device pages in the pool. |
| `resources: <kv>: cpu_offload_pages` | Host pages a preempted request can move to. With the prefix cache on, give it more pages than the device's prefix cache. |
| `unpausable_outputs` | Output modalities (default `[audio]`) whose streamed requests reserve their whole footprint and are never preempted once they start. |
| `rebuild_host_mb` | Pinned host memory for the prompts that dropped requests are rebuilt from. `0` turns dropping off on that node. |

The full rules are in the design note [admission_and_preemption.md](https://github.com/mstar-project/mstar/blob/main/docs/design/admission_and_preemption.md).

### Chunked prefill {#chunked-prefill}

A walk that supports chunked prefill runs at most its token budget per step and splits a longer prompt across steps. Each model sets default budgets, such as 2048 tokens for Qwen3.5's `LLM` and 1024 for Qwen3-Omni's `Thinker`. `max_batch_tokens` overrides them per node, with one budget for every budgeted walk of the node or a budget per walk, and `null` turns a walk's chunking off. Where the chunked walks run inside a combined walk that batches prompts with decode rows (`mixed` for Qwen3.5's `LLM`, `thinker_mixed` for Qwen3-Omni's `Thinker`), the combined walk's budget caps the step:

```yaml
# Qwen3.5: one budget for every budgeted walk of LLM
max_batch_tokens:
  LLM: 512
```

```yaml
# Qwen3-Omni: the budget of one Thinker step
max_batch_tokens:
  Thinker:
    thinker_mixed: 512
```

A node with `sp_size` above 1 runs its prefills whole and logs a warning at startup.

## Placement {#placement}

A model is a graph of nodes, and a request runs as a sequence of graph walks over them. BAGEL has four nodes (`vit_encoder`, `vae_encoder`, `LLM`, `vae_decoder`), three more when its guidance branches get workers of their own, and walks such as `prefill_text`, `decode` and `image_gen`. Each entry of `node_groups` places some of the nodes:

- `node_names`: the nodes.
- `ranks`: the worker ranks that run them. Each rank is one worker process, and rank `n` runs on device `n` unless `rank_devices` maps it elsewhere.
- `graph_walks` (optional): only these walks of the nodes run on these ranks. Without it, every walk does.

The model code does not change with the placement. This is `diff configs/bagel_single_gpu.yaml configs/bagel_cfg_parallel.yaml`, with comments dropped and entries in flow style:

```diff
 model: "bagel"
 max_seq_len: 32768
+max_concurrent_requests: 16
+resources:
+  kv:
+    cpu_offload_pages: 2048
 node_groups:
   - {node_names: [vit_encoder], ranks: [0]}
   - {node_names: [vae_encoder, vae_decoder], ranks: [0]}
-  - {node_names: [LLM], ranks: [0]}
+  - {node_names: [LLM, combine_cfg], ranks: [0]}
+  - {node_names: [LLM_cfg_text], ranks: [1], graph_walks: [image_gen_cfg2, image_gen_cfg3]}
+  - {node_names: [LLM_cfg_img], ranks: [2], graph_walks: [image_gen_cfg3]}
```

BAGEL's image generation runs up to three guidance branches per denoising step. Here the text branch (`LLM_cfg_text`) gets rank 1 and the image branch (`LLM_cfg_img`) gets rank 2, each only for the walks of the guided steps: `image_gen_cfg2` runs two branches and `image_gen_cfg3`, which edits use, runs three. The main branch stays on rank 0 with `combine_cfg`, which combines the branches' velocities. The config also caps running requests at 16 and gives the KV pool 2,048 host pages. `mstar serve bagel_cfg_parallel` serves it on three GPUs.

### Disaggregation {#disaggregation}

`graph_walks` can put the same node on different ranks for different walks. `configs/bagel_pd_disaggregated.yaml` runs BAGEL's prefills on rank 0 and decoding and image generation on rank 1:

```yaml
node_groups:
  - {node_names: [vit_encoder], ranks: [0]}
  - {node_names: [vae_encoder, vae_decoder], ranks: [0]}
  - {node_names: [LLM], ranks: [0], graph_walks: [prefill_text, prefill_vit, prefill_vae]}
  - {node_names: [LLM], ranks: [1], graph_walks: [decode, image_gen, image_gen_head, image_gen_guided2, image_gen_guided3]}
```

`orpheus_pd_disaggregated.yaml`, `qwen3omni_pd_disaggregated.yaml` and `nemotron_duplex_disagg.yaml` do the same for other models.

### Tensor parallelism {#tensor-parallelism}

`tp_size` shards a node's weights and heads over that many ranks. From `configs/qwen3_5_9b_tp2.yaml`:

```yaml
node_groups:
  - {node_names: [vision_encoder], ranks: [0]}
  - {node_names: [LLM], ranks: [0, 1], tp_size: 2}
```

The model must declare the node TP-enabled (`tp_enabled_nodes`); startup refuses a `tp_size` above 1 on any other node.

### Sequence and CFG parallelism {#sequence-parallelism}

`sp_size` splits a node's tokens over ranks (Ulysses, an all-to-all around attention), and `cfg_size` splits its classifier-free-guidance branches, one share per rank. The axes compose with TP: a group's ranks form lockstep instances of `cfg_size * sp_size * tp_size` ranks, laid out `[cfg][sp][tp]` with TP on adjacent ranks. From `configs/wan22_cfg2_sp2_4gpu.yaml`:

```yaml
node_groups:
  - {node_names: [text_encoder], ranks: [0]}
  - {node_names: [vae_encoder, vae_decoder], ranks: [0]}
  - {node_names: [dit], ranks: [0, 1, 2, 3], cfg_size: 2, sp_size: 2}
```

`sp_size` needs a node that declares a sequence shard, or a KV cache with `context_parallel: true`, which stores K/V by position over the SP ranks. The shard's `min_tokens` and `exchange` keys tune the split. `cfg_size` needs a node the model declares CFG-enabled (`cfg_enabled_nodes`), and must divide its guidance branches (two for Wan2.2's `dit`).

### Data parallelism {#data-parallelism}

A group with more `ranks` than one lockstep instance needs runs a replica on each instance. In `configs/qwen3_5_9b_dp2.yaml` an instance is one rank, so each GPU holds a whole replica:

```yaml
node_groups:
  - {node_names: [LLM, vision_encoder], ranks: [0, 1]}
```

The conductor sends each request to the replica with the lowest cost: `routing_weights.load` (default 1.0) times its live requests, minus `routing_weights.prefix` (default 8.0) times the share of the prompt predicted to be in its prefix cache. Ties go to the replica picked longest ago, and `prefix: 0` picks by load alone.

### Expert parallelism {#expert-parallelism}

By default a TP group shards every MoE expert. An `ep_config` block with `parallel: ep` gives each rank whole experts instead, while attention and dense MLPs stay TP-sharded. From `configs/qwen3omni_thinker_ep2.yaml`:

```yaml
node_groups:
  - node_names: [Thinker]
    ranks: [0, 1]
    tp_size: 2
    ep_config:
      parallel: ep          # each rank holds 64 of the 128 experts
```

The expert count must divide by the group size, and the model must declare the node EP-enabled (`ep_enabled_nodes`).

### Several workers on one GPU {#shared-gpu}

`rank_devices` maps ranks to devices, so two node groups can run as separate worker processes on one GPU. In `configs/qwen3tts_split.yaml` the Talker's steps then no longer wait on the codec's host work:

```yaml
node_groups:
  - {node_names: [Talker], ranks: [0], graph_walks: [talker_prefill, talker_decode]}
  - {node_names: [Codec], ranks: [1], graph_walks: [codec_chunk]}
rank_devices: {1: 0}
mps: true
```

`mps: true` runs the workers as clients of a CUDA MPS daemon the conductor starts, so their kernels overlap instead of time-slicing. It is NVIDIA only and needs `nvidia-cuda-mps-control` on `PATH`. Workers that share a GPU see each other's memory only as used, so set `gpu_memory_fraction` (for example `0.45` for each of two) to bound what each one's graph capture plans for. It counts PyTorch allocations, not the CUDA context or NCCL buffers, so leave room for those.

## model_kwargs {#model-kwargs}

`model_kwargs` go to the model's constructor at server start, so they hold for every request. `configs/pi05_droid.yaml` loads the Pi0.5 DROID fine-tune, fixes the camera count and carries the robot's normalization stats (abridged):

```yaml
model: "pi05"
max_seq_len: 2048
model_kwargs:
  model_path_hf: "lerobot/pi05_droid"
  num_cameras: 2
  norm_stats:
    state: {q01: [...], q99: [...]}
    actions: {q01: [...], q99: [...]}
node_groups:
  - {node_names: [vit_encoder], ranks: [0]}
  - {node_names: [LLM, action_expert], ranks: [0]}
```

The keys each model reads are on its page under [Supported models](/models). Per-request knobs such as `temperature`, `voice` and `max_output_tokens` go in the request instead; see [Generation parameters](/clients#generation-parameters).

A request's `seed` gives the same output whatever it is batched with only on samplers that read each row's own seed: on CUDA, a sampler whose vocabulary is 4,096 tokens or fewer (the talker and code-predictor samplers of Qwen3-TTS and Qwen3-Omni), when none of `min_p`, the windowed penalty, `min_tokens`, `top_p_first` or processed log-probs is enabled on its node. Every other sampler, including every text LLM's, draws through FlashInfer with the first row's seed for the whole batch, so there a seed repeats its output only in the same batch, such as a request sent alone.

## API key {#api-key}

Both commands bind `0.0.0.0` by default and accept requests from anyone who can reach the port. Unless a gateway in front of the server authenticates clients, set a key or bind `--host 127.0.0.1`. The server logs a warning at startup while no key is set.

```bash
export MSTAR_API_KEY="$(openssl rand -hex 32)"
mstar serve qwen3_omni
```

With a key set, every HTTP route except `/health` and `/metrics` answers `401` unless the request carries `Authorization: Bearer <key>`, and the WebSocket routes (`/v1/realtime`, `/generate/ws`) refuse the handshake without it. The check is one middleware over the whole app on both frontends, and the comparison takes the same time however much of the key matches. CORS preflights still get their answer, since browsers send them without credentials. On a deployment with an `openpi:` block, the `/` socket also takes `Authorization: Api-Key <key>`, and `/healthz` needs no key.

`--api-key` overrides the environment variable, but prefer the variable: a command-line flag is visible to every local user in the process list. An empty value turns the check off, so `--api-key ""` disables a key set in the environment, and so does a variable that expands to nothing.

Clients pass the key as their API key: `MStarClient(base_url, api_key=...)`, which reads `MSTAR_API_KEY` when not given one, or `OpenAI(base_url=..., api_key=...)`. See [Using a server](/clients).

Under NVIDIA Dynamo (`python -m mstar.integrations.dynamo`), Dynamo's own frontend serves HTTP and the M\* worker checks no key, so authenticate at Dynamo's frontend or a gateway in front of it. The worker sends the engine one-shot calls only (a realtime turn becomes one call when it is committed); for input that streams into a running call, serve the model with `mstar serve` and use `/v1/realtime` or `/generate/ws`.

## Tensor transport {#tensor-transport}

`--tensor-comm-protocol` picks how processes send tensors to each other. Values are uppercase.

| Value | Use | Needs |
|---|---|---|
| `SHM` | One machine. The default of `mstar serve`. | Nothing extra. |
| `TCP` | Any network. `--tcp-transfer-device` picks the network device. | Mooncake (`mooncake-transfer-engine`). |
| `RDMA` | RDMA networks. The default of `mstar-serve`. | Mooncake and RDMA NICs. |

Mooncake is not a core dependency; the model extras that pull it in require `mooncake-transfer-engine` 0.3.13.post1 or newer. Without it, `TCP` and `RDMA` fail at startup with "Mooncake TransferEngine is required for RDMA/TCP protocol".

Mooncake's transfer engine does not authenticate its peers, and each worker's engine picks its ports at startup, so restrict by host: only the deployment's own hosts should reach the workers. Releases before 0.3.12.post1 let any host that reaches the TCP data port read or write the worker's memory (CVE-2026-103764), and a worker warns at startup if it finds one.

## Request profiling {#request-profiling}

`--log-stats`, on either command, prints a profile of each request when it finishes. `--log-stats-file <path>` appends the profiles to a file instead of stdout and implies `--log-stats`:

```bash
mstar serve bagel --log-stats
mstar serve orpheus --log-stats-file stats.txt
```

A report has four sections. Inputs and Outputs, Graph timings and Tensor transfer are left out when they have no data. An example:

```text
============================================================
 Request profile: 3f9c1e2a-…
============================================================
 Inputs:
   text         x1          72 B
   image        x1       1.1 MiB
 Outputs:
   image        x1       1.1 MiB
------------------------------------------------------------
 Timeline:
   recv → preprocess done                       62.6 ms
   preprocess done → conductor ingest            2.3 ms
   conductor ingest → first chunk              133.7 ms
   first chunk → last chunk                    683.3 ms
   last chunk → conductor done                   1.5 ms
   conductor done → finish                       3.1 ms
   total                                       886.5 ms
------------------------------------------------------------
 Graph timings (CPU, ms) — total over request (avg per exec):
                            all                 fwd                 pre                post*
   LLM
     decode  n=588      3277.9 (   5.57)    2858.0 (   4.86)     243.0 (   0.41)     176.9 (   0.30)
     prefill n=1          8.78 (   8.78)      4.24 (   4.24)      3.47 (   3.47)      1.06 (   1.06)

   * post overlaps the next step / another in-flight batch under
     speculative scheduling, so it is not necessarily additive.
------------------------------------------------------------
 Tensor transfer   size / transport-time / count:
   rx (received over the wire), by source → dest:
     worker_0 → worker_1
       hidden                  106.7 MiB      78.7 ms  (x49)

   tx (registered/written for send), by source:
     worker_0
       hidden                  106.7 MiB      0.90 ms  (x49)
============================================================
```

- Inputs and Outputs: count and size per modality. Inputs are the raw bytes the client sent (file sizes, the prompt's UTF-8 length), not the decoded tensors.
- Timeline: wall-clock stages from the API server through the conductor and workers and back, ordered by timestamp, so no stage is negative when two checkpoints race. The timestamps come from `time.perf_counter()` in each process, which compare only when every process runs on one host. Lines such as `worker span (same-host clocks)` and `output postprocess (sum)` appear when those times were recorded.
- Graph timings: CPU time per node and graph walk over the request, as the total and, in parentheses, the average per execution (`n` executions). `all` is `pre` + `fwd` + `post`. `fwd` is the CPU time to launch the batch's forward, not the request's GPU time, since the pipeline is not synchronized. `pre` prepares inputs, and `post` runs after the forward and can overlap the next step.
- Tensor transfer: bytes moved over the [tensor transport](/serving#tensor-transport). `rx` is grouped by source and destination; `tx` only by source, since a sender writes data before it knows who reads it. The time is the read on `rx` and the registration or write on `tx`, and the count is the number of tensors.

With `--log-stats` off, no process does this bookkeeping.

## Host idle states {#host-idle}

On hosts whose idle cores drop into deep C-states, a small model's decode step can wait on CPUs waking up. The `step_thread_core` knob pins each worker's main, GPU and plan threads to cores of their own (`auto`, the default, pins nothing and logs why; also `always`, `siblings`, `off` or a CPU number), and `idle_hold: qos` asks the kernel to keep CPUs out of deep idle through `/dev/cpu_dma_latency`, which most containers hide. Measure on your host before you pin; both are under `knobs` in the [Config reference](/reference/config#knobs) and as `MSTAR_STEP_THREAD_CORE` and `MSTAR_IDLE_HOLD` in [Environment variables](/environment_variables).
