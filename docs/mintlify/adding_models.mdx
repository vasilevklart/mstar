Adding a model to `mstar` takes the steps below. When you finish, the conductor can schedule your model, workers can run it, and `mstar serve <your_model>` serves it. [State contract](/contributing/state-contract) is the reference for the names a model imports, and [Worked examples](/contributing/worked-examples) walks five models in the tree through these steps.

## Overview {#overview}

A model in `mstar` has several separate responsibilities:

- **The** `Model` **class** (`mstar/model/base.py`) is the interface that the rest of the system calls. It tokenizes prompts, declares the computation graph, declares the state each node keeps, builds forward-pass arguments, and post-processes outputs. It contains no GPU compute.
- **Submodules** (`NodeSubmodule` in `mstar/model/submodule_base.py`) are the `torch.nn.Module` s that perform the compute. Each graph node maps to one submodule.
- **State** (`mstar.engine.state`) is what a node keeps between steps: a KV cache, a recurrent value, positions and a sampler. The model declares it in `declare_state()`, and its layers reach it through handles. The engine builds the resources (`mstar/engine/resources/`) that hold each declaration and binds a handle into the submodule and its layers. Per-request LoRA adapters stand outside it: they are weights that no request writes, and a model declares them in `lora_roots()` (see [Per-request LoRA adapters](/adding_models#per-request-lora-adapters)).
- **The engine** (`mstar/engine/engine.py`) is a single class that runs every node. It compiles forwards, captures accelerator graphs, batches requests, and runs each step's resource lifecycle (admit, plan, forward, commit). You never write an engine. A node's capabilities follow from the state it declares.
- **The graph** (`mstar/graph/base.py`) declares what runs in what order: nodes, edges between them, and loops. All of a model's work forms one large computation graph. Each named "graph walk" (for example `prefill` or `decode`) is one path through that graph. In code, however, you declare each walk as a separate standalone graph. A node that appears in several walks is referenced by name in each walk. The submodule behind that name, and its resources, are shared across all of them.
- **The config YAML** (`configs/`) maps graph nodes to physical GPU ranks through `node_groups`. Disaggregation is configured here. The same model code runs on one GPU or on many, and only the config changes.

A **tensor bundle** routed between nodes is a `NameToTensorList`, which is `dict[str, list[torch.Tensor]]` (`mstar/communication/tensors.py`). It maps an edge name to a list of tensors. The list usually has length 1.

The diagram below shows the request flow at the conductor and model level. Its granularity is one graph walk. The model decides at ingest which walks a request runs; the conductor runs them in order, moving on as each walk completes. Everything that happens inside a walk is described in later steps and is omitted here:

```text
process_prompt()              # text/media -> initial tensors
     │
     ▼
walk_plan()                   # per partition: the walks to run (e.g. prefill, decode)
     │
     ▼   (conductor sends each walk its inputs, the engine runs each node)
postprocess()                 # model output tensor -> bytes for the client
```

### Lint rules {#lint-rules}

`test/modular/test_state_lint.py` reads the source of every ported package. A new package passes it when:

- [ ] its directory is listed in `PORTED`. `test_a_model_package_is_ported_or_on_the_frozen_list` fails CI for a model package on neither list, and nothing is added to `UNPORTED`.
- [ ] it imports the engine only from `mstar.engine.state`. The exceptions are in `ALLOWED`: the capture configs in `mstar.engine.accelerator_graph_config` (`BatchedAcceleratorGraphConfig`, `PackedAcceleratorGraphConfig`, `PiecewiseBatchedConfig`, `PiecewisePackedConfig` and the rest), `ExecutingBatch`, `LoraFile` and `DEFAULT_PAGE_SIZE`.
- [ ] it defines no `get_node_resources`, `bind_resources` or `bind_node_resources`.
- [ ] it reads none of `node_resources`, `resources`, `request_state`, `request_states`, `per_request_states` or `sequence_shard`, nor what a handle holds (`FORBIDDEN_ATTRIBUTES`).
- [ ] it uses no `torch.compiler.disable`, as a call or a decorator, outside the functions `ALLOWED_IN_FUNCTION` names with a reason. The state calls hold the graph breaks.
- [ ] from `mstar.model.components.lora` it imports only `LoraRoot`, `AdapterRoot` and `PER_SEGMENT`.
- [ ] a token-decoder node subclasses `DeclaredTokenDecoder`, not `SampledTokenDecoder` directly, and writes none of its handle hooks (`bind_state`, `node_step`, `next_position`, `loopback_tokens`, `last_token_hidden`, `sample_tokens`) itself. An exception goes in `OWN_HOOKS` with its reason, as Qwen3.5's `node_step` does for its second array.

When the contract can't declare something your model needs, its mask or op and its binding land in `mstar/engine/state/adapters.py` first, in their own PR. Run the lint alone with `python -m pytest -q test/modular/test_state_lint.py`.

## What you will create {#what-you-will-create}

A typical model lives in its own package under `mstar/model/<your_model>/`:

```text
mstar/model/<your_model>/
├── __init__.py
├── config.py            # a @dataclass with architecture + generation params, and declared names
├── <your_model>_model.py # the Model subclass (the contract)
├── submodules.py        # NodeSubmodule subclasses (the compute wrappers)
└── components/          # the actual nn.Modules (attention, decoder, etc.)
```

Outside the package, [Step 1](#step-1-register-the-model) lists the registry, CLI, lint and docs entries, and [Step 6](#config-yaml) the config YAML.

## Step 1: Register the model {#step-1-register-the-model}

Open `mstar/model/registry.py` and add your model to `MODEL_REGISTRY` (and, if it loads weights from Hugging Face, to `HF_MODELS`). The dict key is the string you put under `model:` in a config YAML.

The value is a `(module_path, class_name)` tuple, not an imported class: the module is imported lazily through `import_module` when the model is used, which keeps `mstar.model.registry` cheap to import. A direct class import here would pull every model's dependencies into every process.

```python
MODEL_REGISTRY: dict[str, tuple[str, str]] = {
    # ...
    "your_model": ("mstar.model.your_model.your_model_model", "YourModel"),
}

HF_MODELS: dict[str, dict] = {
    # ...
    "your_model": {"model_path_hf": "org/your-model-id"},
}
```

There is no plugin scan, so the registry is the only place the class is discovered. It is not the only wiring step. A model also needs:

- `DEFAULT_CONFIGS` in `mstar/cli/main.py`, mapping the name to its default config file. Without it, `mstar serve <your_model>` exits with `error: unknown model` before anything loads.
- its package directory in `PORTED` in `test/modular/test_state_lint.py`. `test_a_model_package_is_ported_or_on_the_frozen_list` fails CI for a model package on neither `PORTED` nor `UNPORTED`, and `UNPORTED` takes no new entries ([Lint rules](#lint-rules)).
- a `request_kwargs()` override on the model class, naming every `model_kwargs` key the model reads ([Per-request settings](#per-request-settings)). `test_every_registered_model_declares_its_request_kwargs` in `test/modular/test_model_contracts.py` fails for a registered model that doesn't override it.
- a row in `docs/mintlify/models.mdx`, which is the model list users read.
- an `OpenAIAdapter` subclass in `ADAPTER_REGISTRY` (`mstar/api_server/openai/adapters.py`), *only* if the model maps onto OpenAI semantics such as `chat.completions`, `audio.speech` or `images.generate`. A model reached only through `POST /generate` needs none. The adapter is ported to the Rust frontend in the same change (a type implementing `OpenAIAdapter` in `rust/server/src/adapters/` and its row in `ADAPTERS`, tested by `test/rust/test_rust_openai_adapters.py`): `mstar serve` serves HTTP from `mstar-server`, the Python HTTP frontend is deprecated, and a surface only it serves is unfinished.
- the client-example tuples further down `mstar/cli/main.py`, so `mstar serve` prints a usage snippet. Cosmetic, but user-visible.

`test/modular/test_model_registration.py` enforces the registry, CLI and docs entries, so CI fails rather than shipping a model nobody can reach.

## Step 2: Implement the `Model` class {#step-2-implement-the-model-class}

Subclass [`mstar.model.base.Model`](https://github.com/mstar-project/mstar/blob/main/mstar/model/base.py) and implement its abstract methods. The constructor receives `model_path_hf` (from `HF_MODELS`) and any `**kwargs`. It normally loads the tokenizer and stores a config dataclass. Do not load weights in the constructor. Load them in `get_submodule`, so that the conductor process never allocates GPU memory.

You must implement these abstract methods:

`get_graph_walk_graphs(self) -> dict[str, GraphSection]` <br />
Return `{walk_name: graph}`. See [Step 3](/adding_models#step-3-declare-the-computation-graph).

`process_prompt(self, prompt, input_modalities, output_modalities, tensors=None, prompt_parts=None, **kwargs) -> NameToTensorList` <br />
Tokenize the prompt and produce the initial request tensors, for example `{"text_inputs": [token_ids]}`. This method runs in the API-server data worker, after raw media tensors are loaded. It can therefore read `tensors` (for example `image_inputs`, `audio_inputs` or `video_inputs`) to compute derived tensors such as `pixel_values`. The returned dict is merged into the request's tensors. See [Layouts](/adding_models#layouts) for what it returns about the request's state.

`input_modalities` is the request layout: one entry per prompt element in the order written, so `["image", "text", "image"]` is a distinct request from `["image", "image", "text"]`. `prompt_parts` carries the same sequence with the text attached, and is `None` for entrypoints that submit files and text separately. [`mstar.model.multimodal`](https://github.com/mstar-project/mstar/blob/main/mstar/model/multimodal.py) turns either into the prefill plan that `process_prompt` and the schedule builder both work from.

`walk_plan(self, partition_name, input_modalities, output_modalities, input_signals, model_kwargs) -> list[WalkStep]` <br />
The walks a partition runs for this request, in order, as [`mstar.model.base.WalkStep`](https://github.com/mstar-project/mstar/blob/main/mstar/conductor/request_info.py)s; `[]` when the request doesn't use the partition. A prefill-decode model returns `[WalkStep("prefill"), WalkStep("decode", bind={"text_inputs": "new_token"})]`.

- Inputs: every external and loop-back input of the walk that no stream feeds gets the persisted signal of its own name, the one `bind` names, or an empty edge (a denoise loop's seed, a chunk loop's tick). A persisted tensor a step reads is released when that step is sent, unless a later step reads it before any walk persists the name again; anything else is held until the request ends.
- Metadata: `step_metadata` carries request constants to every node of the step's walk. The last prefill before decode, which samples the reply's first token, sets `FINAL_PREFILL` (from `mstar.conductor.request_info`); `media_prefill_step` does this for a `MultimodalDecoderModel`.
- Advancing: a stream-fed step that runs only chunk loops runs once per chunk until the stream's final chunk, its inputs sent with the first chunk only. Any other step advances when its walk reports. In a partition a stream moves (`Connection.consumer_walk`), the conductor still moves past a step on its first report when it is the last step or the next step takes inputs, so such a step must run once (a `Loop`, say), and the plan must list every walk the stream can move it to.
- Errors: a `ValueError`, or `[]` for every partition, is a 400. A plan the conductor can't run is a 500: a walk not in the partition, a `bind` key that is not an input of the walk, a step after a once-per-chunk step, or a later step whose walk takes no input the conductor sends.

Qwen3.5 (through `MultimodalDecoderModel`), Z-Image, Orpheus and Chatterbox are references.

`get_submodule(self, node_name, device="cpu", tp_group=None, autocast_dtype=None, moe_parallel=None, cfg_group=None) -> NodeSubmodule | None` <br />
Build and return the `NodeSubmodule` for `node_name`, and cache the result. Load weights here, on `device`. Return `None` for dummy mode.

`tp_group` is the node's tensor-parallel communicator when the node is sharded. Pass it to the parallel-linear constructors. See [Step 6](/adding_models#tensor-parallelism). A node on sequence-parallel ranks gets no communicator: its resources run the exchanges (see [Sequence and context parallelism](/contributing/state-contract#sequence-parallelism)). `cfg_group` is passed only to a node whose group sets `cfg_size > 1`; see [Guidance (CFG) parallelism](/adding_models#guidance-cfg-parallelism).

`moe_parallel` is the node group's `ep_config`, parsed into a `MoeParallelConfig`. It is passed only to an EP-enabled node whose group sets one, so a model without MoE layers never receives it. See [Expert parallelism (MoE)](/adding_models#expert-parallelism-moe).

`autocast_dtype` is the dtype in which the node's parameters must be allocated. If you build the module on the `meta` device, cast it to this dtype before calling `to_empty(device)`. Casting after `to_empty` allocates every parameter in float32 first, which doubles the peak VRAM during loading.

See [Step 4](/adding_models#step-4-implement-the-submodules).

<Note>

`model_kwargs` reaches your model from clients through the OpenAI routes' `extra_body` passthrough. The Dynamo bridge (`mstar/integrations/dynamo/bridges.py`) strips OpenAI-standard fields no model consumes (`_STRIP_KEYS`) before that passthrough runs. If your model starts reading such a field from `model_kwargs`, the way `ignore_eos` is read, also delete the key from `_STRIP_KEYS`, or requests arriving through the Dynamo frontend will silently lose it.

</Note>

<Note>

`model_kwargs` cross the control plane to the conductor as plain data, so a value that `process_prompt` moves onto a tensor edge must not travel there too. List those kwargs in `PREPROCESS_ONLY_KWARGS`: the data worker keeps the originals for `postprocess` and leaves them out of the conductor's copy. Pi0.5 lists `robot_state`, and Cosmos3 lists `action` and `robot_state` (it passes only their sizes on, as `action_shape` and `robot_state_dim` metadata). A tensor left in `model_kwargs` fails at send with an error that names the kwarg.

</Note>

<Note>

The metadata `process_prompt` returns is laid over the request's own `model_kwargs`, so a key the model reads back there (a prompt layout) must be set in every mode and listed in `INTERNAL_KWARGS`: the data worker drops a client's value for it before `process_prompt`. Qwen3-TTS lists its prompt layout, speaker, language and clip digest.

</Note>

<Note>

A stream that starts with context-only items (a voice clone's reference frames) says so in the metadata as `"stream_lead_items": {edge: n}`: `edge` names a streaming `Connection`, and `n`, at most that edge's policy's left context, leads the first window as context and is never output. Leave the key out when `n` is 0. The data worker drops a client's value, and the consumer partition's workers prime the stream with it (Qwen3-TTS, VoxCPM2).

</Note>

The following methods have defaults and are optional to override: `text_output`, `postprocess` and `postprocess_inline` (described next), `get_request_resource_configs` (described below), `get_sampling_config`, `get_max_output_tokens`, `get_autocast_dtype`, `load_image`, `load_audio`, `load_video`, `load_decoded_image`, and the partition methods described at the end of this page. The default `load_audio` decodes an upload to mono at the class attribute `AUDIO_INPUT_RATE` (16 kHz) and refuses one longer than `MAX_AUDIO_SECONDS` (30 minutes); set those rather than overriding it. `load_decoded_image` takes an image the API server already holds decoded (RGB uint8 `[3, H, W]`, from the openpi WebSocket) and must return what `load_image` returns for the same pixels in a file. The default refuses, so a model takes images only as files until it overrides this. pi0.5's `load_image` calls it, so the two paths cannot drift apart. A robot policy also overrides `robot_io`, returning a `RobotIO`: the `model_kwargs` key its robot state goes under, and the `[action_horizon, action_dim]` shape of the float32 actions its `postprocess` returns. The openpi WebSocket serves a model by these two hooks alone, so a new policy needs no change to the API server.

`text_output(self) -> TextOutput | None` <br />
Declare how text output (token ids) becomes bytes: a detokenizer, and the ids that end a reply, which are dropped unless the request sets `ignore_eos`. `postprocess` and `postprocess_inline` derive their text paths from it. A text chunk may end inside a character, since the API server joins a request's text chunks before decoding them, so declare a detokenizer from `mstar.model.utils` that emits each token's raw bytes (`TextChunkDetokenizer` or `ByteLevelDetokenizer` for byte-level BPE, `SentencePieceDetokenizer` for a SentencePiece vocabulary) rather than `tokenizer.decode([id])`, which turns a split character into U+FFFD.

`postprocess(self, output, modality, request_kwargs=None) -> bytes` <br />
Encode a finished output tensor to bytes for the client: `utf-8` for text, PNG for images, and so on. The default encodes text through `text_output` and mono audio as headerless 16-bit PCM (a float waveform in [-1, 1] is scaled and truncated; integer samples are cast), and raises `ValueError` for any other modality. Override it for those, or for audio with more than one channel, and hand the rest to `super().postprocess`.

`postprocess_inline(self, values, modality, request_kwargs) -> list[bytes]` <br />
`postprocess` for one decode step's inline values (one sampled token id per request), called once per step. With `text_output` declared, each id maps to its bytes (the detokenizer's `token_bytes`); otherwise each value goes through `postprocess` as a one-element tensor.

`Model.nodes` is a read-only property. It returns the sorted set of node names that appear in any graph walk.

### Per-request settings {#per-request-settings}

A declaration is fixed at load time and is shared by every request. Parameters that differ per request, such as sampling parameters, come from a separate method:

```text
get_request_resource_configs(
    self, input_modalities: list[str], output_modalities: list[str], model_kwargs: dict,
) -> dict[str, SampleSettings]
```

The returned dict is keyed by the sampler's declared name. The conductor calls this method once per request, with the request's modalities and kwargs as `walk_plan` gets them, and sets the seed, derived per sampler so each sampler of a request draws its own stream. A name that no sampler declares fails the request. `SampleSettings` holds a request's knobs:

- `temperature`, `top_k`, `top_p`, `repetition_penalty`, `ignore_eos` and `min_p`. `min_p` follows the HF processor order (after the penalty and temperature, before top-k/top-p) and needs `Sampler(min_p=True)`, which adds the filter to that node's captured sampler only. `penalize_prompt` says whether the penalty also counts the prompt's tokens.
- `min_tokens`: the sampler's `eos_ids` are barred until `min_tokens` tokens exist, applied after top-k/top-p (CUDA only).
- `return_logprobs` and `logprobs_mode`. `return_logprobs` reports each sampled token's log-prob under `softmax(logits / T)`, before the penalty and filters, with T = 1 for greedy requests, as `{"logprobs": [...]}` in the chunk's metadata. The model passes it into its `SampleSettings` (the conductor refuses the request otherwise), samples once per step and hands over row-addressed stop buffers (`BatchedModelOutput.check_stop_buffers`), which the log-probs ride to the host. The captured sampler then scores every step, so a deployment turns it on with `resources: {<sampler name>: {enable_logprobs: true}}`. `logprobs_mode: "processed"` (`enable_processed_logprobs`, CUDA, a separate switch) scores the distribution after the penalty, temperature, min-p, top-k/top-p and min-tokens floor, where a greedy token scores 0; a trainer sampling greedily wants `"raw"`.
- `repetition_window`, `top_p_first` and `top_p_min_keep` stay at their defaults until a port needs them: they ask the node's sampler for a capability a `Sampler` declaration doesn't name yet.

A step whose every row samples greedily (temperature 0, no repetition penalty, no `min_tokens` and no log-probs) takes each row's argmax instead of the full sampler's draw, eagerly or in a twin of each batched capture (see [Lean captures](/contributing/state-contract#lean-captures)); any other step runs the full sampler. By default only a sampler whose `vocab_size` is past the one-kernel draw (4096) does this, since a narrower one draws in one kernel already. A deployment's `resources: {<sampler name>: {greedy_capture: false}}` turns it off, and with it the twins' capture memory and time, for a deployment that never samples greedily, and `true` turns it on whatever the vocabulary. The model declares nothing for it.

A model can pass through what the request set:

```python
def get_request_resource_configs(self, input_modalities, output_modalities, model_kwargs):
    keys = ["temperature", "top_p", "top_k", "repetition_penalty", "ignore_eos",
            "return_logprobs", "logprobs_mode"]
    return {SAMPLER: SampleSettings(**{k: model_kwargs[k] for k in keys if k in model_kwargs})}
```

Sampling knobs mean the same thing on every model ([Generation parameters](/clients#generation-parameters)), and the server range-checks them before your model sees them. A model's part of that contract:

- Default each knob the request leaves unset from the checkpoint's own `generation_config.json` (`mstar.model.utils.load_generation_defaults`), falling back to your config only when the checkpoint ships none.
- Raise `ValueError` (a 400) for an input you cannot serve; never clamp, coerce, or fall back silently. A `Sampler` declared without `penalty` or `min_p` refuses those knobs at admission, so do not default a penalty onto it.
- Declare every `model_kwargs` key you read in `request_kwargs()`; any other key a client sends is logged as ignored by the server. `test_model_contracts.py` fails for a registered model that does not override it.
- Bound a request's length, or a denoise loop's step count, through `get_loop_caps`: the conductor refuses a cap past the loop's `max_iters` instead of cutting the request short, so do not clamp it, or check it against a typed-in limit, yourself.
- Draw any model-local randomness from the request's seed (`random_seed` on the forward-pass info), never the global RNG.

A spec can also build its own request's config from `model_kwargs` (`NodeResourceSpec.request_config`), which the conductor adds beside the model's. That is how a resource the deployment declares, such as a LoRA pool, takes per-request settings without model code. A row with no config under a resource's key may let that resource run lean for the step; see [Lean captures](/contributing/state-contract#lean-captures).

`get_sampling_config(node_name, model_kwargs)` is a helper for assembling sampling parameters. The engine does not read it; pass its result into a `SampleSettings` here.

<Warning>

Never pass sampling parameters into a captured forward as Python scalars. Their values are recorded into the captured kernel launch, and every replay then reuses the values from capture time. No error is raised. Parameters that reach the sampler through `SampleSettings` are stored in buffers whose addresses do not change across replays, so they stay per-request and remain safe under graph capture.

</Warning>

### Layouts {#layouts}

A model with an append-only array states, for every request, what its walks write into each label of the array. The engine turns that layout into the request's footprint, the most pages each label can hold, before the request runs. An array declares its labels (`Array(labels=...)`, `{"main"}` by default), and each request's layout comes from `process_prompt`.

`kv_labels(self) -> dict[str, dict[str, KVLabel]]` <br />
Return `{array: {label: KVLabel}}` for every label of every append-only array, naming only declared labels. This hook is temporary, until prefix keys come from layouts. A [`mstar.model.base.KVLabel`](https://github.com/mstar-project/mstar/blob/main/mstar/model/base.py) has two fields:

- `growth`: `(walk, loop)` pairs, each a walk that keeps writing after admission, bounded by the named loop. Only a named loop can bound growth, since an unnamed one is renamed in every process.
- `keys`: a [`mstar.model.base.PrefixKeys`](https://github.com/mstar-project/mstar/blob/main/mstar/model/base.py), or `None`. See **Cross-request prefix reuse** below.

A label written only by spans and scratch, such as a guidance branch, is `KVLabel()`.

`process_prompt` returns, under `state_layout` in its metadata, a `Layout` for every label the request opens, keyed by array and then label: the labels it can name on any node and walk, `main` when it names none. On an append-only array the request opens the labels the layout names there, so the model returns no `KVReqConfig` for them. On one the layout doesn't name, it opens the labels `kv_labels()` lists for it, or `main` where that lists none, and a paged array needs a layout for each label it opens, so leaving one out fails the request: lay out every paged array. A layout may be empty where an opened label is never written. A Value's layout is `Layout()`, because a Value takes one slot per label. A layout has four fields:

- `spans`: the committed writes known at intake, in walk order. A `Span` has a `kind`: `"ids"` for token ids from the tensor `source` names, `"digest"` for KV made from an uploaded file (`source` is `(modality, index)`), and `"rows"` for KV made from anything else, such as another node's outputs. `length` is the slots the write fills, `advance` how far it moves the position counter, and `scratch` the most one non-committing step writes before the span commits (a window's denoise steps).
  - A request whose spans are not all `"ids"` can be rebuilt at one rank when the node's `RebuildPolicy` names their walks: the worker keeps host copies of what the node read in each prefill step and runs the steps again from them, in `opens_step` order. `copy_width` gives, per walk that reads more than ids, the values those copies hold per KV slot; startup raises without it. The last span must be `"ids"`, a keyed label must be keyed over every span, and the walk must read its prompt with the samples appended to the last row's ids. Without a rebuild policy, such a request in a pool that decides admission can only move to the host, and reserves its whole footprint where the host has no room.
- `growth`: `(loop, entries)` pairs, `entries` per iteration of `loop`.
- `scratch`: the most entries one non-committing step writes past the kept length.
- `max_growth`: the most entries the growth reserves, below what the loops' caps give, for a label whose loops stop sooner than their caps say. None takes the caps.

`process_prompt` may also return `keyed_spans`, keyed by array and then label: how many leading spans the label's keys cover, by default every span before the first `rows` span. A prompt on a walk the keys don't name sets 0, because the data worker refuses a keyed span from any other walk. This key is temporary, with `kv_labels`. A name either key doesn't declare fails the request.

The footprint adds the spans, the growth at each loop's iterations (up to the layout's `max_growth`) and the scratch, and rounds up to whole pages per label. A span's own scratch counts only with the spans before it, so a window's denoise steps and its commit count once. Under a `RetentionPolicy` it takes the window's peak instead. `KVReqConfig.validate` refuses a request whose footprint is bigger than its pool with a 400 at intake, and `KVReqConfig.loop_room` cuts the default length of a request that asks for none until it fits. With every loop at 0 iterations, the same sum is the prompt a request reserves when its pool admits it.

`prompt_spans(plan, texts, text_walk, item_spans)` builds the spans of a prompt whose text and attachments, in `prefill_plan` order, are each written by their own walk, as BAGEL lays out its prompt:

```python
layout = Layout(
    spans=tuple(prompt_spans(prefill_plan(parts), segments, walk, image)),
    growth=(("decode_loop", 1),),
)
return ProcessPromptOutput(result, {
    "state_layout": {KV_CACHE: {"main": layout}, GDN_STATE: {"main": Layout()}},
})
```

`get_loop_caps(self, **model_kwargs) -> dict[str, int]` <br />
The iterations each named loop may run for this request. The conductor refuses a request whose cap is below 1 or past its loop's graph `max_iters`, or whose layout at its caps holds more positions than its pool's `max_seq_len`, with a 400. A request that sets no length has the default `max_output_tokens` cut to the context its prompt leaves, and `request_info.max_tokens` carries the cut. A model that reads a length from another key lists it in `LENGTH_KWARGS`. Speculation never runs past a cap, so the cap is the loop's budget. A model with an AR decode loop names it in the class attribute `DECODE_LOOP`, and the default `get_loop_caps` caps it at `max(1, max_output_tokens - 1)`, the prefill having sampled the first token; its stop check counts nothing. A model with other loops whose count each request knows up front (denoise steps, rollout frames) overrides `get_loop_caps` to add them, calling `super()` for the decode loop, and its stop check counts nothing either. A model whose own stop check still ends a loop at a count returns that count, so the two end the loop on the same iteration; `test/modular/test_model_kv_layouts.py` checks caps per model. Growth on an uncapped loop is counted to its graph `max_iters`.

Where `process_prompt` computes a length that a walk computes another way, such as a media item's rows, the walk asserts the two agree: BAGEL's ViT walk against `vit_patches`, Qwen3-Omni's vision encoder against the processor's grid.

Loading fails in three cases, and a request fails in two:

- A paged pool has no labels. The message is `` <Model> declares no labels for its paged pool '<key>'; add them to `kv_labels`, and return each request's layout for them from `process_prompt` ``. A ring pool needs none.
- A label's growth or keys name a walk the model never runs. The message is `<Model> declares '<key>'/'<label>' over ['<walk>'], which it never runs; its walks are [...]`.
- A label grows on a loop its walk doesn't run. The message is `<Model> declares '<key>'/'<label>' growing on '<loop>', which '<walk>' doesn't run; its loops are [...]`.
- A request's layout leaves out a label the request opens, or lays out one the model doesn't declare. The request fails with a 500, `<Model> returned no kv_layout for '<key>'/'<label>', which the request opens`, or `<Model> returned a kv_layout for '<key>'/'<label>', which it does not declare`.

A request that takes a page past its footprint logs once per label, with the layout that under-counted. A request is held only to the labels it opens, and to no pages on a label it doesn't open. A page there logs the same line, reported apart from a real overrun on that label so neither hides the other. Under `MSTAR_KV_DEBUG_ASSERTS=1` each commit is also checked against the layout: the walk that wrote each span, growth past its bound, scratch past its declaration and the retention a step declares. At removal, a label left a page or more under its footprint logs the most pages it held.

### Cross-request prefix reuse {#cross-request-prefix-reuse}

Two requests that begin with the same tokens fill the same KV pages, and the second can attend the pages the first filled instead of recomputing them. A model opts a label in by giving it `keys`, and names its checkpoint. A model with no keyed label is never cached. The deployment switch and the per-request opt-out are described under **Resource overrides** in [Serving](/serving).

`PrefixKeys(tensor, walks, growth=False)` <br />
- `tensor` names the request tensor whose entries the layout's ids spans are keyed by, as `process_prompt` returns it.
- `walks`: only a write from one of these walks keeps the keys going. A write from another walk ends them, and the rest of the label is computed, never served.
- `growth`: the ids the label's growth walk samples extend the keys, so a later request that re-sends the reply matches it too.

The keys cover the label's first `keyed_spans` spans. An ids span is keyed by its token ids, a digest span by its file. Each span is its own step unless it sets `opens_step=False`, which puts it in one row with the span before it, of the same walk (`LabelLayout.row()` fails a layout where it isn't): a match cuts the row, and the row keeps placing its own positions, so its walk declares the advance of the whole row whatever the cut left (Qwen3-Omni's prefill of text around an attachment).

BAGEL keys its text and ViT walks and the decode that follows them:

```python
return {"kv": {"main": KVLabel(
    growth=((DECODE, "decode_loop"),),
    keys=PrefixKeys("text_inputs", ("prefill_text", "prefill_vit"), growth=True),
), ...}}
```

Orpheus keys its prompt walk:

```python
return {KV_CACHE: {"main": KVLabel(
    growth=(("decode", "decode_loop"),), keys=PrefixKeys("text_inputs", ("prefill",)),
)}}
```

`checkpoint_path(self) -> str | None` <br />
Return the local directory that holds the weights and `config.json`. The cache hashes the checkpoint's safetensors index and config into the root of every key, so naming the checkpoint is what keeps two builds off each other's pages. The default returns `None`, which leaves the weights out of the root. A model without a checkpoint therefore needs `prefix_cache_salt` set to use the cache at all. Without one, the engine keeps the cache shut and logs why.

A recurrent layer can't skip tokens: its state after a token is all it keeps of the tokens before it. On a node with a recurrent state pool, a hit is cut to the longest snapshot of that state the pool holds, and the deployment gives the pool `prefix_slots` under its `resources:` key. [Prefix cache](/contributing/state-contract#prefix-cache) covers when snapshots are taken, and when the engine keeps a cache shut.

A model with a keyed label is checked at load time. Loading fails in two more cases:

- A position resource over a keyed cache uses a scheme other than sequential. A page is reusable only where its tokens land at the positions they were written at. The message is `resource '<key>' places positions by <scheme>, but it sits over ['<kv key>'], which the model keyed for prefix reuse; either drop the stream or give the resource a sequential scheme`.
- A resource on a keyed node does not set `prefix_skip_safe`, and is neither a recurrent state pool nor a resource over pools alone. A hit takes the front of the request away from every resource on the node, including resources that never saw those tokens. The message is `resource '<key>' cannot serve a request whose prefix came from the cache, but it sits on ['<node>'], which the model keyed for prefix reuse; either drop the stream or give the resource the prefix hooks`.

Some requests stay uncached even when the model keys a label. The engine cuts a prefix only from inputs that `split_inputs` can slice, so a request whose inputs carry `kwargs` or `resource_step_info` (BAGEL's guided requests carry `requires_cfg`) is never probed, and one with `tensor_inputs` only when the submodule sets `cuts_tensor_inputs` and overrides `split_inputs` to cut them. A request is not cached either when a keyed node streams into another partition it runs, since a hit would skip the rows streamed for the cached tokens. BAGEL keys an understanding prompt's text and images, and a generation's first span only when it is text, because an edit's images are resized after the digest is taken. A label under a `RetentionPolicy` files pages only up to its protected prefix.

A request on a LoRA adapter keys its pages under a root that names the adapter's weights, so the same tokens under two adapters never share pages. Nothing on the model side is needed for this ([Prefix cache](/contributing/state-contract#prefix-cache)).

A model that picks a request's adapter itself (Phi-4-multimodal runs an image prompt on its `vision` adapter and an audio prompt on `speech`) names the adapters it may pick in `Model.prompt_lora_adapters` and returns its pick as `ProcessPromptOutput.lora_adapter` (`None` for the base model; left at `KEEP_ADAPTER`, the client's choice stands). The API server refuses at startup a deployment whose `resources: lora: adapters:` block does not serve them all. The data worker then gives the request what `ServedModels.select` gives a client that names the adapter: its digest and its root, from the API server's `ServedModels`, so runtime loads and unloads apply. An adapter unloaded since startup, or one other than the adapter the client named (`None` included), refuses the request with a 400; a pick outside `prompt_lora_adapters` is a 500.

A declaration whose KV differs per request for the same tokens, such as a `LongRoPE` table picked by prompt length, keys its requests apart by itself.

## Step 2a: Declare your state {#step-2a-declare-your-state}

`declare_state(self) -> list[Array | Sampler | SeqShard]` says what each node keeps between steps, and whether its steps may split over SP ranks. The declaration says only what the model's math needs: the shape of each entry, its dtype, which earlier entries each layer reads, and what its kernels update. How the state is stored, such as a cache's page size and layout, depends on the deployment, so the engine decides it. `mstar.engine.state` is the whole surface a model imports, and its `__all__` only grows. `SubmoduleStep` imports from there too, and stays out of `__all__`, since it is the engine's own dataclass and its fields will change.

Every process calls `declare_state` and `kernel_settings`, so each must be a pure function of the model's config and the deployment's settings, with no device and no process state. Declarations are values: they hash, and changing a dict after passing it changes nothing. A declaration that follows the deployment reads it in `get_worker_graphs`, as BAGEL's nodes follow its CFG placement. Every worker and the API server check the digest of each declaration and of `kernel_settings()` against the conductor's at startup, and a mismatch stops the server, naming what differs.

An **array** holds, per request, per label and per declared layer, entries at log positions `0` to `n - 1`, with `n <= max_len`, or with no bound when `max_len` is None. An entry's index is its log position, never its RoPE position or a ring slot.

```python
def declare_state(self):
    c = self.config
    return [
        Array(
            KV_CACHE, nodes={"LLM"}, layers=frozenset(range(c.num_hidden_layers)),
            entry=KVEntry(heads=c.num_key_value_heads, head_dim=c.head_dim),
            max_len=c.max_position_embeddings,
            positions=Positions(rope=Rope(theta=c.rope_theta)),
            reads={ATTN: Read(mask=Causal(), op=Attend(q_heads=c.num_attention_heads))},
        ),
        Sampler(SAMPLER, nodes={"LLM"}, vocab_size=c.vocab_size, penalty=True),
    ]
```

The names you pass (the array's, each read's and update's, the sampler's, the sequence shard's) share one namespace. Existing models define them as module-level constants in `config.py`. A deployment YAML tunes them under `resources:` (see [Step 6](/adding_models#config-yaml)).

- `Array(name, nodes=, layers=, entry=, max_len=, reads=, updates=, rewritable=, labels=, positions=)`. `nodes` lists who may touch the array, and `layers` holds the model's own layer ids. Layer sets of different arrays may overlap. `labels` names the streams a request may open, `{"main"}` by default.
- `Entry({field: TensorType(shape, dtype=, shard=)})`: what one entry holds. Shapes are global, before sharding. `dtype=None` is the engine's compute dtype, and `shard` is the axis split across TP ranks, `None` when every GPU holds all of it. `KVEntry(heads=, head_dim=)` builds an entry of `k` and `v` sharded on their heads.
- `Read(mask=, op=, layers=, walks=)`: how a layer reads the array, one read per layer and walk. `Causal()` sees every entry up to the query's own, `Window(size)` the last `size` of them, its own included, and `Bidirectional()` every entry the row keeps and every entry this step adds for it. Reads of one attention config share one resource, and each step plans `causal` from its walk's read: BAGEL reads `kv` through `attn` (`Causal()`) on `prefill_text` and `decode`, and through `attn_image` (`Bidirectional()`) on its image and denoise walks. Loading refuses reads of two configs over one layer, a combined walk or a capture whose walks read a layer with two masks, `walks` on a cross read, and a piecewise region's step over an array whose reads name walks. A walk can't read through `Bidirectional()` or `Block()` where chunked prefill, `PrefixKeys` or a rebuild policy regroups its adds across steps. A keyed walk whose node doesn't take `PrefixKeys.tensor` (BAGEL's `LLM` on `prefill_vit`) fails a request that puts an ids span, or a digest span sharing its step, on it. `Attend(q_heads=)` is attention with the model's query heads, a multiple of the entry's heads.
- `Value(name, nodes=, layers=, entry=, updates=)`: a rewritable array of one entry, such as a recurrent state. `updates` names the kernels that read and write one of its fields in place: `CausalConv()` needs a field `conv` of shape `(channels, kernel - 1)`, `GatedDeltaNet()` a field `state` of shape `(h_v, d_k, d_v)`, and `Mamba2()` a field `ssm` of shape `(heads, head_dim, state_size)`.
- `max_len=0`: the array keeps nothing between steps, for attention within this step only. Its one read uses `Block()`, which sees only the entries of the token's own segment. See [Cacheless attention (encoder towers)](/adding_models#cacheless-attention-encoder-towers).
- `max_len=None`: the log has no bound, and the engine keeps what the reads can still reach. Today such an array takes one label and one `Window` read through `Attend`, with `packed=False` and as many query heads as the entry, over every layer. A bounded KV holds it, one slot per request ([Bounded (sink + window) caches](/adding_models#bounded-sink-window-caches)). Its read takes `distance_bias`, `(rows, q_heads, T, size)`, whose entry `d` adds to the score of the key at distance `d`, and `Positions()` is each request's count of committed entries.
- `Positions(rope=)`: a position counter per request and label, on an append-only array that keeps entries. `rope=None` is a counter only. `Rope` carries `theta`, `rotary_dim`, `interleave`, `scale`, the Llama 3.1 factors (all three or none), the rotation's `dtype` and a `table_dtype` for a cos/sin table built once. `longrope` takes a `LongRoPE`'s short and long factor sets, and a request rotates with the long set when the prompt length `process_prompt` sets under `MAX_POSITION_KWARG` passes the original context (Phi-4-multimodal). On the contract this picks the kernel, and a shared layer's `rope_*` arguments have no effect, so a port declares what its layer passed before. The counter is separate from log positions: a kept step advances it by each row's advance, a fork copies it, and a prefix hit advances it over the skipped spans.
- `Sampler(name, nodes=, vocab_size=, penalty=, min_p=, eos_ids=, draws=)`. `penalty` and `min_p` declare capabilities, not intentions: each selects which kernel variant is recorded into the captured graph. `draws` is how many draws each step that lists the sampler makes, by `sample` or `drew`. Each is a fresh draw that advances each kept row's sampling state. Log-probs and a device loop-back take one token per step, so loading refuses both above one draw.
- `SeqShard(name, nodes=, labels=, walks=, exchange=)`: the node's steps may split over its SP ranks ([Sequence and context parallelism](/contributing/state-contract#sequence-parallelism)). The engine decides per step whether the tokens of the one label in `labels` (`{"main"}` by default) split, so the shard has no step of its own. It cuts rows of one span (`packed=False`, Wan2.2 and LTX-2.5's DiTs) each row alike, and packed tokens or a segmented row (Qwen3.5, Qwen3-Omni's Thinker, MiniMax-H3's DiT) contiguously; reads that take both are refused. `walks` (`None` is every walk; a combined walk splits where a member is listed) should list only walks with many tokens a row, so decode's compiled frame traces the bracket straight through. `exchange` (`auto`, `none`, `ulysses`, `all_gather` or `ring`) is the author's default, which a deployment's `resources:` block overrides under `name`. The layer stack calls `scatter` before it and `gather` after it on the shard's handle ([Reaching your state](/adding_models#reaching-your-state)); the arrays' reads and updates exchange the rest. Loading refuses a walk the model doesn't run and a label no array on the shard's nodes opens. A node with no arrays declares a `SeqShardSpec` directly, as MiniMax-H3's video decoder does.

Qwen3.5's declaration shows both kinds of state, its sequence shard and its ViT:

```python
def declare_state(self):
    c, v = self.config, self.vision_config
    # gdn is an Entry of "state" and "conv"
    state = [
        Array(KV_CACHE, nodes={"LLM"}, layers=c.full_layer_indices,
              entry=KVEntry(heads=c.num_key_value_heads, head_dim=c.head_dim),
              max_len=c.max_position_embeddings, positions=Positions(),
              reads={ATTN: Read(mask=Causal(), op=Attend(q_heads=c.num_attention_heads))}),
        Value(GDN_STATE, nodes={"LLM"}, layers=c.linear_layer_indices, entry=gdn,
              updates={CONV: CausalConv(), LINEAR_ATTN: GatedDeltaNet(qk_l2norm=True)}),
        Sampler(SAMPLER, nodes={"LLM"}, vocab_size=c.vocab_size, penalty=True),
        # prefills may split, never decode; Ulysses, all_gather and ring are the deployment's to opt into
        SeqShard(LLM_SHARD, nodes={"LLM"}, walks={PREFILL_TEXT, *media_walk_names(self.encoders)}, exchange="none"),
    ]
    if v is not None:
        state.append(Array(VISION_TOKENS, nodes={"vision_encoder"}, layers=frozenset(range(v.depth)),
                           entry=KVEntry(heads=v.num_heads, head_dim=v.head_dim), max_len=0,
                           reads={VISION_ATTN: Read(mask=Block(), op=Attend(q_heads=v.num_heads))}))
    return state
```

A declaration today's engine can't hold fails at load, with `no layout yet` and what is missing. Every refusal names the declaration and the field.

A read with `queries=ARRAY` is cross-attention: its queries are laid out by that array's segments in this step, and each request's k-th segment on one pairs with its k-th on the other. It takes a mask that uses no query position: `Block()` on an array with `max_len=0`, and `Bidirectional()` on one that keeps entries, whose context is added on the walk that carries it and listed at span 0 afterwards. A cross read on an array that keeps entries is that array's one read, over one label, and its queries come from an append-only array that keeps entries in pages. It is refused at load on a node that splits its steps over SP ranks, and where its pool or the queried array's pool is stored by position (`context_parallel`). A `max_len=0` cross read's queries come from an array of one label, and `queries` never names the read's own array. Separate token sets are separate arrays, and arrays of one kind and geometry on one node share one resource, each under its own label.

Under sequence parallelism an array declares nothing: it splits on a step when the node's `SeqShard` lists its label and splits that step. Segments always cover the whole sequence, so `declare_step` is the same on every rank, and the read's resource picks the exchange ([the table](/contributing/state-contract#sequence-parallelism)).

A read takes its queries packed, `(tokens, heads, head_dim)` over every row. A read whose layers pass rows of one length, `(rows, len, heads, head_dim)`, as a DiT's do, declares `packed=False`, and a packed call to it is refused. A read on an array with a `max_len` above 0 takes packed queries, since the paged kernels take no others. A read on an unbounded array takes rows, each row's span first and the rest of its length padding. A read whose request's segments lie end to end in one row, as a DiT's packed rows and their pad do, declares `segmented=True`. It takes `Block()`, `packed=False` and no `queries`, and it runs one request a step. Under sequence parallelism its shard splits the whole row (`axis=0`), not each segment.

A `Value` may hold only host fields, small values a step changes, as `Entry({}, host={"eos_sent": bool})`. Each starts at its type's zero value. `host(h, request, label, layer)` reads them, and `ArrayStep(host={(row, label, layer): {field: value}})` writes them when the step commits, so the next step's `prepare_inputs` sees the write and a step that never ran changes nothing.

A `Value` with tensor fields and no `updates` holds state the model reads and writes whole per row, `Value(name, nodes=, layers={0}, entry=Entry({"tail": TensorType((8, 3), dtype=torch.float32), "count": TensorType((), dtype=torch.int64)}))`, where a shape of `()` is one scalar per entry. `h.read(layer).fields[f]` is `[rows, *shape]` in the step's row order, padding rows included, in tensors the caller owns, so a captured forward may write them in place. A row with nothing written yet, at span 0 or that pads the step reads its start: `h.set_start({f: tensor})` in `bind_state` takes tensors of one entry's shape, made at load, and zeros stand in for a field it doesn't name. `h.write(layer, **fields)` writes the rows' entries in place where the forward runs it, in an eager step or a replay, so a step refused after a write keeps it in the slots its rows already held. In a step, a layer's reads come before its write, a field takes one write, and each row at span 1 or more gets every field from the step's own write or from a piecewise region whose own step lists it. Such a `Value` takes no `keep=False` and sits on no node with prefix keys. Parakeet's transducer state and both speech codecs are the examples. Chatterbox's S3Gen keeps its vocoder tail and reference in `s3gen_stream`'s tensor fields and its generator state in a host field: `prepare_inputs` draws the chunk's noise from the state `host` returns, and the step declares the next one in `ArrayStep(host=)`, so a step prepared again after a refused admit draws the same noise.

`kernel_settings(self)` is a temporary hook for what the engine doesn't pick itself yet: `splits`, `decode_fmha` and `decode_tensor_cores` on a read of a paged array, `splits` on a `GatedDeltaNet`, and `max_segments_per_request`, `max_segments_per_step`, `compile_op` and `workspace_mb` on a `Block` read. Under an array's name it sets the default size of the array's pool, `max_num_pages` on a paged array and `max_slots` on a `Value` with tensor fields or an unbounded array, which a deployment's `resources:` block overrides. A cross read on an array that keeps entries takes `decode_tensor_cores` alone, and two reads that share a resource can't set one field to two values. It refuses anything else.

### What the engine builds {#resource-specs}

The engine builds a resource for each declaration, read and update, under the declared name, and a deployment tunes it under `resources:` by that name. [What the engine builds](/contributing/state-contract#resources) maps each declaration to its resource and the keys it takes, and [Resource notes](/contributing/state-contract#resource-notes) covers each resource's backends and limits. Two lockstep-parallel nodes on one worker must not share a paged KV pool ([Paged KV](/contributing/state-contract#paged-kv)); give each node an array of its own, or place the nodes on different workers.

Orpheus's declarations ([Example](/contributing/state-contract#example), with the Llama 3.1 `Rope` factors) build four specs for its one autoregressive node: a `KVSpec`, an `AttentionSpec`, a `PositionSpec` and a `SamplerSpec`. Its `snac_decoder` node appears in no declaration, so it receives no state.

**Which state does a node need?**

| Node | Declare |
|----|----|
| Self-attending LLM (text decode, or an LLM used as a denoiser in a flow loop) | An `Array` with `positions` and an `Attend` read. Add a `Sampler` if the node samples. |
| Decoder of an encoder-decoder model | The row above, plus a second `Array` for the encoder context with a `Bidirectional()` read whose `queries` names the first; see [Cross-attention (encoder-decoder models)](/adding_models#cross-attention-encoder-decoder-models). |
| An LLM with MLA or DeepSeek sparse attention | No declaration yet. GLM-5.2, which is unported, writes them by hand ([Legacy resource specs](/contributing/legacy-resources#hand-written-specs)); a port lands the op in `mstar/engine/state/adapters.py` first. |
| A node that carries per-request state between steps of a loop (an RNN-T decoder, recurrent attention) | A `Value` with tensor fields, read and written whole, and for a linear-attention layer stack a `Value` with a `GatedDeltaNet` or a `Mamba2`. |
| A node that samples with two different sets of parameters | Two `Sampler` declarations that both name the node, under different names. |
| An encoder tower that attends within the segments of one packed forward | An `Array` with `max_len=0` and a `Block` read, and nothing else: there is no cache to page and no counter to advance. Needed only if the tower's attention must run inside a CUDA graph; see [Cacheless attention (encoder towers)](/adding_models#cacheless-attention-encoder-towers). |
| ViT, VAE or audio encoder, codec decoder, projection stage, combine stage | Usually nothing. Declare nothing that names the node, unless the node needs the row above. |

### Two samplers on one node {#two-samplers-on-one-node}

If a node's forward samples with different parameters, declare one `Sampler` per parameter set. Both name the same node. Qwen3-Omni's Talker node needs this. The Talker LLM samples codec group 0. The CodePredictor samples groups 1 to N-1, using its own vocabulary size and no repetition penalty, `draws` times per step:

```python
Sampler(TALKER_SAMPLER, nodes={"Talker"}, vocab_size=c.talker_text.vocab_size, penalty=True),
Sampler(CODE_PRED_SAMPLER, nodes={"Talker"}, vocab_size=c.code_predictor.vocab_size,
        penalty=False, draws=c.num_code_groups - 1),
```

The forward samples through each one's handle, and the rows come from the step:

```text
layer0 = sample(self.talker_sampler, logits)
code   = sample(self.cp_sampler, logits)
```

Each sampler owns its own buffers. The two parameter sets are therefore independent, per-request, and safe under CUDA graphs.

### Cross-attention (encoder-decoder models) {#cross-attention-encoder-decoder-models}

A decoder that attends to a fixed encoder context declares two arrays that keep entries: its own self-attention array, and a second array that holds the context.

Use two separate arrays, not two labels on one. The self-attention resource plans one wrapper per label of the cache it names. If the context shared that cache, the resource would re-plan the context on every decode step. The context is large and never changes, so this work would be wasted.

Whisper (`mstar/model/whisper/`) is the reference implementation. The context array's one read is `Bidirectional()`, and `queries=KV_CACHE` lays its queries out by the self-attention array's segments:

```python
Array(KV_CACHE, nodes={DECODER_NODE}, layers=layers, entry=kv, max_len=c.max_target_positions,
      positions=Positions(), reads={ATTN: Read(mask=Causal(), op=attend)}),
Array(CROSS_KV_CACHE, nodes={DECODER_NODE}, layers=layers, entry=kv, max_len=c.max_source_positions,
      labels={CONTEXT_LABEL},
      reads={CROSS_ATTN: Read(mask=Bidirectional(), op=attend, queries=KV_CACHE)}),
```

There is no special API for writing the context. You express it in the step declaration. The prefill step declares a non-zero span on the context array's `ArrayStep`. Every later step declares a span of 0. A span of 0 reads the stream without extending it.

The encoder K and V are added once per request, in `preprocess` under `ArrayStep(eager_add=True)`, so the captured prefill is sized by its prompt alone. Each layer's `ParallelCrossAttention(context_kv_key=CROSS_KV_CACHE, layer=i)` reads the context through its handle, and its `add_context` adds the layer's K and V. Whisper's decoder calls it for each layer:

```text
for layer in self.layers:
    layer.encoder_attn.add_context(encoder_states)
```

A model with several context sources, such as "audio" and "image", declares one context array per source, and each cross-attention layer names its source's array in `context_kv_key`.

### Cacheless attention (encoder towers) {#cacheless-attention-encoder-towers}

A ViT or audio encoder attends within its own sequence and keeps nothing afterwards. Several images are packed into one forward, and each must attend only within its own span. That is varlen, or "ragged", attention: the whole layout belongs to this step, and nothing carries to the next.

Such a tower needs no state at all if it calls a varlen kernel directly, passing `cu_seqlens` as an argument. Declare an array with `max_len=0` and a `Block` read when the tower must run inside a CUDA graph. The engine builds a `RaggedAttentionSpec` from it. The plan is what makes that possible: the engine plans the layout outside the graph, into buffers whose addresses do not change, and the captured region attends through them. A kernel that reads `cu_seqlens` as an argument, or builds its mask from it, cannot be captured this way.

Which kernel runs it, and how a deployment picks another, is under [Attention within a step](/contributing/state-contract#ragged-attention).

Qwen3.5's tower is the reference on the contract:

```python
Array(VISION_TOKENS, nodes={"vision_encoder"}, layers=frozenset(range(v.depth)),
      entry=KVEntry(heads=v.num_heads, head_dim=v.head_dim), max_len=0,
      reads={VISION_ATTN: Read(mask=Block(), op=Attend(q_heads=v.num_heads))})
```

A layer adds its k and v and reads with its q, and the handle hands them to the kernel together. The add keeps nothing, so `keep=True` raises, and a read takes the add before it:

```python
self.state.add(self.layer, k=k, v=v)
out = self.state.read(self.layer, q)
```

On an array with `max_len=0` the calls add no break of their own. With `compile_op` set through `kernel_settings()`, the read stays in a compiled caller's graph, so the region keeps one graph across the attention. Without it, the read breaks at the kernel. A step declares `state={VISION_TOKENS: ArrayStep()}` over segments that are the entire layout, and a captured region names the array ([Piecewise graphs](/adding_models#piecewise-cuda-graphs-capturing-an-inner-loop)).

BAGEL's SigLIP2 tower is declared the same way, over `VIT_TOKENS`, and sets `max_segments_per_request: 1` in `kernel_settings()`, since a request has one image.

<Note>

The eager varlen path is sometimes good to have. The BAGEL ViT has a head dimension of 72, which the FlashInfer kernel, with its few fixed head dimensions, zero-pads to 128. So that tower attends through `VIT_TOKENS` only when it is replaying a captured graph, and runs flash-attn varlen otherwise.

</Note>

#### Cross-attention between spans {#cross-attention-between-spans}

A diffusion transformer whose streams attend each other (video queries over text keys, or audio over video) has several spans per request and no cache either. Declare each span as its own array with `max_len=0`, and give the array of keys a `Block()` read whose `queries` names the array of queries. LTX-2.5 (`mstar/model/ltx2_5/ltx2_5_model.py`) declares six such arrays on its DiT node:

```python
def within(name, heads, head_dim, read, label, queries=None):
    return Array(
        name, nodes={DIT_NODE}, layers=frozenset(range(t.num_layers)), entry=dit_entry(heads, head_dim),
        labels={label}, max_len=0,
        reads={read: Read(mask=Block(), op=Attend(q_heads=heads), queries=queries, packed=False)},
    )

return [
    within(VIDEO, *video, VIDEO_SELF, VIDEO_SPAN),
    within(TEXT_FOR_VIDEO, *video, VIDEO_TEXT, TEXT_SPAN, queries=VIDEO),
    ...
]
```

Each pair is planned as its own layout, pairing each request's query span with that request's key span, and cross-attention is never causal. One resource has one head geometry, so attentions that differ in head count or head dim are separate arrays.

#### Bounded (sink + window) caches {#bounded-sink-window-caches}

A streaming encoder whose frames each see a fixed left context (a conformer's `att_context_size=[left, 0]`) declares an `Array` with `max_len=None` and one `Window(left + 1)` read. The engine keeps each request's newest entries in a slot it takes on its first step and keeps: the window is a ring overwritten in place, so a step reserves and releases nothing, and rows at different positions share a batch and a captured graph. Each query attends the keys at distances `0..left` from it, so a step of several frames is causal within itself and matches the offline mask. The streaming FastConformer (Nemotron VoiceChat's `ENCODER_KV`) is the example; [Bounded KV](/contributing/state-contract#bounded-kv) has the rest.

### Per-request LoRA adapters {#per-request-lora-adapters}

A `LoraSpec` serves LoRA adapters per request over frozen base weights: each target linear adds `scaling * (x @ A^T) @ B^T` for the adapter of the token's request, so rows of one batch can run different adapters, or none. The engine owns the adapter weights. A model declares which linears adapters may touch; it never indexes the pool itself.

A model declares LoRA from its own modules: the shared linears add the delta themselves once bound, and the bridge builds the spec by walking each node's weights root. LoRA stands outside the state contract, as weights do: no request writes an adapter, a request picks one by its kwargs, and each step's rows come from its segments, so nothing per request is left for `declare_state` to hold. A model declares a `LoraRoot` for each node adapters reach in `lora_roots()`, and `declared_lora_spec` builds the one spec from them. The spec is opt-in (`NodeResourceSpec.opt_in`), built only when the serving YAML has a `resources: lora:` block. Orpheus is the reference (`OrpheusModel.lora_roots`):

```python
from mstar.model.components.lora.modules import PER_SEGMENT, LoraRoot

def lora_roots(self) -> tuple[LoraRoot, ...]:
    return (LoraRoot(
        node="LLM",
        # builds the module the node's weight loader fills, at one rank, on the
        # meta device: only once the spec is read, which a deployment without
        # a `lora:` block never does
        build=lambda group: OrpheusForCausalLM(self.config, comm_group=group),
        adapter_roots=[("", "model.")],  # adapters saved on the bare LlamaModel
        rows={"lm_head": PER_SEGMENT},    # rows that are not the step's tokens
        embeddings=True,                  # every embedding call is in the forward
    ),)
```

`root_path` is the root's attribute path in the node submodule (`"model"` by default), and `adapters` names the adapters a checkpoint ships for the root (Phi-4-multimodal's `vision` and `speech`). No model builds a `LoraSpec` itself. The state lint (`test/modular/test_state_lint.py`) refuses `get_node_resources` in a ported model, and any import in a ported model from `mstar.model.components.lora` or below but `LoraRoot`, `AdapterRoot` and `PER_SEGMENT`. It also refuses, in any model file outside the bridge (`mstar/model/base.py` and `mstar/model/components/lora/modules.py`, with `tests` folders skipped), a call to `declared_lora_spec`, `module_lora_spec` or `join_lora_specs` and a built `LoraSpec`.

The weights root states how the checkpoint lands on it once (`checkpoint_rules() -> CheckpointRules`: a prefix, a remap, the stacked-shard rules); its weight loader and `module_lora_spec` both use them, so adapters are placed exactly as weights are.

- **What takes a delta.** `ColumnParallelLinear` (and `MergedColumnParallelLinear`, `QKVParallelLinear`, `KVColumnParallelLinear`), `RowParallelLinear`, `FusedColumnLinear` and `VocabParallelEmbedding` describe their own target from their shard layout (`LoraCapable.lora_target`). Binding swaps a module to its family's twin class, which adds the delta after the base GEMM and before the module's own gather or all-reduce (after it, for the embedding) through `apply_lora(delta, x, y) -> y`. A plain `nn.Linear`, a `Conv1d/2d/3d` whose kernel is its stride, and subclasses of either that keep their base's forward are swapped alike, whole on every rank. An unbound module keeps its class, so a deployment without a `lora:` block runs, traces and guards as before. An MoE layer's `FusedExperts` is a target per parameter (`LoraCapable.lora_targets`): `experts_gate_up_proj` and `experts_down_proj`, an A and B per expert, placed by the loader's `"gate:N"` / `"up:N"` / `"down:N"` shard ids, with the deltas added after each grouped GEMM inside `FusedExperts._dispatch`. A subclass with its own `_dispatch`, and PEFT's fused 3-D experts form, are refused. Anything else holding weight matrices (a router, a depthwise conv, `nn.Embedding`, a forward overridden on an instance or hooked) takes no delta, and an adapter touching it is refused with the reason. A child its parent runs through the weight rather than its forward (folded at load, an `F.linear` over it) must be named in the parent's `lora_unservable` (path -&gt; reason): MLA's absorbed projections, SigLIP's patch embedding, Command-A+'s fused decoder-layer projections, the Qwen3 talkers' code-predictor heads. An undeclared one is bound and its delta silently never added.
- **Targets.** One per role in a layer stack (`<stack>.N.<role>`, the first `ModuleList` or `Sequential` in the path, whatever it is named; `layers` set where a role is on some layers only), named by the role's last component (`names` overrides), plus one per other module: one outside the stacks, or at a role whose entries differ in shape (UNet levels, vision stages), which is named by its path but keeps its role for `rows`.
- **What the model states.** Only what modules cannot know. `rows`: a target that sees one row per segment (`PER_SEGMENT`: a head after the last-token select) or one per `k` folded tokens. `exclude` (with a reason): modules called outside the planned step, a text projection or a conditioning encoder run in `prepare_inputs`. `embeddings=True` only when every embedding call is in the step. `adapter_roots` / `aliases` / `adapter_stacked_params`: the prefixes, names and split projections adapters write, rewritten to the checkpoint's before the root's rules place them. `ignore`: modules an adapter may carry that never run.
- **Several nodes.** A model whose adapters reach several nodes (an LLM and its vision encoder, which a TP config may put on different ranks) declares a root on each, and the bridge joins their specs into one (`join_lora_specs`): its targets name their nodes, a checkpoint module belongs to the node that places it (the one whose `adapter_roots` claim it most specifically, when several do), so one adapter file serves both, and each node gets a pool of its own (`LoraSpec.per_node`, keyed `lora@<node>`). The one `lora:` block sizes them all.
- **Binding and rows.** `NodeSubmodule.bind_node_resources` binds every module placed on its node under `root_path`, after checking it is the declared target and that the pool's shard is its rank-local shape (a module built whole on a TP node fails here, not in a forward). The pool's step is the node's own segments (`Resource.steps_from_segments`): the engine (`engine_step`) adds a `ResourceStep` of them under the pool's key, the rows its linears see, in order (a request may have several: Chatterbox's cond and uncond copies; Qwen3.5's vision encoder: one segment per frame, the merger's rows folding them). A step that lays its rows out otherwise declares its own step under the pool's key, which the engine keeps. A step that is `None` or declares no segments gets none, and an adapted module it runs refuses, so a node serving adapters returns a step with its segments wherever one runs.
- **Only inside the step.** A delta called outside a planned step (in `prepare_inputs`, or on an output cached from an earlier step) refuses, eager or compiled. The engine's warm-ups outside any step run with no adapter, so the first step with an adapter row compiles its own. A piecewise region plans its rows from its own segments per replay. A `one_row_per_step` region would address every row to the first request's adapter, so it is captured with the pool lean and replayed only for steps whose rows run no adapter; other steps run it eagerly.

What the engine builds from these roots is under [LoRA pool](/contributing/state-contract#lora-pool). Nothing there is per model.

A node whose `SeqShard` splits its steps over SP ranks (including `exchange` `all_gather` or `ring` over KV placed by position) or that runs CFG parallelism cannot serve LoRA yet, since the pool lays rows out per request over the whole batch; the deployment is refused before spawn (SP) or when the pool is built (CFG). A node on SP ranks whose steps run copied (`exchange` `auto` or `none` over KV placed by position) serves LoRA.

## Step 3: Declare the computation graph {#step-3-declare-the-computation-graph}

`get_graph_walk_graphs` returns one graph per walk. The primitives are defined in `mstar/graph/base.py`:

- `GraphNode(name, input_names, outputs)` is one unit of compute. `name` is the node name that `get_submodule` receives, and the name that declarations put in their `nodes` set. `Model.nodes` returns all such names across all walks. `input_names` lists the tensor names that must be present before the node can run. `outputs` is a list of `GraphEdge`.
- `GraphEdge(next_node, name, ...)` routes an output tensor named `name` to `next_node`. `persist=True` keeps the tensor available for later steps and walks, which is how a generated token is carried from `prefill` into the `decode` loop. `output_modality`, combined with `next_node=EMIT_TO_CLIENT`, streams the tensor to the client. Its value is one of `"text"`, `"image"`, `"audio"`, `"video"` or `"action"`. The special destinations `EMIT_TO_CLIENT` and `EMPTY_DESTINATION` are defined in `mstar/graph/special_destinations.py`. No edge flag stops a `decode` loop. A loop stops when a submodule's `check_stop` registers a stop signal against that `Loop`, for example on EOS. See Step 4.
- `Sequential([...])` and `Parallel([...])` compose subgraphs in order or concurrently.
- `Loop(name, section, max_iters, outputs)` is a subgraph that iterates. Its body feeds its own outputs back as the inputs of the next iteration. It runs at most `max_iters` times, and can stop earlier. A decode loop's `max_iters` is the model's context length, and each request's own length is its cap from `get_loop_caps`. Give the loop a `name` so that a submodule's `check_stop` can register a stop signal against it. This is the usual `decode` loop.

A minimal text generator has two walks: a `prefill` node that runs once, and a `decode` `Loop` whose body feeds its own output back as the next input.

```python
def get_graph_walk_graphs(self) -> dict[str, GraphSection]:
    prefill = GraphNode(
        name="LLM",
        input_names=["text_inputs"],
        # the generated token persists so the decode loop can pick it up
        outputs=[GraphEdge(next_node=EMPTY_DESTINATION, name="new_token",
                           persist=True)],
    )
    decode = Loop(
        name="decode_loop",
        section=GraphNode(
            name="LLM",
            input_names=["text_inputs"],
            outputs=[GraphEdge(next_node="LLM", name="text_inputs")],  # loop-back
        ),
        max_iters=self.config.max_position_embeddings,
        outputs=[],
    )
    return dict(prefill=prefill, decode=decode)
```

## Step 4: Implement the submodules {#step-4-implement-the-submodules}

Each node name maps to a [`mstar.model.submodule_base.NodeSubmodule`](https://github.com/mstar-project/mstar/blob/main/mstar/model/submodule_base.py), which is a `torch.nn.Module`. Autoregressive nodes use the `ARNodeSubmodule` subclass. The methods are:

`prepare_inputs(self, graph_walk, fwd_info, inputs, **kwargs) -> NodeInputs` <br />
Convert the routed `NameToTensorList` into a typed `NodeInputs`, or into an `ARNodeInputs` with `input_ids` or `input_embeds`. This method runs once per request. Do only cheap host-side work here: shape and length bookkeeping, building position metadata, slicing token id lists. Do not launch GPU compute here. GPU compute belongs in `forward`. The engine may call `prepare_inputs` on a different thread from the GPU thread, and much earlier than execution.

Always set `input_seq_len`, a field of the base `NodeInputs` class. The engine sums it across the batch to select a CUDA-graph capture bucket and to compute padding sizes, and `declare_step` normally computes its spans from it. Leave it at 0 only when the submodule's inputs are not sequence-shaped. If `declare_step` needs a value that `forward` does not use, put that value in `resource_step_info`.

`get_input_sequence_len(self, graph_walk, fwd_info, inputs, **kwargs) -> InputSeqLenInfo | None` (optional) <br />
Return the length of the row's whole input, before any cached prefix is cut; the engine subtracts what the prefix cache already holds. Return `None` for a walk that declares no length, or when the inputs it would measure are absent. Read off input shapes alone: this runs before `prepare_inputs`.

`speculative_input_seq_len(self, graph_walk, fwd_info, prev_seq_len) -> int | None` (optional) <br />
Estimate the length of a row continuing from the step in flight, before that step's outputs reach it; `prev_seq_len` is its length in that step, or -1 if it ran on another node. The default repeats `prev_seq_len`. Only an estimate: it sizes the token budget left for the rows a speculation merges in beside it. A walk with a fixed length (one token a decode step) should return it.

`declare_step(self, graph_walk, request_ids, inputs, slot_lease=None, piecewise_leases=None, per_request_info=None, **kwargs) -> SubmoduleStep | None` <br />
Declare what this batch's step does to the node's resources. See [Step 4a](/adding_models#step-4a-declare-the-step) below.

`preprocess(self, graph_walk, engine_inputs, inputs) -> dict` <br />
Collate a list of `NodeInputs` into the keyword arguments that `forward` expects. The default implementation handles batch size 1. Override it to support batching. `ARNodeSubmodule` declares this method abstract, because autoregressive submodules normally support continuous batching. You can still disable batching for one node, or for specific graph walks. See [Step 5](/adding_models#step-5).

`forward(self, graph_walk, engine_inputs, **kwargs) -> NameToTensorList` <br />
The tensor-to-tensor computation. The keys of the returned dict are the edge names that the graph routes downstream. Reach declared state through handles. See [Reaching your state](/adding_models#reaching-your-state).

The engine applies `torch.compile` to both `forward` and `forward_batched`, for every submodule, and captures graphs when you declare capture configs ([Step 5](/adding_models#step-5)). `disable_torch_compile = True` turns compilation off for a submodule. An encoder whose output feeds a prefix cache layout walk compiles with dynamic shapes, unless it marks every varying dimension with `torch._dynamo.mark_dynamic` in `prepare_inputs` and sets `marks_dynamic_dims = True`. The engine raises the recompile limit past `MSTAR_RECOMPILE_LIMIT` to hold one entry per captured bucket; a submodule whose frames keep several entries per bucket (GLM-5.2's decoder layers, traced once per layer kind) declares how many as `compiled_entries_per_shape`. A ported package adds no `torch.compiler.disable` of its own ([Reaching your state](#reaching-your-state)). A submodule that disables the whole-forward compile returns the parts to compile from `compile_regions()`: attribute paths (a module or a method) mapped to example arguments. The engine compiles them on an accelerator before capture, with dynamic shapes and the default mode; a part that needs static shapes, another mode or `fullgraph` compiles in model code. Qwen3.5's vision encoder and Omnilingual ASR are examples.

Some submodules must run in their own parameter dtype. One example is an fp32 vocoder that is numerically sensitive. Such a submodule sets `disable_autocast = True`. The engine then does not cast its parameters to the autocast dtype, does not wrap its forward in autocast, and explicitly disables any enclosing autocast.

The engine runs float32 matmuls as TF32 in every process (`torch.set_float32_matmul_precision("high")`). A node that needs full fp32, for example a flow solve that amplifies TF32 rounding, sets `float32_matmul_precision = "highest"`, and `cudnn_allow_tf32 = False` for cuDNN convolutions and RNNs. The engine applies these around that node's forward, its compile and its CUDA-graph capture, and restores the default afterwards, so other nodes keep TF32. `None` (the default) keeps the process setting. Don't flip `torch.backends` flags in model code: they are process-wide, and a CUDA graph keeps the precision it was captured with. The setting covers `forward` and `forward_batched` only, not `preprocess` or `postprocess`. It can also be set per instance in `__init__`, for example only when the model loads in fp32.

A node whose captured convolutions are faster with cuDNN's timed algorithm choice sets `capture_cudnn_benchmark = True`: the engine turns `torch.backends.cudnn.benchmark` on around that node's capture sizing only, so each captured shape is searched once, and eager steps keep the heuristic pick (Kokoro is an example). The search tries workspaces as large as the GPU has free, so on a deployment that sets `gpu_memory_fraction` the engine holds the allocator to that share while it sizes the node's captures, and the boot fails if the node's largest eager step does not fit in it beside what the worker already holds.

`postprocess(...)` (optional) <br />
Metadata-only fixups that run on the GPU thread. This method must not read tensor values. Do not call `.item()`, `.cpu()` or `.tolist()` here. This is a performance requirement, not a correctness requirement. Reading a value forces a host synchronization, which stalls the GPU thread and loses the worker's asynchronous scheduling overlap. Use this method only to rename outputs for routing. Put decisions that depend on tensor values in `check_stop`.

`check_stop(...) -> set[str] | StopCheck` (optional) <br />
Runs off the GPU thread, and may read tensor values. Return the names of the `Loop` objects to stop, for example after seeing the EOS token; this is how a decode loop ends. The token budget is the loop's cap from `get_loop_caps`, not a stop check. An AR submodule whose loop ends on a stop token sets `self.token_stop = TokenStop(...)` in `__init__` instead, which also gives it `check_stop_batched` over one host copy of the step's tokens (Qwen3.5's `LLMSubmodule`). A decode walk can keep its sampled token on the device with a `DeviceLoopback` ([Device loop-back](/adding_models#device-loop-back)).

A prefill samples the first token before its decode loop exists, so a stop there returns `END_PARTITION` (from `mstar.model.submodule_base`): the conductor ends the partition rather than start decode. Return it only from a row outside any loop. `TokenStop` does this for its `prefill_walks`, whose token counts toward the budget, and only on the pass its `last_prefill_flag` names (`FINAL_PREFILL` for `SampledTokenDecoder`). `END_PARTITION` ends the partition whatever its plan has left, so a model that runs another walk after its loop (an `align` walk, image generation after thinking) or publishes final-only state at the stop must not return it there. A `check_stop_batched` you write must agree with `check_stop`.

`StopCheck(stops, withheld=(names...))` (`BatchedStopCheck` from `check_stop_batched`) also keeps some of this step's outputs from being routed, such as a frame streamed beside the EOS token: the Qwen3-Omni Talker and Fish S2 Pro's AR keep their EOS frame out of the codec stream this way, and a `TokenStop` names such outputs in `withhold` (the Qwen3-TTS Talker). Only an output that leaves by a streaming edge can be withheld, not one a node this worker speculates into reads, nor the loop-back signal. Startup checks `TokenStop.withhold`, not a `StopCheck`.

`on_request_added(self, request_id, request_info)` (optional) <br />
Called on the worker's main thread when the request reaches the worker, before any of its steps, with the request's first `CurrentForwardPassInfo`. For host work worth starting early on a thread of the submodule's own; it must not touch the device. The DiT scaffold draws a request's seeded noise here (`PREFETCH_SEEDS`).

`get_stop_policies(self, graph_walk) -> dict[str, StopPolicy] | None` (optional) <br />
Declare what `check_stop` amounts to on a walk, per loop, when it is only the common checks; the graph runtime then runs them over the step's token column, from the stop buffer the batched output carries (`BatchedModelOutput(check_stop_buffers={...})`, as Qwen3.5 and Orpheus return), without calling `check_stop`. A step without that buffer, or one that mixes walks, still calls it. `StopPolicy(StopKind.AR, token_signal=..., eos_tokens=..., sampler=...)` stops on an EOS token (unless the sampler's request config sets `ignore_eos`) or when the iteration count plus one reaches `max_iters` (`info.max_tokens` unless given); `StopKind.ITER` checks only the count and `StopKind.EOS` only the token. `ignores_eos=` replaces `sampler` on a node without one: a callable on the forward-pass info. Return `{}` for a walk where `check_stop` never stops a loop, and `None` (the default) to keep calling it. The policies must agree with `check_stop` (`test/modular/test_stop_policies.py`). A `TokenStop` with `runtime_check=True` declares them for you on its `walk`.

`cleanup_request(self, request_id)` (optional) <br />
Free per-request state held inside the submodule when a request finishes: buffers, per-request caches, counters. See Qwen3-Omni's `Code2WavSubmodule` for an example.

`filter_batched_output(...)` and `unpack_packed_outputs(...)` (optional) <br />
Output fixups that run after the forward. A captured forward always emits the same set of keys, because the graph shape is fixed. Use `filter_batched_output` to drop keys that a particular request must not receive. Use `unpack_packed_outputs` to slice a packed `(total_tokens, ...)` tensor into per-request entries, when the slice boundaries depend on the real sequence lengths and therefore cannot be computed inside the captured region. Both methods are defined on `NodeSubmodule`, so any node can use them.

`spanned_outputs(graph_walk) -> frozenset[str]` (optional) <br />
Outputs whose valid length per row is known only on the device, such as audio with silence to trim. `forward_batched` returns a `BatchedModelOutput` whose `output_spans` maps each declared output to a `[bs, 2]` int64 device tensor: row `i`'s first and one-past-last valid index along the last dimension. The forward keeps a fixed width and does no host read; the worker cuts each row to its span (a view) after the step completes, before the stop check, transport or a stream reads it. Engine-side `postprocess` sees the uncut output. A row with an empty span is dropped as a withheld output is. A spanned output must not feed a node that the same worker speculates into.

Two more methods control batching and graph capture: `can_batch` with `forward_batched`, and `get_accelerator_graph_configs`. They are described in [Step 5](#step-5).

**Chunked prefill (optional).** A walk with long prompts can run each across several steps, at most a token budget per step, so the decode rows batched beside it keep running. Each chunk is one iteration of a Loop around the node, which counts the tokens its chunks ran and ends at the prompt's length. To opt a walk in:

- `Model.get_chunking_policies()` returns `{node: (ChunkingPolicy, ...)}`, each policy naming the `walks` it covers. It is declared on the model, not the submodule, because the graph build reads it: `Model` wraps each chunkable node in its Loop wherever `get_graph_walk_graphs` is read, so the model returns its walks as usual. The fields:

  - `chunkable=True` lets the walk's rows be cut.
  - `max_batch_tokens`: the most tokens a step runs. A combined walk that carries chunked rows sets one too, since its steps run under it. Its step may pass it beside a speculation chain's decode rows, by at most those rows' tokens, and the engine trims a serving config's `prefill_token_buckets` assuming each such row runs one token. A walk whose decode rows run more (an MTP verify row's k+1) passes that bound, and its steps past a trimmed ladder's top run eagerly.
  - `accumulated_outputs`: output edges a consumer needs every chunk of. They arrive as one item per chunk, all when the prompt finishes.
  - `per_chunk_outputs`: streaming edges sent on every chunk as it runs, for a consumer that can start on a prefix. Any edge in neither set carries the final chunk's output alone.
  - `reuses_cached_prefix`: a callable saying whether a row may start past its cached prefix; `None` (the default) is always. Set it where a row may have to write its prefix again.
  - `reserve_whole_prefill` (default on): a row's first chunk reserves the state its whole prefill needs, so a part-done row cannot wedge on a full pool. Turn it off for a walk whose state grows by something other than the tokens a step runs.

  A resource that keeps state only on a grid counted from a chunk's start declares `Resource.chunk_alignment`, and a cut chunk of the node's rows is then a multiple of every alignment its resources declare (`Engine.chunk_alignment`). The chunk floor rounds up to it, and a budget under it fails loading.

  A streaming consumer of an accumulated edge whose `ChunkPolicy` expects one item (`FixedChunkPolicy(1)`, say) sets `Connection.join_dim`, so its `StreamBuffer` joins the pieces into that item. A consumer that can take the pieces as they come says so with `ChunkPolicy.allow_partial_input` (`FixedChunkPolicy(allow_partial=True)`), and the producer then sends the edge per chunk, as Qwen3-Omni's Thinker does into its Talker. A chunked stream its consumer would misread, each piece taken for the whole input, is refused at startup.

- `get_input_sequence_len(graph_walk, fwd_info, inputs)` gives a row's length from its input shapes, before `prepare_inputs` runs. The scheduler cuts the row by it, and a row whose prepared input turns out another length fails.

- `split_inputs(graph_walk, fwd_info, inputs, start, end)` cuts the whole prepared input to tokens `[start, end)`. `ARNodeSubmodule`'s default cuts the token ids or embeddings and any custom position ids, and refuses inputs it cannot see into (`tensor_inputs`, `kwargs`, `resource_step_info`).

Each chunk is a full forward, so it samples a token, but only the final chunk's token is real (`inputs.is_final_chunk`). The model need not handle that: the sampler commits no RNG offset or seen token for a row mid-prefill (it reads `StepContext.chunk_tokens_after`), the Loop carries only the final chunk's outputs, and the worker takes no stop or prefix key from a non-final chunk. `test/modular/test_chunked_prefill.py` and `test/modular/test_bagel_chunked_prefill.py` show how to test a chunking model. A deployment can change the budgets (see *Chunked prefill budgets* in [Serving](/serving)).

### Step 4a: Declare the step {#step-4a-declare-the-step}

`declare_step` tells the engine what one batched step does to the node's resources: which cache streams it touches, how much each stream grows, what the attention plan is based on, which streams fork, and what is committed after the forward completes.

The runner calls the declaration and the resource lifecycle around your forward:

```text
declare_step()  →  admit  →  plan  →  preprocess  →  forward  →  commit
```

The runner owns this lifecycle. A submodule that declares a step must therefore contain no plan calls and no advance calls of its own.

Declaring the work also lets the worker handle a cache that is full. If a step cannot be admitted, the engine returns an admit failure. The scheduler can then apply backpressure and evict other requests. Without a declaration, the same situation raises a `RuntimeError` inside the forward.

Returning `None` declares nothing for the step, as the outer declaration does while a piecewise region holds its own lease (**Splitting the declaration** under [Step 5](#step-5)).

A walk named in `resident_walks()` runs its captured steps off per-request tables on the device instead of a plan rebuilt per step (`mstar/engine/resources/resident.py`). The walk declares, for each resource, one stream that takes one token per row, or one it only reads at span 0 (a cross-attention context), with no forks, retention or sink, and its `preprocess` reads no planned position or KV location, since the captured graph fills those in. Capture raises on a declaration that breaks this. The engine turns it on only if every resource of the node can (`Resource.resident_refusal`) and `knobs: resident_planning` is `auto`; the worker log says why otherwise. A resource shared with nodes that plan on the host is fine; one shared with another resident or lockstep node is refused, and so is a GDN layer on a node whose steps can split. Steps of other walks and eager steps keep the host plan, and the next resident step rewrites the row. The sampler's per-request scalars (temperature, top-k, top-p, seed, penalties) become cells of the row; the RNG offset, last token and penalty mask stay in the sampler's own row.

A `SubmoduleStep` contains a list of `Segment` objects and, under `state`, what the step does to each array and sampler it touches. The engine expands `state` into one `ResourceStep` per resource, so nothing downstream changes:

- `Segment(request_id, label, span)` is one request's contribution to one label in this step. `span` is how far the row advances on that label: an append-only array adds that many entries, and a Value folds that many positions into its one entry. A `span` of 0 reads the array without extending it. Under `max_len=0` each segment is one block.
- `ArrayStep(segments=, keep=, forks=, placeholders=, eager_add=, fixed_layout=, advance=, position_ids=)`. A step lists every array it touches, and a call on one it doesn't list raises. `segments` gives one array its own spans, `None` being the step's. `keep=False` makes every add this step scratch. `advance` moves each row's position counter by something other than its span, for a prompt whose grid covers fewer positions than tokens, and `position_ids` passes explicit ids.
- `SampleStep(apply_penalty=, apply_filters=, prompt_tokens=, kept_rows=)`. `prompt_tokens` initializes the repetition-penalty mask with the prompt tokens. Only the prefill step passes them, because the sampler tracks every token it samples afterwards. `kept_rows` names the rows whose draw counts, `None` being every row. A dropped row still draws, but its RNG offset and seen-token mask don't advance. `apply_filters=False` samples a step with top-k/top-p off (e.g. a TTS's first code); declare it the same way on every step of a walk.
- Reads and updates need nothing in the step, because the declaration says which read each layer uses in each walk.

The simplest form uses one label and computes spans directly from the prepared inputs. Command A+'s LLM node inherits it: `SampledTokenDecoder.declare_step` builds the segments and `DeclaredTokenDecoder.node_step` the state (`mstar/model/components/sampled_token_decoder.py`), and the snippet folds the two together:

```python
def declare_step(self, graph_walk, request_ids, inputs, **kwargs):
    return SubmoduleStep(
        segments=[
            Segment(request_id=rid, label="main", span=inp.input_seq_len)
            for rid, inp in zip(request_ids, inputs, strict=True)
        ],
        state={
            KV_CACHE: ArrayStep(),
            SAMPLER: SampleStep(prompt_tokens={
                rid: inp.input_ids for rid, inp in zip(request_ids, inputs, strict=True)
            } if graph_walk in PREFILL_WALKS else {}),
        },
    )
```

**Padding rows.** Under a captured graph, the batch is padded to the shape of the capture bucket, and `request_ids` also contains the ids of the padding rows. Declare segments for those rows in the same way as for real rows. The `zip(..., strict=True)` in the example above already does this.

**The two leases.** `slot_lease` is the CUDA-graph slot on which this step will replay. It is `None` for an eager step. If a submodule's declaration differs between the captured case and the eager case, it must check the lease, not its own capture key. The capture key only says that the batch could be captured. The lease says that the batch was captured. For example, Cosmos3 packs both guidance branches into a single plan for the captured shape, and uses the dense backend otherwise.

`piecewise_leases` names the inner regions of this node that hold their own slot for this step. Such a region declares, plans and commits its own work. Any resource that the region owns must therefore be excluded from the outer declaration. See [Piecewise graphs](/adding_models#piecewise-cuda-graphs-capturing-an-inner-loop).

**Advanced `ArrayStep` fields.** BAGEL and Whisper use these:

- `keep=False`: the step reads and plans, but its writes do not become resident yet. `keep=False` on a Value with updates is refused for now, because its kernels write in place.
- `forks`: `Fork(src="main", dst="cfg_text", at=...)` forks one label from another. `at="start"` forks before any planning or writing, for a branch that must keep the context from before this step. `at="end"` forks at commit time, for a branch that must include this step's writes. `rows` limits the fork to some rows, and today a step's forks must all name the same rows. A fork shares the prefix of an append-only array and copies a Value's entry.
- `placeholders`: `(row, label)` pairs that hold a place but read and keep nothing.
- `eager_add=True`: the step's adds run outside any captured graph, for example in `preprocess` before the replay. Their addressing stays an ordinary plan rather than the slot's static buffers, which are sized for the bucket's in-graph tokens. Whisper's prefill uses it to write its 1500-token encoder context while replaying a graph sized by its few prompt tokens. The reads of such a step attend the pages alone, so one that needs the step's own k and v (an attention through an exchange, a context-parallel pool on a multi-token step, the dense backend) is refused at the first add.
- `fixed_layout=True`: every replay of the step's capture bucket lays its rows out as the capture did, so a ragged self-attention may capture a kernel that bakes the layout in (cuDNN). A resource's step takes it only if every read on the resource declares it.

A step's segments may name several of an array's labels, label-major: every row's first label, then every row's second. The engine plans them as one plan, named by joining the labels with `+`, which a declared label can't hold. Every call covers every segment in segment order: `at_last_token(h, x)` gives each (row, label)'s last token in that order, and `at_last_token(h, x, label=L)` label `L`'s rows in row order. On an array that keeps entries a row has one segment per label a step. A Value takes one label a step, and a cross read's queries come from one label. The one plan is for every array on KV pages, so a step that packs labels on one paged array lists the node's other paged arrays on the same labels, and the engine refuses a step that lists one on other labels. Chatterbox's guided T3 steps and BAGEL's guided text steps and denoise are the examples: Chatterbox combines its guidance from every (row, label)'s last token, and BAGEL samples from `label="main"`.

**Writing K/V yourself.** A layer that writes its K/V inside a fused kernel of its own learns where the step's tokens go from a `@state_op`'s `target` ([Reaching your state](#reaching-your-state)), as `qk_norm_rope_attend` in `mstar/model/components/qwen3_lm.py` does.

**Testing.** `declare_step` performs only host-side bookkeeping, so you can unit-test it on CPU without model weights. `test/modular/test_state_ports.py` compares both ports' steps against hand-written ones, and `test/modular/test_resource_runner.py` tests the runner's lifecycle directly.

### Reaching your state {#reaching-your-state}

The engine binds one handle per declared array, sampler and sequence shard. `bind_state(self, handles)` receives them by declared name, on the submodule and on every layer that defines it:

```python
class LLMSubmodule(ARNodeSubmodule):
    def bind_state(self, handles):
        self.kv = handles[KV_CACHE]
        self.sampler = handles[SAMPLER]
```

An array's handle has three calls. `layer` is always the model's layer id as declared, and each row's label comes from the step's segments, so there are no cursors:

```python
st.kv.add(layer, k=k, v=v)                # kept
st.kv.add(layer, k=k, v=v, keep=False)    # scratch
out = st.kv.read(layer, q)
st.mem.write(layer, state=x)              # rewritable arrays only
```

- `add` appends each row's span at its next log positions. A kept add happens at most once per layer per step, and it is the layer's last add. Scratch adds can repeat, and last until the next add or the end of the step. `keep=None` takes the step's `keep`. The resources keep or drop a step's adds as a whole, so a step that keeps needs each layer to end on a kept add, unless every row it lists has span 0, is a placeholder or got its adds from a piecewise region whose own step lists it, and a step with `keep=False` refuses `keep=True`.
- `read` sees kept entries from earlier steps, plus this layer's latest add, at the positions its mask reaches. It runs the op the declaration names for the layer.
- `write` sets the step's rows' entries in place where the forward runs it, not at the step's commit.

These raise, naming the array and the cause: a call on an array the step doesn't list or on a layer it doesn't declare, an add after a kept add, a kept add after a read in the same layer, and `write` on an append-only array. The checks run in eager steps and at capture, so graph replays skip them. On an array with `max_len=0` a compiled block skips them too, since a check there would guard on the layer.

The rest are free functions in `mstar.engine.state`:

```python
out  = add_read(self.kv, layer, q, k=k, v=v)                            # add, then read, behind one break
qkv  = causal_conv(self.gdn, layer, qkv, weight=w, bias=b)              # reads and writes `conv`
core = gated_delta_net(self.gdn, layer, q, k, v, a, b, A_log, dt_bias)  # reads and writes `state`
y    = mamba2(self.ssm, layer, x, dt, b, c, A_log, D, dt_bias)          # reads and writes `ssm`
p    = position(self.kv, fwd_info.rid_handle, label)                    # a request's next position, on the host
ids  = positions(self.kv)                  # this step's ids, on the device
q, k = rope(self.kv, q, k)                 # rotate at this step's ids with the declared Rope
tokens = sample(self.sampler, logits)      # one token per row, each a fresh draw
last = at_last_token(self.kv, hidden)      # each row's last token in this step
ids  = last_sampled(self.sampler)          # each row's last sampled token, for a DeviceLoopback
x, cos, sin = scatter(self.shard, x, cos, sin)  # this rank's share where the step splits, else as they are
hidden = gather(self.shard, hidden)        # every rank's share, back whole
mine = split_range(self.shard)                 # this rank's range (start, count, counts), None where copied
ranks = self.shard.ranks                   # the SP ranks a layout must tile over
```

The shard's handle is opened on every step of its node and takes the label it brackets from the step's segments and the walk from the step, so the calls name neither. Both are the identity on a copied step, at one SP rank and outside a step.

A layer with nothing traced between its `add` and its `read` calls `add_read`, since two breaks compile a frame for the gap on every shape. It runs both calls' checks in their order, and refuses an array with `max_len=0`, whose calls a compiled block traces. Call it from the frame the layer compiles: a break inside a method that frame calls compiles that method as a frame of its own.

On an array that keeps entries, every call that touches state breaks the compiled graph and runs eagerly, so model code adds no `torch.compiler.disable` of its own. A layer stack calls `run_layers(..., no_cursor)`, which runs its loop eagerly and compiles each layer's frame once, and the forward around it takes `@eager_frame` when it does no tensor work of its own. So that one frame serves every layer, a compiled layer passes its layer id as a 0-d int64 CPU tensor, held as a plain attribute, not a buffer. An eager caller can pass the int.

`kernel_setting(h, read, field)` reads a `kernel_settings` field in effect, YAML included. It is temporary, with that hook.

A kernel that writes state itself, in one launch with the math before it, is a state op. It names what it touches, the formats its kernel can address, and a reference over the contract's calls, which any other format runs:

```python
@state_op(adds=("kv",), reads=("kv",), mutates=("q",), formats=(PagedNHD(devices={"cuda"}),),
          reference=_reference)
def attend(kv, layer, q, k, v, *, target: PagedNHDTarget):
    ...                                      # write k and v at target, and change q in place
    return kv.read(layer, q)

out = attend(self.kv, self.layer, q, k, v)  # the layer's add, then its read, behind one break
```

`reads` may name only the array in `adds`, and the call refuses an array with `max_len=0`, as `add_read` does. The engine picks the kernel or the reference at bind, and a step whose reads attend its own `k` and `v` (a context-parallel pool's multi-token step) runs the reference. `target` says where this step's entries go on the layer. A conformance test holds each kernel to its reference on each listed format, what it returns included, and `MSTAR_KV_DEBUG_ASSERTS=1` checks that an eager call writes nothing outside the step's slots.

Between steps, a model may keep a memo of a pure function of request inputs, whose loss costs time and changes no output, and scratch buffers that it makes at load and that no step reads before writing. Anything else it keeps between steps is declared state or an edge. This rests on the engine running a node's forwards one at a time, in stream order. The diffusion loop's schedule and prefetched seeds are memos, its latents and solver state are loop-back edges, and a code predictor's frame-local KV is scratch.

A model on the contract reads no `node_resources`, `engine_inputs.resources`, `request_state` or `per_request_states`, imports the engine only through `mstar.engine.state` and defines no `bind_resources`; `test/modular/test_state_lint.py` holds each ported package to that. Qwen3-TTS's `batch_postprocess` keeps the opt-in watermark's per-stream state in `request_state` under one named lint exception, until it moves to a watermark node's plain Value.

`ModelInputsFromEngine` carries five other useful fields:

- `step` is this step's `SubmoduleStep`. A forward that must match its own declaration reads it here instead of computing the same information again.
- `captured` is true when this forward runs under a graph capture or replay. It is useful when `preprocess` packs its inputs differently for the fixed capture shape.
- `synthetic` is true when every row is a dummy request, during CUDA-graph capture or its warmup. Use it to keep statistics such as routing counts free of dummy traffic.
- `real_seq_len` is the token count of the real requests. Their rows come first; any rows after them are padding that a replay adds to reach the bucket shape. It is `None` when nothing was padded, so every row is real. Read it instead of assuming anything about the padding rows' own inputs.
- `piecewise_runners` holds the piecewise graph runners, keyed by region name.

The shared layers take their layer id in the constructor. `ParallelGatedDeltaNet` takes a handle, and `Attention`, `ParallelAttention` and `VisionAttention` pick their path at bind from what they receive: a handle under their key, or the resources an unported package binds.

<a id="device-loop-back" />

**Device loop-back.** A decode loop normally routes its sampled token back to itself as a tensor per request. An AR node that sets `self.device_loopback = DeviceLoopback(walk, signal, sampler, buffer)` instead reads each row's last sampled token off the sampler on the device (`MSTAR_DEVICE_LOOPBACK`): the base class's `device_loopback_signals` names the signal, so the worker routes it without a tensor and sends the client's copy inline, `prepare_inputs` returns `self.uniform_row_inputs(...)` for such a row, and `preprocess` reads the tokens with `self.loopback_inputs(engine_inputs, inputs)`. A row whose last step did not keep its value on the device (its first decode step, after the prefill) still brings it routed, and that read puts it over the slot's. `SampledTokenDecoder` declares it for Qwen3.5, Muse Glimmer, Higgs Audio, Qwen3-ASR and the Cosmos3 reasoner, and a node on it that reads the routed token sets `device_loopback = None`; Whisper and Qwen3-Omni's Thinker declare their own. A node on `DeclaredTokenDecoder` and Whisper's decoder read the tokens with `last_sampled`, and put a row's routed token over its slot's with `splice_loopback_ids`. Its `walk` may be a `frozenset` of walks when several decode walks read the token back; a combined step's rows each follow their own walk, and naming a combined walk is refused at startup.

A token that also streams to another node can go down the stream by value, when the stream's `Connection` sets `by_value=True`: its consumer then takes a window of the stream as one CPU int64 tensor of its items' values. A step whose node names the signal in `inline_signals(walk)` sends each row's value in the step's `EDGE_ITEMS` frame instead of a tensor, with nothing to stage, read or acknowledge. A step carries one inline column: the first of those signals it outputs, and every other it outputs that reads the same stop buffer, so a client token and a stream of the same token both ride inline; a signal read off another buffer keeps its tensors. A row whose stop check withheld one of them (`StopCheck.withheld`) sends nothing for it, and its stream counts no item. The step keeps its rows on the device when every output is one of `device_loopback_signals` or rides the column on every edge (a client emit or a `by_value` stream, neither persisted, no non-streamed edge counted toward the conductor's output tokens, and not collected by an enclosing loop): MiniCPM-o's TTS decode loops its code back on the device and streams the same code to the vocoder by value. A rows-only step builds no per-request outputs and skips `postprocess`, so whatever a submodule's `postprocess` does must be about the outputs a stored step routes. A lockstep node's streams keep their tensors, and a `by_value` connection cannot join its items, drive its consumer's walk or come from the client.

On such a node a captured step writes each row's token and RNG offset back to the request's row inside the graph (`knobs: sampler_ingraph_scatter`, on by default). Those rows are allocated once, `knobs: sampler_slots` of them, so a request takes its row when the runner admits it and waits while none is free, as it does for a recurrent state slot. A row the step drops (`SampleStep(kept_rows=...)`) writes the trash row, so it keeps its offset.

State that a decode loop carries from step to step beside the token is a `Value` with tensor fields, which the forward reads and writes each step, captured or not. Whisper's `decoder_state` holds its timestamp rule row and its transcript.

A kernel in the forward can draw its rows' tokens itself, as Qwen3-TTS's depth-loop kernel does for fifteen draws a step. `fused_draw_args(s)` returns the step's per-row temperature, top-k, top-p, seed and offset, in the step's row order, padding rows included. The kernel draws row `r`'s `i`-th token with `draw_row(..., seed[r], offset[r] + i, ..., LAY=draw_row_layout())`, imported from `mstar.engine.state`, which picks the token `sample` would and consumes one draw from the row's random stream, as one `sample` call does. After the launch, `drew(s, n)` counts `n` draws toward the sampler's `draws` and moves the offsets. `fused_draw_args` returns None when `sample` would do more than that draw (an eager step, the penalty, min-p, logprobs, a kept last token, a TP, SP or CFG node) or the declared vocabulary is above 2048, where `fused_sample` leaves the layout `draw_row` assumes; the model then calls `sample`. These calls and `FusedDrawArgs`, the tuple `fused_draw_args` returns, stay out of `mstar.engine.state.__all__`, so they can change until a second model draws in place.

### Loading weights {#loading-weights}

`get_submodule` loads a node's parameters. Weight loading is standardized through `mstar/model/loader/`. Use it instead of a custom `load_state_dict` call. Only then can the same code load both a single-GPU checkpoint and a tensor-parallel shard. See [Step 6](/adding_models#tensor-parallelism). There are three layers:

1.  In `get_submodule`, build the `nn.Module` on the `meta` device, materialize it with `to_empty(device=...)`, then call `load_weights(module, source, device=...)` from `mstar.model.loader`. This function selects the correct safetensors iterator, for a single file or for a sharded Hugging Face directory, and then calls `module.load_weights(weights)`.
2.  Your module implements `load_weights(self, weights)` and delegates to `load_hf_weights(self, weights, stacked_params=..., name_remapper=...)`. That function streams the `(name, tensor)` pairs and dispatches each pair to the `weight_loader` of the matching parameter.
3.  `stacked_params` is a list of `StackedParamRule`. Each rule routes several checkpoint keys into one fused parameter, for example the Hugging Face `q_proj`, `k_proj` and `v_proj` keys into a single `qkv_proj` parameter. `LLAMA_STACKED_PARAMS` is a predefined rule set for Llama models. `name_remapper` rewrites or drops checkpoint keys that do not match your parameter paths.

```python
# in the Model: build on meta, materialize, hand off to the driver
def _create_llm_submodule(self, device, tp_group=None):
    from mstar.model.loader import load_weights
    with torch.device("meta"):
        language_model = OrpheusForCausalLM(self.config, comm_group=tp_group)
    language_model.to_empty(device=device)
    load_weights(language_model, local_dir, device=device)  # → module.load_weights(...)
    ...

# in the nn.Module: declare the fused-shard routing and delegate
def load_weights(self, weights):
    from mstar.model.loader import LLAMA_STACKED_PARAMS, load_hf_weights
    return load_hf_weights(self, weights, stacked_params=LLAMA_STACKED_PARAMS)
```

Each parameter's `weight_loader` also performs tensor-parallel sharding. When the module is built with a `comm_group` and `tp_world_size > 1`, the loader slices the incoming tensor along that parameter's shard dimension before copying it. For this reason, one `load_weights` path serves both single-GPU runs and tensor-parallel runs without change.

A quantized checkpoint is refused at load unless the model reads its format itself. Without this, a model that knows only unquantized weights would load fp8 values unscaled and drop the scales and packed weights, and then serve garbage. There are two checks:

- The safetensors iterators refuse a checkpoint that declares a quantization: `quantization_config` in `config.json` (HF fp8, AWQ, GPTQ, bitsandbytes, mxfp4, compressed-tensors, ModelOpt), ModelOpt's `hf_quant_config.json`, or AutoGPTQ's or AutoAWQ's config file.
- `load_weights_into` refuses a quantized weight's part, such as `weight_scale_inv`, `weight_scale`, `weight_packed` or `qweight`, when no parameter takes it.

A model that loads a format itself names its `quant_method`. GLM-5.2 and GLM-5.3-Flash, for example, pass `quant_methods=("fp8",)` to `load_weights` and to the iterators.

## Step 5: Continuous batching and accelerator graphs {#step-5}

Continuous batching and accelerator graphs are the two main throughput optimizations. Both are optional. For an autoregressive node, you normally want both.

**Continuous batching.** The worker's micro-scheduler groups compatible in-flight requests into one GPU call. A submodule controls this behavior with these methods:

- `can_batch(self, batch: ExecutingBatch, model_inputs) -> bool` returns whether these requests can share one forward pass. The default is `False`, which disables batching. Override it to accept batches, for example when the requests use the same graph walk and have compatible shapes.
- `forward_batched(self, graph_walk, engine_inputs, **kwargs) -> dict[str, NameToTensorList]` performs the batched compute. It returns per-request outputs, keyed by `request_id`. When a batch runs, the engine calls this method instead of the single-request `forward`.
- `max_batch_size(self, graph_walk)` sets an optional upper limit.
- `step_order(self, graph_walk) -> StepOrder` says who runs first when more rows are ready than `max_batch_size` allows. The default, `StepOrder.ARRIVAL`, is first come, first served to completion: the requests holding the step keep it, then the request that arrived first. `StepOrder.TURNS` is longest-waiting first: a request that just ran gives way to one that waited, so a node capped at one row advances its requests a step each in rotation. Declare it on a walk whose sessions have to keep moving while others run, as LingBot's rollout and Cosmos3's chained windows do. A combined walk takes turns if any of its walks does. The order applies to the rows a speculation chain continues, the backlog and the queued rows alike; when every ready row fits, it doesn't matter. An admit that runs out of KV pages offloads the row last in that same line.

**Walk priorities.** Which (node, walk) a worker's next step goes to is a `SchedulingPolicy` (`mstar/worker/scheduling_policy.py`). By default it is round robin, least recently scheduled first, and a speculation chain keeps its first step before giving way. A model that returns `WalkPriority` entries from `Model.get_walk_priorities` gets `Priority`: an entry names a node, a walk or one (node, walk), and the most specific entry decides. Keys with ready rows go in priority order, round robin among equals, and a chain gives way at once to a higher key with a row to take. It suits a walk of short steps whose latency matters, such as a TTS prefill that first audio waits on. A ready key that has waited `max_wait` chain steps since it last ran goes first, longest waiting first. A priority on one walk of a combined walk lifts the whole combined key, and a backlogged key still finishes first whatever its priority. The serving config's `scheduling` replaces the entries, sets a default `max_wait` or turns priorities off ([Serving](/serving)). An entry naming nothing the model runs, a negative priority, or two entries for one target refuse the worker's start.

<a id="combined-walks" />


**Combined walks.** By default a step holds one walk. A model lets several walks of a node share a step by returning `{node: {combined_walk: {walks}}}` from `get_combined_graph_walks`, for example decode rows beside a prompt's prefill. The combined walk is a name of its own, which `max_batch_size` and the CUDA-graph configs can key on. A step of one walk keeps that walk's cap. A step that mixes walks takes the combined walk's `max_batch_size` when it has one, else the smallest cap of the walks it holds, so a small prefill cap never limits a decode-only step. `max_rows_in_combined(self, graph_walk)` also bounds how many rows of one walk a mixed step may hold, for kernels sized to a few prompt rows (see `CombinedSplit`). To run a combined walk on such split kernels, pass a `CombinedSplit` in the `splits` of each resource config that supports one (`AttentionConfig` on the `FLASHINFER` backend, for captured steps only, and `LinearAttnConfig` with the GDN variant; other backends ignore `splits` and run the walk unsplit); their specs return it from `combined_splits()`, which is what the engine reads, and resources of one node must agree on a walk's `prefill_walks`. The engine then orders that walk's steps with the `prefill_walks` rows last, so the kernels read the decode rows as the step's first tokens, in place. Every other walk of the combined walk must be one token per row.

**Steps beside the chain.** A worker's main loop runs one chain of steps, each holding the next behind its kernels. A node that shares a worker with a heavier one can set `side_stream_walks` on its submodule to walks that may run beside the chain, on a second stream, and a deployment turns that on with `side_stream: true` on the node's group ([Serving](/serving)). Windows that come ready while a side step runs batch into the next one (`StepPipeline._launch_side` in `mstar/worker/step_pipeline.py`). It suits a stream-fed walk that nothing on the chain reads, such as a codec. `EngineManager.build` refuses a TP, SP or CFG node, a node alone on its worker, a device without streams, a node with chain walks or resources, and a side walk that is shared, combined, or has output spans or a stop check. Without the config field the node stays on the chain.

`ARNodeSubmodule` declares `preprocess` abstract because autoregressive nodes are expected to collate a batch. You can still disable batching for one node, or for specific walks, by returning `False` from `can_batch` in those cases.

**Accelerator graphs.** A submodule declares the shapes it can capture in `get_accelerator_graph_configs(self, device, tp_world_size=1) -> list[AcceleratorGraphConfig]`. The default is an empty list, which means eager execution. For each config, the engine first runs `torch.compile`, controlled by the config's `compile` flag, which defaults to `True`. It then captures the forward through the platform's graph backend (CUDA graphs on CUDA, XPU graphs on Intel XPU) and replays it. Two config types are defined in `mstar/engine/accelerator_graph_config.py`. They differ in which stage of the submodule pipeline they freeze:

| Config type | Use and captured stage |
|----|----|
| `BatchedAcceleratorGraphConfig` | Decode-style forward passes, in which every request in the batch has the same length. That length is usually one token. Pass `single_request_inputs`, which is a `NodeInputs` for one request. The runner clones it to build each captured batch. This config fixes the output of `prepare_inputs`, and `preprocess` runs on both capture and replay. |
| `PackedAcceleratorGraphConfig` | Prefill-style forward passes that operate on packed, variable-length sequences. Pass `capture_token_lengths`, which lists the token-count buckets to record, and `make_node_input(n)`, a factory that builds a `NodeInputs` for one request of length `n`. The runner partitions each bucket across the batch. Attention is planned at capture time from the step declaration, and planned again into the captured buffers on each replay. |

Both types share the base `AcceleratorGraphConfig` fields:

- `capture_graph_walk` is the walk to capture.
- `replay_graph_walks` lists the walks that may replay this capture. One capture can therefore serve several walks, for example `prefill_audio` reusing `prefill_text`.
- `capture_batch_sizes` lists the batch sizes to record. `None` uses the runner default; `[]` records none.
- `additional_key_info` is an extra hashable component of the capture bucket key. Use it when one walk must be captured more than once because the batch shape alone does not identify the capture. Its value must equal both the value returned by the submodule's `cg_key_info(graph_walk, per_request_info)` for a batch and the `cg_key_info` value that the batch's `declare_step` sets on its step. A mismatch raises no error: the batch matches no capture and runs eagerly. Compute all three values from one place.
- `capture_forward_method` names the method to capture. The default is `"forward_batched"`.
- `caps_eager_batch_size` controls whether this config's captured sizes also limit the engine's eager batch size for the walk. The default is `True`, so the engine never batches beyond a captured size.
- `compile` runs `torch.compile` before capture. The default is `True`.
- `compile_mode` is that `torch.compile`'s mode. The default, `None`, takes the deployment's compile level (`mstar serve -O`, `MSTAR_COMPILE_LEVEL`); naming a mode opts out of it. `default` keeps Inductor's fusion but takes cuBLAS for every GEMM and skips autotuning. `deterministic`, the engine's own, picks kernel configs by rule rather than timing, so every process compiles the same kernels; a compile outside the runner gets the same options from `accelerator_graph_runner.compile_kwargs("deterministic")` or `mstar.platforms.compile.deterministic_inductor_options()` (the Wan VAE decode, the DiT scaffold's `compile_blocks`, Cosmos3's denoise step). An unknown mode, and one that turns on Inductor's own CUDA graphs (`reduce-overhead`, `max-autotune`), are refused.
- `inductor_options` are Inductor config entries the compile runs under, over the mode's or the compile level's own, e.g. `{"max_autotune_gemm_backends": "ATEN"}` to keep max-autotune's fusion choices but cuBLAS for the GEMMs (autotune's timings of decode-width GEMMs can vary between processes). Building the config refuses an entry Inductor doesn't have, and `triton.cudagraphs`.
- `input_seq_dims` maps a static-input key that `preprocess` returns to the dimension that varies with the bucket, where the runner's size match would pick another axis that happens to equal the bucket's token count.

A bucket that fails to capture is dropped, and its steps run eagerly. `MSTAR_REQUIRE_ACCELERATOR_GRAPHS=1` turns a dropped bucket into a startup failure instead.

`BatchedAcceleratorGraphConfig` also accepts `total_tokens_multiplier`. Use it when one request's step commits KV across several labels that are combined into a single plan, as in batched guidance that packs the conditional and unconditional sequences together. The static buffer must hold all of them, and this field scales the buffer independently of the per-label span.

For example, a token decoder that captures a batched `decode` graph and a packed `prefill` graph declares the following (`SampledTokenDecoder` builds these, and a mixed one, for its subclasses):

```python
PREFILL_TOKEN_BUCKETS = [32, 64, 128, 256, 512, 1024]
PREFILL_CAPTURE_BATCH_SIZES = [1, 2, 4, 8, 16]

def get_accelerator_graph_configs(self, device, tp_world_size=1):
    return [
        BatchedAcceleratorGraphConfig(
            capture_graph_walk="decode",
            single_request_inputs=ARNodeInputs(
                input_ids=torch.zeros(1, dtype=torch.long, device=device),
                input_seq_len=1,
            ),
        ),
        PackedAcceleratorGraphConfig(
            capture_graph_walk="prefill",
            capture_token_lengths=self.PREFILL_TOKEN_BUCKETS,
            make_node_input=lambda n: ARNodeInputs(
                input_ids=torch.zeros((n,), dtype=torch.long, device=device),
                input_seq_len=n,
            ),
            capture_batch_sizes=self.PREFILL_CAPTURE_BATCH_SIZES,
        ),
    ]
```

A deployment replaces a packed capture's `capture_token_lengths` with the serving config's `prefill_token_buckets` (node -> capture walk -> ladder, see [Serving](/serving)). The engine applies it to the configs `get_accelerator_graph_configs` returns, so a model plumbs nothing. A `PiecewisePackedConfig` region's `total_tokens` takes the ladder its label names the same way.

BAGEL shows the case of two captures for one walk. It captures `decode` twice, once with `additional_key_info=False` and once with `additional_key_info=True`. A decode step with guidance enabled lists each row on `main` and `cfg_img`, so its capture sets `total_tokens_multiplier=2`, and a decode step with guidance disabled lists it on `main` alone. BAGEL's `cg_key_info` reports which of the two a batch is.

### Piecewise graphs (capturing an inner loop) {#piecewise-cuda-graphs-capturing-an-inner-loop}

The configs above capture the whole `forward_batched` method of a submodule. The engine then drives the replay, including sampling and output remapping.

Sometimes you want to capture only one inner region of a forward, such as a transformer block loop, and keep the surrounding code in eager Python. The code before the region computes embeddings and assembles the sequence. The code after it applies the final norm and projection. A piecewise graph supports this.

A submodule enables piecewise capture by returning one or more configs from:

```text
get_piecewise_accelerator_graph_configs(self, device, autocast_dtype, tp_world_size=1)
    -> dict[str, PiecewiseAcceleratorGraphConfig]
```

The dict key is a region name, which is any string that identifies the captured region. Several keys capture several independent graphs. At warmup, the engine builds one `PiecewiseAcceleratorGraphRunner` per key and puts them in `engine_inputs.piecewise_runners`. Your forward looks up the runner by key and calls it. Nothing is stored on the submodule.

Two config types are defined in `mstar/engine/accelerator_graph_config.py`. They correspond to the two whole-forward types:

| Config type | Use and captured shape |
|----|----|
| `PiecewiseBatchedConfig` | Batched inputs of equal length. The captured region sees `[bs, seq_len, D]`, and every request has the same `seq_len`. Pass `seq_len`, the number of tokens per request. One graph is captured per batch size. |
| `PiecewisePackedConfig` | Packed, variable-length inputs. The captured region sees `[total_tokens, D]`, with several sequences of different lengths packed together. Pass `total_tokens`, a list of token-count buckets. One graph is captured per pair of batch size and bucket. |

Both types share the base `PiecewiseAcceleratorGraphConfig` fields:

- `capture_fn` is the callable to capture. Its interface is described below.
- `make_static_inputs` is a factory with signature `(shape: PiecewiseCaptureShape) -> dict[str, Tensor]`. It returns the persistent buffers that the captured region reads. The runner owns these buffers. Before each replay, it copies your real tensors into them by name. `shape` provides `bs`, `seq_lens` and `total_tokens` for the bucket being built. Allocate each buffer in the dtype of the tensor you pass for it, which for a hidden state is usually `autocast_dtype`. The copy before replay casts a value into a wider dtype of its kind (int32 token ids into an int64 buffer, a bf16 table into an fp32 one). A value the buffer may round (a narrower dtype, such as an fp32 hidden state into a bf16 buffer, or an integer into a floating-point or complex buffer) is refused with a `ValueError` naming the buffer.
- `forward_kwargs` holds static keyword arguments that are passed to `capture_fn` on every call, for example a layer count or an `is_causal` flag.
- `required` makes every declared shape mandatory: if any participating rank leaves one out of capture, for memory or by a failure, the worker refuses to start rather than serving that shape eagerly. Set it on a region with no eager path, such as one whose per-stream state only its captures read and write. The default is `False`.
- `declare_step` has signature `(request_ids, seq_lens) -> SubmoduleStep | None`. It declares the region's own state work over the padded batch, an `ArrayStep` for each array the region touches, as the example below does. It is separate from the submodule's `declare_step` because the region has its own shape. The runner admits, plans and commits this step on each replay.
- `lease_before_step` makes the runner take this region's graph slot before the outer `declare_step` runs, and report the slot in that call's `piecewise_leases` argument. The region still declares, plans and commits its own work. The lease only tells the outer declaration which resources are already taken, so that it can exclude them.
- `can_lease` has signature `(inputs: list[NodeInputs]) -> bool`. It applies only with `lease_before_step`, and lets the region refuse a batch for a limit that the capture bucket key doesn't express, such as Qwen3.5's segment count per step. The engine then gives the region no lease for that step. Your forward must replay a `lease_before_step` region exactly when its label is in `engine_inputs.piecewise_leases`, and not whenever `runner.can_run` is true: a refused batch can still fit a bucket, and replaying it would declare the region's resources twice.
- `one_row_per_step` makes the runner lease, check (`can_run`) and replay the region as one row, whatever the step's batch size, under the step's first request. It is for a packed region that runs every request's segments as one ragged batch, such as a vision tower, and needs `lease_before_step` and `capture_batch_sizes=[1]`. The region's `declare_step` then receives `[first_rid]` with every request's `seq_lens`, so the whole step's segments count against one replay's plan: size its attention resource with `max_segments_per_step`, and pair it with a `can_lease` that refuses a step with more. On a node serving LoRA adapters it is leased only for a step whose rows run none, since its replay would address every request's tokens to the first request's adapter.
- `capture_batch_sizes` lists the batch sizes to record. `None` uses the runner default; `[]` records none, for an eager-only region (below).
- `eager_fallback` runs a shape with no graph eagerly through `run` instead of raising: the runner declares, plans and commits the region's step over the real rows (as a replay declares it, without padding), so the caller has one path for captured and uncaptured shapes. Off, the caller checks `can_run` first. MiniCPM-o's vocoder uses it, with eager-only regions for the shapes it never captures.
- `compile` runs `torch.compile` on `capture_fn` before capture. The default is `False`.
- `compile_mode` is that `torch.compile`'s mode, as on `AcceleratorGraphConfig`.

**Splitting the declaration.** When a region leases its own slot, exactly one of the two declarations must own each resource. The common pattern is for the outer `declare_step` to return `None` when the region holds a lease, and to declare the resources itself otherwise, which covers the eager fallback path:

```python
def declare_step(self, graph_walk, request_ids, inputs,
                 slot_lease=None, piecewise_leases=None, **kwargs):
    if (piecewise_leases or {}).get(BLOCK_LOOP_REGION):
        return None                      # the region declares its own KV + attention
    return SubmoduleStep(                # eager path: nobody else reserves these pages
        segments=[
            Segment(request_id=rid, label="main", span=inp.input_seq_len)
            for rid, inp in zip(request_ids, inputs, strict=True)
        ],
        state={KV_CACHE: ArrayStep()},
    )
```

**The capture_fn interface.** The captured callable takes one `PiecewiseCallInputs` argument and returns a dict:

```text
capture_fn(inp: PiecewiseCallInputs) -> dict[str, Tensor]
```

`PiecewiseCallInputs` has three fields. `static_inputs` holds the buffers owned by the runner. `engine_inputs` is the region's view of the batch: request ids and per-request info padded to the capture bucket. `kwargs` is the config's `forward_kwargs`, unchanged. Capture and replay both use this same type, so a region cannot read a field that exists on only one of the two paths.

<Warning>

Read tensors from `inp.static_inputs`, and never assign to its entries. The runner passes the same dict object at capture time, and updates those buffers in place before each replay. An assignment such as `static_inputs["x"] = ...` replaces the buffer, and the region then no longer uses the memory address that the graph recorded.

</Warning>

A `capture_fn` may also return a single `Tensor`. The runner wraps it as `{"x": ...}`.

**Calling the runner.** Look up the runner by region name and pass your real inputs to it. It returns a `PiecewiseOutput`, which behaves like a dict. Indexing and `.get` return a clone that you own and can keep. `.get_view` returns a view without copying, which is only valid until the next call to `run`. See `mstar/engine/accelerator_graph_runner.py`. The runner handles input padding, admission and planning of the region's declared step, replay, commit, and output slicing.

The V-JEPA2 AC predictor is the reference implementation. See `mstar/model/vjepa2/submodules.py`, region `"block_loop"`. It has an eager section before the region, a captured block loop that reads the KV cache over a fixed per-step sequence, and an eager section after the region.

```python
from mstar.engine.accelerator_graph_config import (
    PiecewiseBatchedConfig, PiecewiseCallInputs, PiecewiseCaptureShape,
)

# --- the captured inner region ---
def _block_loop_capture(self, inp: PiecewiseCallInputs) -> dict[str, torch.Tensor]:
    # READ out of inp.static_inputs; never reassign its entries
    cond_tokens = inp.kwargs.get("cond_tokens")
    fn = self.predictor.make_block_loop_fn(cached=True, static_pos_bufs=inp.static_inputs, cond_tokens=cond_tokens)
    return {"x": fn(inp.static_inputs["x"])}

# --- declare the region ---
def get_piecewise_accelerator_graph_configs(self, device, autocast_dtype, tp_world_size=1, **kwargs):
    def make_static_inputs(shape: PiecewiseCaptureShape) -> dict[str, torch.Tensor]:
        # hidden state in autocast_dtype so the replay copy_ is a same-dtype memcpy;
        # position buffers stay float32 (RoPE frequency precision matters more)
        return {
            "x": torch.zeros(shape.bs, capture_seq_len, embed_dim,
                             dtype=autocast_dtype, device=device),
            "d_pos": torch.zeros(N * N, dtype=torch.float32, device=device),
            ...
        }

    def declare_step(request_ids: list[str], seq_lens: list[int]) -> SubmoduleStep:
        return SubmoduleStep(
            segments=[
                Segment(request_id=rid, label="main", span=seq_len)
                for rid, seq_len in zip(request_ids, seq_lens, strict=True)
            ],
            state={KV_CACHE: ArrayStep()},
        )

    return {
        BLOCK_LOOP_REGION: PiecewiseBatchedConfig(
            capture_fn=self._block_loop_capture,
            make_static_inputs=make_static_inputs,
            declare_step=declare_step,
            # take the slot before the outer declaration, so it can leave
            # this region's KV to the runner
            lease_before_step=True,
            seq_len=capture_seq_len,
            forward_kwargs={"cond_tokens": cond_tokens},
            capture_batch_sizes=[1, 2, 4, 8],
        )
    }

# --- invoke it inside the forward ---
runner = engine_inputs.piecewise_runners.get(BLOCK_LOOP_REGION)
if runner is not None and runner.can_run(x.size(0)):
    out = runner.run(                       # admits + plans + replays + commits
        static_inputs={"x": x, "d_pos": d_pos, ...},
        request_ids=engine_inputs.request_ids,
    )
    x = out["x"]                            # owned clone
```

Positions are computed eagerly and passed in through `static_inputs`, so the captured region does not compute them again. The captured and eager paths run the same block loop. The region's `declare_step` covers only the captured path; the submodule's own `declare_step` covers the eager one (**Splitting the declaration** above).

BAGEL's ViT tower is the packed, cacheless counterpart. See `mstar/model/bagel/submodules.py`, region `"vit_block_loop"`: a `PiecewisePackedConfig` over `VIT_TOKENS`, with patch embedding and the RoPE gathers left eager because they are data-dependent indexing. A packed region whose rows each attend within themselves passes `array`, the declared array with `max_len=0`, and leaves `declare_step` unset: the config then declares one `main` segment per row over that array (`PiecewisePackedConfig.region_step`).

## Step 6: Write a config YAML {#config-yaml}

A config maps nodes to GPU ranks. The value under `model:` is your registry key. Each `node_groups` entry assigns one or more `node_names` to `ranks`. An entry can also name specific `graph_walks`, which is how prefill-decode disaggregation is expressed. Every node of a walk must be placed by exactly one entry that applies to that walk; the conductor refuses a config that places it twice or not at all.

```yaml
model: "your_model"
max_seq_len: 2048
node_groups:
  - node_names: ["LLM"]
    ranks: [0]
```

Run it with:

```bash
mstar serve your_model --config configs/your_model.yaml
```

With the name in `DEFAULT_CONFIGS` (Step 1), `mstar serve your_model` loads this file without `--config`. [Deployment config](/reference/config) lists every top-level key; this page covers the ones a model author touches.

### Tuning resources per deployment {#tuning-resources-per-deployment}

The model declares the shapes that the model requires. A deployment then tunes the values that suit the machine it runs on. Use a `resources:` block for this, with one sub-block per declared name. A model with two caches of the same kind, such as Whisper's decoder cache and its encoder context, can therefore tune each one separately:

```yaml
model: "whisper_large"
max_seq_len: 448
resources:
  kv_cache:
    cpu_offload_pages: 128
  cross_kv_cache:
    cpu_offload_pages: 128
```

Each resource accepts its own keys, and an unknown key raises an error at load time, so that a misspelled setting is never silently ignored. [What the engine builds](/contributing/state-contract#resources) lists the keys for each declaration, and [Sequence and context parallelism](/contributing/state-contract#sequence-parallelism) covers `context_parallel`, `min_tokens` and `exchange`.

`flashinfer_backend` on a cacheless attention is unset by default, so a self-attention reads the `ragged_attention` kernel table; any name (`auto`, `fa2`, `fa3`, `cudnn`, `cutlass`) runs that FlashInfer backend and no table. The `lora:` block takes `max_slots` (adapters resident on the device at once, beside the zero adapter), `max_rank` (the largest rank served; slots are sized to it), `cpu_capacity` (adapters held in pinned host memory), `adapters` (adapter name to safetensors path: the names requests can ask for), `targets` (the subset of the model's targets to allocate; [LoRA pool](/contributing/state-contract#lora-pool) gives the default, and experts targets are allocated only when listed), `runtime_updates` (default false: serve `/v1/load_lora_adapter` and `/v1/unload_lora_adapter`) and `runtime_update_timeout_s` (default 120: how long the conductor waits for every worker to answer one before giving up on it). The one `lora:` block sizes the pool of every node the model's spec reaches.

Tune the cache shape on the KV resource, not on the attention resource that reads it. For example, `configs/qwen3tts.yaml` selects FA2 under `talker_attn`, `configs/cosmos3_nano.yaml` sets the page count under its paged KV key, and `configs/waypoint.yaml` sets the resident world count under its ring KV key.

A top-level `kv_cache:` block raises an error at load time. Put the block under `resources:`, keyed by the resource name.

### Routing across data-parallel replicas {#routing-across-data-parallel-replicas}

When a node group has several replicas, the conductor sends each new request to the replica where it is cheapest ([Serving](/serving)). Models declare nothing for it: a paged KV pool takes part by its predicted prefix hits ([Routing across data-parallel replicas](/contributing/state-contract#routing)).

### Preprocessing threads {#preprocessing-threads}

The API server runs `load_image` / `process_prompt` and output encoding with torch's intra-op pool. Torch sizes it at one thread per host core, which in a container can be several times the CPUs the cgroup quota lets run, and an op waits on any of its threads the scheduler has parked. The API server therefore defaults to a quarter of the CPUs it may use (its affinity, capped by the cgroup `cpu.max` quota), at most 4. A model sets its own size with `PREPROCESS_TORCH_THREADS` on the class (Qwen3.5 uses 4). A deployment overrides either at the top level of its config; `null` keeps torch's default:

```yaml
model: "qwen3_5_4b"
preprocess_torch_threads: 4
```

The setting applies only to the API server process. The conductor and workers keep torch's default. It does not size video decoding: each torchcodec decode that asks `media_limits.video_decode_threads` (`Model.load_video` does) runs FFmpeg with up to 8 threads, no more than the CPUs the process's CPU plan leaves unpinned (`CpuPlan.left`).

The data worker prepares one request at a time on its own thread, so a request's media decode holds up every request behind it and the output chunks of the ones running. A model whose `load_image` / `load_audio` / `load_video` and `process_prompt` keep no shared state sets `PREPROCESS_PARALLEL = True`, and requests then prepare on a pool sized to the CPUs left (`CpuPlan.prepare_workers`: at most 8, and the pool times the process's intra-op thread count stays within the CPUs left, so a higher `preprocess_torch_threads` means fewer workers). Tensors are still stored and requests still reach the conductor from the data worker's thread, in arrival order. A deployment sets the pool at the top level of its config; 1 turns it off:

```yaml
model: "qwen3_omni"
preprocess_workers: 2
```

The pool only helps work that releases the GIL, so measure each stage first. Qwen3-Omni, V-JEPA2, Cosmos3, Parakeet, Nemotron ASR, Omnilingual ASR and Pi0.5 declare it (`configs/vjepa2.yaml` and `configs/vjepa2_ac.yaml` set 8 and 4, the sizes measured for their video decode; Cosmos3's DROID policy configs set 1, since a robot sends one request at a time). A model with client streams always prepares inline, since an append has to follow its request.

A model that takes several images per request and whose `load_image` is mostly a decode can also set `PREPROCESS_PARALLEL_IMAGES = True`, which decodes one request's images at once on a second pool the size of the prepare pool, unless `preprocess_workers` is 1. Pi0.5 declares it for its camera frames.

A pool that small is slow for a large copy (a 121-frame 832x480 video is 145 MB), so a video decoder emits its clip in the encoder's layout, transposed on the GPU inside its forward: `[T, C, H, W]` for torchcodec's `VideoEncoder` (Cosmos3), `[T, H, W, 3]` rgb24 for PyAV (Wan2.2, LTX-2.5) or a raw `video_frame` stream (LingBot-World). A permute in `postprocess` costs a host copy of the whole clip. Write a PyAV mp4 with `mstar.model.components.video_encode.encode_mp4`, which converts pixel formats on a thread ahead of x264, and a long torchcodec mp4 with `video_encode.encode_mp4_chunked`, which encodes pieces in parallel and joins them (a keyframe per piece).

### Tensor parallelism (sharding) {#tensor-parallelism}

To shard a node across several GPUs, add `tp_size` to its `node_groups` entry and list `tp_size` ranks. The runtime splits the group's ranks into TP groups of that size and builds one `comm_group` per shard.

A node is sharded only if its components are built from the tensor-parallel modules in `mstar/model/components/distributed`: `ParallelAttention`, `ParallelCrossAttention`, `ParallelGatedMLP`, `ColumnParallelLinear`, `RowParallelLinear`, `VocabParallelEmbedding` and others. The `weight_loader` of each such parameter slices it automatically. See [Loading weights](/adding_models#loading-weights). A node whose components do not use these modules is replicated on every rank instead. For example, a tensor-parallel Qwen3-Omni Talker keeps its code predictor replicated.

Once a component is built from these modules, moving from one GPU to tensor parallelism requires only the YAML change and a small sharding declaration. No model code changes. The example below runs the Orpheus LLM with tensor parallelism across two GPUs. See `configs/orpheus_tp2.yaml`:

```yaml
model: "orpheus"
node_groups:
  - node_names: [LLM]
    ranks: [0, 1]
    tp_size: 2
    graph_walks: [prefill, decode]
  - node_names: [snac_decoder]
    ranks: [0]
    graph_walks: [snac_chunk]
```

For a node to be eligible for `tp_size > 1` it must be declared TP-enabled by the model. Override `get_default_sharding_config` to return a `ShardingConfig` that names the shardable nodes, and any non-default shard dimensions:

```python
def get_default_sharding_config(self):
    from mstar.distributed.base import ShardingConfig
    return ShardingConfig(groups=[], tp_enabled_nodes={"LLM"}, shard_dim={})
```

Two separate mechanisms split work across the TP group. Keep them distinct:

- **Weights** are sharded inside the components, by each parameter's `weight_loader`. Column-parallel and row-parallel linear layers built with the `comm_group` do this automatically, once the module is constructed for tensor parallelism. The config needs nothing more.
- **Activations** that cross a node boundary are handled by `shard_dim` in the `ShardingConfig`. It maps an inter-node edge or signal name to the dimension along which that tensor is split across the group. If a name is absent, or maps to `None`, the tensor is replicated to every rank. You need an entry only for edges where the producer and the consumer both keep the data sharded. The common case is replicated activations, which needs no entry. You can also set `shard_dim` per run, under a `sharding_config` block in the YAML. A sharded signal is split over the node's whole lockstep instance, so placement refuses one on a node group with `sp_size` or `cfg_size` above 1.

If a node group has `tp_size > 1` and names a node that is not in `tp_enabled_nodes`, loading fails. See `configs/qwen3omni_thinker_tp2.yaml` for an example with several node types.

A row-parallel projection followed by an RMSNorm can leave its all-reduce to the norm, which runs both in one fused kernel. Set the projection's `reduce_results = False`, so it returns its partial sum, and hand the norm the comm group: `RMSNorm.forward_residual(x, residual, comm_group)` reduces, adds and norms, and `RMSNorm.forward(x, comm_group)` reduces and norms (a post-norm before the residual add). The two go together, since a norm called without the group norms an unreduced partial sum, which is wrong only under TP. Keep both in the module whose `forward` calls the norms, as `Qwen3_5LanguageModel`, `MuseGlimmerTextModel` and `RippleTextModel` do. `MultimodalDecoderModel` builds the kernel's workspace for its TP node.

### Guidance (CFG) parallelism {#guidance-cfg-parallelism}

A diffusion node that runs its classifier-free-guidance branches as one batch can split them over a node group's `cfg_size` ranks, a mesh axis of its own beside `tp_size` and `sp_size` (see [Serving](/serving)). Declare the node and the most branches it runs in `cfg_enabled_nodes`; placement refuses a `cfg_size` that doesn't divide that count:

```python
def get_default_sharding_config(self):
    return ShardingConfig(
        groups=[], tp_enabled_nodes=set(), shard_dim={},
        cfg_enabled_nodes={"dit": 2},
    )
```

The submodule receives `cfg_group` from `get_submodule`, takes its rows of the branch batch with `my_rows(cfg_group, branches)` (`mstar/distributed/communication.py`), and after the forward reassembles them with `cfg_group.all_gather(out, dim=0)`. Every rank then runs the same guidance combine and solver step on replicated latents. CFG ranks keep every attention head; only TP and SP ranks split them. The ranks run in lockstep on the same requests, so any per-request resource the node declares must stay the same shape on every rank, and a node with `cfg_size > 1` can't hold a paged KV cache (placement refuses one before any worker starts): branches that hold different KV are separate nodes in a graph `Parallel` instead, on a node group with `cfg_size: 1`, as BAGEL's `LLM_cfg_text` and `LLM_cfg_img` are. `Wan22DitSubmodule` is the reference.

### Expert parallelism (MoE) {#expert-parallelism-moe}

A sharded MoE node can split its routed experts in two ways. Under TP, the default, every rank holds a slice of every expert. Under EP, each rank holds whole experts. A deployment picks one per node group with an `ep_config` block; see [Serving](/serving) for the keys. The shared pieces are in `mstar/model/components/moe_parallel.py`. The Qwen3-Omni Thinker (`mstar/model/qwen3_omni/components/thinker.py`) is the reference user.

To support it in a model:

1.  **Declare the node EP-enabled.** Add it to `ep_enabled_nodes` in `get_default_sharding_config`. An `ep_config` on any other node fails at start-up.

    ```python
    return ShardingConfig(
        groups=[], tp_enabled_nodes={"LLM"}, shard_dim={}, ep_enabled_nodes={"LLM"},
    )
    ```

2.  **Build the MoE layers with** `instantiate_moe_block`. Accept `moe_parallel` in `get_submodule` and pass it, with the node's `tp_group`, down to each MoE layer. The helper returns a `ParallelSparseMoeBlock`, with `expert_parallel=True` under EP. It keeps its experts in a `FusedExperts` (`block.experts`), which owns the `gate_up_proj` / `down_proj` parameters, the weight loaders that keep only the rank's slice or its own experts, and the dispatch. `moe_parallel=None` gives TP.

    ```python
    self.mlp = instantiate_moe_block(
        hidden_size=cfg.hidden_size,
        moe_intermediate_size=cfg.moe_intermediate_size,
        num_experts=cfg.num_experts,
        num_experts_per_tok=cfg.num_experts_per_tok,
        norm_topk_prob=cfg.norm_topk_prob,
        comm_group=tp_group,
        moe_parallel=moe_parallel,
    )
    ```

3.  **Optionally, mix in** `MoeParallelMixin` on the model's top-level module, and call `self.init_moe_parallel(moe_parallel)` at the end of its `__init__`. It provides:

    - `maybe_log_expert_load(synthetic)`, which implements `log_expert_load_every`. Call it from eager code before each forward, usually from `preprocess`, with `synthetic=engine_inputs.synthetic` so capture and warmup routing are discarded.
    - `moe_token_valid(hidden_states, num_valid_tokens)`, which implements `mask_padding`. It returns the `token_valid` mask for the MoE blocks, or `None` when masking is off. Pass the mask only to MoE layers, not dense MLPs. `num_valid_tokens` must be a `(1,)` device tensor that `preprocess` returns as a static input, so a replay can update it; fill it from `engine_inputs.real_seq_len`. `ThinkerSubmodule.preprocess` shows the wiring.

`instantiate_moe_block` builds no shared-expert block. A node with one (`ParallelSparseMoeBlock(shared_expert=...)`, the Qwen3-Omni Talker's) builds it directly and stays TP-only.

### Tuned kernel configs {#tuned-kernel-configs}

Launch configs that depend on the GPU and the shapes, such as the fused MoE's tiles, are data, not code. Each kernel op (`mstar/kernels`) names the dimensions its configs are keyed by, and its tuned configs live in one JSON table per GPU under `mstar/kernels/tables/<op>/`. A model on a shared component gets them without code of its own: the component looks its shape up once per process and keeps the default config where no table has it, and the server logs the sweep command for that shape (`kernel table: no moe_gemm bfloat16 E=128,N=1536,K=2048,top_k=8 ...`). A block-fp8 dense linear (`fp8_linear`, `mstar/utils/dense_fp8.py`) takes its kernel per token count the same way: the w8a16 Triton kernel, FlashInfer's or cuBLAS's block-scale GEMM, where the GPU's row names one that runs there. A cacheless self-attention (`ragged_attention`) takes its kernel per head geometry and longest query segment the same way: torch's cuDNN SDPA or one of FlashInfer's ragged backends. A table can also be named for an architecture (`sm_103.json`) rather than one GPU model, for rows that hold on every GPU of it; the sweep's `--arch` writes that file.

`python -m benchmark.kernels.sweep` times the candidates at those shapes on one GPU, checks each against a reference output, and writes the winners with where they were measured. `--out DIR` with `MSTAR_KERNEL_TABLES=DIR` serves a sweep before it is committed; `benchmark/kernels/README.md` has the workflow and how to add an op.

## Advanced: async partitions and streaming {#advanced-async-partitions-and-streaming}

Models with a single partition can skip this section. The defaults in `Model` provide one partition, named `"default"`, that contains all walks.

Use several partitions when one stage must run asynchronously while another continues to produce data, for example an LLM feeding a vocoder, or a thinker feeding a talker. Override these methods:

- `get_partition_topology()` declares the partitions and the streaming `Connection` objects between them, including a `chunk_policy_factory` such as `SlidingWindowChunkPolicy(window=..., stride=...)`.
- `get_partitions()` declares each `PartitionDefinition`: its name and its walks. Every walk belongs to exactly one partition.
- Route cross-partition tensors with `StreamingGraphEdge(next_node=..., name=..., target_partition=...)` instead of a plain `GraphEdge`.

A consuming partition's plan needs nothing about the stream. A step whose walk a stream feeds, and that runs no Loop but chunk loops, runs once per chunk the stream brings, and the partition ends when the worker reports the pass that consumed the stream's final chunk. For a stream from another partition, the conductor tells the consumer `producer_done` once the producer partition is done; the data worker ends a stream from the client (below) itself.

The consumer receives each chunk as its items stacked along a new leading dimension, or as the item itself when the chunk holds one. Don't write into a streamed input in place: a one-item chunk is the stored tensor, which the producer may also have routed to other destinations, and a sliding window's overlap items reappear in the next chunk.

Keep a walk that consumes a stream to one node or one `Loop` on one node group, and move later work into a downstream partition fed by its own `StreamingGraphEdge`. A consumer whose every input is streamed runs again as soon as the next chunk arrives, and the runtime and conductor count passes per worker graph, so the conductor refuses at startup such a consumer sharing its worker graph with another top-level node or `Loop`, and a stream-consuming walk split over worker graphs, unless every consumer also waits on a non-streamed input and all the walk's worker graphs run on the same workers. That input must arrive once per pass (from the conductor, say); startup cannot check this.

A consumer whose walk should follow the producer's progress, rather than a count fixed at ingest, is *producer-triggered*: the producer decides the consumer's walk. Set the same `consumer_walk` function on every connection into the consumer, all from one producer partition. The producer worker calls it for each row of a pass that emits on those edges, with a `ProducerWalkCtx`: the walk that row ran (its own, even in a step that mixed walks), the node that just completed, the iteration each enclosing dynamic loop is on, and the producer's full `CurrentForwardPassInfo` (`step_metadata` and all; the hook runs on the producer). The row's streamed items run under the walk it returns. The context is reused across calls, so a hook must not keep it.

- Each streamed item carries its assigned walk, and a chunk never spans two walks, so these connections need a `FixedChunkPolicy`. A client stream cannot set `consumer_walk`.
- The consumer's worker switches walk before popping a chunk, and only once the partition has no pass under way. The conductor learns each pass's walk from the worker's `WORKER_GRAPHS_DONE`.
- A walk the consumer enters on its own, with conductor inputs, takes effect when they arrive, so send them only once the stream has moved the consumer through the walk before it.

Qwen3-Omni's Talker (`_talker_walk`) is the reference: Thinker prefill passes run `talker_prefill`, the first decode iteration runs `talker_last_prefill`, and later ones run `talker_decode`. Its plan lists the three walks. The conductor follows the walk each pass reports and enters the next step only to send it something, so it feeds `talker_decode` its first input once `talker_last_prefill` has run.

### Streams from the client {#streams-from-the-client}

A model that listens while it runs (a full-duplex speech model, say) takes its live input as a stream the client feeds. Declare it like any other connection, with the reserved producer `CLIENT`:

```python
from mstar.streaming.topology import CLIENT, Connection

Connection(from_partition=CLIENT, to_partition="Encoder", edge_name="audio_in",
           chunk_policy_factory=lambda: FixedChunkPolicy(chunk_size=1))
```

`CLIENT` is not a partition: it has no walks and no worker, and it must not appear in `partitions`. The node that lists `audio_in` in its `input_names` (with `consumes_stream=True`) consumes it through a `StreamBuffer` and the connection's chunk policy, exactly as it would a stream from another partition. Its partition self-triggers from the stream, and the conductor sends its walk none of the streamed input. That node must be the only one, in any walk, that takes the edge; the conductor checks this at startup, and that the model implements `process_stream_chunk` unless each client stream declares `ClientAudio` (below). A partition may take several client streams (audio and video, say): each has its own buffer and its own end.

- `process_stream_chunk(chunk)` turns each append the client sends into stream items, keyed by client edge name. `chunk` is a `ClientChunk` (`mstar.model.base`): `text`; `tensors` and `input_metadata`, the append's files loaded as for a request (`audio_inputs` and so on); `streams`, per `tensors` list the client stream each file names (`None` where the client named none, so the model decides); `model_kwargs`, the append's own; and `request_kwargs`, the opening message's. Raise `ValueError` for an append the model doesn't take (the client gets a 400). An append of text alone, or of `model_kwargs` alone that ends no stream, that yields no item is refused rather than dropped, but the data worker can't tell which items text sent with files yielded: refuse such text yourself if the model takes none. Keep it stateless; the consuming node keeps its own state, in its declared state.
- Tensors `process_prompt` returns under a client edge's name are the stream's first chunk, so a one-shot request (one uploaded file, then nothing) is a stream of one chunk. `process_prompt` gets `open_streams`, the client streams the opening leaves open; a model whose request settings can't take appends on one (Qwen3-TTS text in a layout that streams none) raises `ValueError` there, so the live opening gets a 400.
- A client stream may declare limits, `Connection(..., limits=ClientStreamLimits(...))` (`mstar.streaming.topology`), which the client-stream layer enforces before any of the model's code runs: `max_items`, what the stream may carry over a call's life, each item counting `item_size(item)` (1 by default; a stream of variable-length chunks counts their frames or samples, named by `unit`). A call past `max_items` ends with a 400 that names the limit, so the consumer need not check a session cap of its own. Declare the most the consumer can take: a deployment may lower a declared bound under `client_streams:` (see [Serving](/serving)), but not raise it.
- An audio client stream may declare what its audio is, `Connection(..., audio=ClientAudio(sample_rate, frame_samples))`: mono audio at `sample_rate`, whose consumer computes on frames of `frame_samples`. `/v1/realtime` then serves the model as a conversation ([Using a Server](/clients)), when only one of its client streams declares it and its audio output is mono: the route decodes the caller's codec, resamples to `sample_rate` and turns the model's output back into the caller's format from `get_output_sample_rate`. On every route the data worker, the stream's producer, sends it in whole frames: each whole frame of an append goes as an item (an opening clip's frames as one) and the rest waits for the next append, or goes with the stream's end. A model whose client streams all declare `ClientAudio` needs no `process_stream_chunk`: the data worker takes appended audio files at `sample_rate` (one at another rate is refused: resampling an append alone leaves a seam), refuses non-finite samples and clamps to [-1, 1]. Nemotron VoiceChat declares `ClientAudio(16000, 1280)`: its encoder's 80 ms frame, taken from the encoder's own hop and subsampling.
- A model that declares `ClientAudio` decides when to speak (full duplex). To serve `/v1/realtime` conversations it also declares `turn_tokens = (start_id, end_id)` on the model (a property when the ids come from its config): the text tokens that open and close each reply, and, if its replies may get no end mark, `turn_idle_steps`: a reply then also ends after that many steps with no text and no audio above `turn_silence_rms` (the RMS of samples in [-1, 1], 0.005 unless the model sets it), and text outside a reply opens one. Without them `/generate/ws` still serves it, and a conversation is refused (an omitted `intent` then means transcription, if the model's adapter serves it). The data worker marks the text chunks they arrive in with `metadata["turn"]`, their marks (`"start"` / `"end"`) in token order, on every route, before `postprocess` (which may decode them to nothing), and stamps each text and audio chunk with `metadata["step"]`, the iteration of the loop that emitted it. `/v1/realtime` frames one response per reply from the marks and puts step `k`'s audio in the reply whose text steps hold `k`, so the text and the audio node must each emit from a loop that steps once per input item. Startup refuses one that emits outside a loop, or from a partition not stepped one item at a time on every connection from the `ClientAudio` stream; `FixedChunkPolicy(chunk_size=1)` is the only policy the check takes as one. Turns as a pair of token ids fit a model that brackets each reply (Nemotron's BOS / EOS); one that marks speech another way, such as Moshi-style PAD / EPAD runs, can't declare them yet, and serves `/generate/ws` only.
- A stream ends when the client ends it: `end_input: true` ends all of the call's streams, a list of names only those. The consumer gets `producer_done` for that edge and a final chunk, and a loop fed by the stream ends as any stream-terminated loop does. Over `/generate/ws` a client that opens with `end_input: false` appends and ends input explicitly (see [Using a Server](/clients)), and a `/v1/realtime` conversation keeps it open for the call's life; every other request ends the input as soon as it is submitted. Both frontends serve `/generate/ws` and `/v1/realtime`.
- The API server's data worker is the stream's producer. The conductor tells it the consuming node and its ranks once per call, when it dispatches the request, and the data worker sends each append's items to every one of those ranks itself, and then the stream's end with how many items it carried. Every rank gets each item whole, so a client stream can't take a `sharding_config.shard_dim` entry (startup refuses one). Once the consuming partition ends, later appends for its streams are answered as late.
- A consumer with nothing to do on the step that ends its last stream (`is_final_stream_chunk`; empty when the last item was taken before the end arrived) returns None from `prepare_inputs`. The row still completes its node, so its loop ends and its partition reports done. None on any other chunk drops the row from the step. Every rank sees the same chunk, so all decline alike.

## Testing {#testing}

Validate the graph and the worker integration before you use real weights. The modular tests run on CPU and exercise models in dummy mode, where `get_submodule` returns `None`. They build a graph runtime and the Rust communicator, so build the Rust extension once per checkout:

```bash
uv pip install -e ".[dev]" pytest-xdist maturin
maturin develop --release -m rust/Cargo.toml
```

While you work, run the modules your change touches, with no GPU visible:

```bash
CUDA_VISIBLE_DEVICES="" HF_HUB_OFFLINE=1 python -m pytest -q \
    test/modular/test_state_lint.py test/modular/test_model_registration.py test/modular/test_model_contracts.py
```

Before you push, run what CI's CPU job runs (4 to 5 minutes on 8 CPUs from a local disk) and the linter:

```bash
ruff check .
CUDA_VISIBLE_DEVICES="" HF_HUB_OFFLINE=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
    python -m pytest test/modular test/distributed test/chatterbox test/kokoro \
    test/omnivoice test/sampling_test mstar/model/*/tests benchmark/worker_phases \
    -q -p xdist -n 8 --dist worksteal --timeout=120 --basetemp=$(mktemp -d /tmp/s_XXXX)
```

A visible GPU sends tests that check for one onto it, so keep `CUDA_VISIBLE_DEVICES=""`. `--timeout=120` names a stuck test instead of letting it hold the run. A new test module under `test/modular/` runs in CI as soon as it exists, so guard CUDA, weights and optional packages with a `skipif` or `pytest.importorskip`.

These modular tests cover the parts that are easy to get wrong:

| Test | Covers |
|----|----|
| `test/modular/test_state_lint.py` | The package is on `PORTED` and reaches the engine only through `mstar.engine.state`. |
| `test/modular/test_model_registration.py` | The registry, `DEFAULT_CONFIGS` and docs entries. |
| `test/modular/test_model_contracts.py` | `request_kwargs()` and each model's sampling defaults. |
| `test/modular/test_model_kv_layouts.py` | Loop caps and layouts per model. |
| `test/modular/test_resource_runner.py` | The admit, plan and commit lifecycle driven by `declare_step`. |
| `test/modular/vjepa2/fake_resources.py` | A stub array handle for running a submodule's layers without a GPU. |
| `test/modular/test_accelerator_graph_capture.py` | Capture-bucket keys, including `cg_key_info` and `additional_key_info`. |
| `test/modular/test_micro_scheduler.py` | Batch admission, and the paths for failed and backpressured requests. |
| `test/modular/test_admit_failure_handling.py` | Behavior when a resource cannot admit a step. |
| `test/modular/test_kv_offload.py` | Offload and reload of a request's cache state. |

With weights and a GPU, run `pytest test/integration/` and serve the model:

```bash

curl http://localhost:8000/health
```

Then send a request to `POST /generate` ([Native generate](/clients#native-generate)) and check the streamed output.

To start, copy the closest model on the contract: Qwen3.5 or Higgs Audio for a decoder LLM with encoders (`DeclaredDecoderModel`), Orpheus for a streaming LLM with a codec, FLUX.2 klein, Z-Image or Wan2.2 for a DiT (`DenoiseLoopSubmodule`), and Canary (`EncoderDecoderNode`) or Whisper for encoder-decoder speech.
